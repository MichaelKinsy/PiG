# The two Linux test-conformance jobs run these twenty shards, ten each, one after another, each its own go test process under go test's 10-minute package
# timeout. Every shard process shares the extension cells (testenv.SharedCellCacheDir, warmed in TestMain), so a shard's wall is its tests' own time plus
# about 26 s of process overhead; a cell built once per job instead of once per process was ~75 s of each of 28 shards in the first 28-shard layout, which made
# each job 12 minutes longer than the 12-shard layout (it is how a test's wall depended on whether it was the first to need a fixture in its shard).
# The weights are generated, not tuned by hand: automation/ci/shard-pack.py fits a model of a shard's wall (overhead + a*serial + b*parallel test time) to the
# go test -json timings of a warm run of every shard (28 shards at 4 CPUs, four containers at once: wall = 25.8 + 0.909*serial + 0.299*parallel, within 8% on
# average), pins the tests of 5 s or more by longest-first packing on top of the hash-placed rest, and picks the fewest even shard count whose modelled worst
# shard stays at or under half of the 600 s limit on a runner 1.4x slower than the host that took the timings, allowing 10% model error (190 s): 18 shards would
# model at 187 to 189 s and measured up to 220 s (51% on the slower runner), so the count is 20 (model 181 to 182 s, 140 pins), with 70 s reserved on the first two
# shards of each job for the one-time cell builds of a cold job. Regenerate after the suite changes: run every shard warm with go test -json into a directory
# and run  automation/ci/shard-pack.py --package ./test/extension-conformance --cold 70 --shards auto --replace-shards 20 --write <this file> <dir>...
# Measured side by side, 4 containers of 4 CPUs, fresh checkouts and cold caches (make test-conformance-1 and -2): the twelve shards (before) took 1,987 and
# 2,019 s a job, shards 268 to 355 and 280 to 346 s; these twenty took 1,758 and 1,743 s, shards 92 to 201 s, the worst 33% of the limit (47% on a runner
