# The two Linux test-conformance jobs run these twenty shards, ten each, one after another, each its own go test process under go test's 10-minute package
# timeout. Every shard process shares the extension cells (testenv.SharedCellCacheDir, built in TestMain), so a shard's wall is its tests' own time plus about
# 14 s of process overhead.
# The weights are generated, not tuned by hand, and can be checked: automation/ci/test-shard-timings/extension-conformance.json holds the timings they come
# from (the go test -json of a warm run of every shard of the previous 20-shard layout, one container of 24 CPUs, -p 2, 2026-11-15: for each test its shard,
# elapsed seconds, the sum of its subtests' and whether it is t.Parallel; and each shard's wall). automation/ci/shard-pack.py fits a model of a shard's wall to
# them, wall = 14.0 + 0.965*serial + 0.442*parallel test time, with an error on the 20 fitted shards of 7% on average and 18% at worst. It pins the tests of 5 s
# or more by longest-first packing on top of the hash-placed rest (161 pins, model 203 to 354 s). The packing stays at twenty shards because TestReloadLeak, one
# serial test of about 340 s that no shard pattern can split (its rows are subtests), is the floor: the slowest shard is the one that holds it, whatever the count.
# 30 s are reserved on the first shard of each job for the one-time cell build of a cold job, which TestMain does once in the first process. Regenerate when the
# suite changes (a test added since the timings were taken is hash-placed and unmeasured: the 125 tests added between 2026-11-06 and 2026-11-15, 1,265 s of
