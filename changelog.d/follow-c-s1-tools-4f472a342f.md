### Changed

- `afterTool` runs on every result a tool task writes, not only on an executed call's, as in Pi (`87eff524`): also on the error results the Harness writes itself, for a tool that does not resolve (`tool_unavailable`), invalid arguments (`invalid_arguments`, with `call.Arguments` as the model sent them), a block (`blocked`), an interruption (`interrupted`), the restart limit (`restart_limit`), and an abort (`aborted`, `abandoned`); the diagnostic code tells them apart. Such a result is bounded with the tool's output limits after the hooks, never keeps a `StructuredOutput`, and applies `Control` only when the call completes; a nested call a hook turns into a success gets its bounded output as value unless the tool declares a schema. Once a tool task was cut off more than `settings.restartLimit` times the hooks no longer run, nor in the last attempt the scheduler gives an abort handler. On an abort the hooks run inside the abort handler, so a slow hook delays `Abort()`. A slot's truncation diagnostic of an interrupted, cut-off, or aborted call is now listed after the call's own diagnostic, and stays only while the hooks keep the output.
- A call to a tool its request did not offer gets a `pi.tool` task like any call (Pi `1c6928b3`), flagged `Unoffered: true` in its input and its `pi.live.tools` slot, instead of a result the generation wrote without one: the task resolves nothing (a deferred tool the agent has still never runs), settles `tool_unavailable`, and runs `afterTool`, whose `Control` then counts toward the round (one such call no longer prevents `terminate`). Its slot starts `pending` with a `TaskId` instead of `done`, and its result entry lands in a later commit than the tool-calling answer. A round applies controls in call order, and an aborted sequential round answers its unstarted unoffered calls `tool_unavailable` instead of `aborted`.

### Upgrading

- The stored format of two built-in tasks changes. `pi.tool` is version 3: an input may carry `unoffered: true`; a stored version 1 or 2 task migrates when the Harness loads it (version 1 gets `kind: "model"`, version 2 is kept as it is). `pi.generation` is version 2: a sequential round keeps calls to tools not offered in its `pending` list, flagged in their slots. A build that still expects `pi.tool` version 2 or `pi.generation` version 1 (the previous Pi and PiG releases) leaves a task a newer build stored blocked (`task_too_old`).
