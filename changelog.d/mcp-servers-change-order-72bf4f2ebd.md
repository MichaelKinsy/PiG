### Fixed

- extensions (MCP): a server an extension registers at run time (`pi.registerMcpServer` and its SDK forms) reached the built-in MCP extension only after the call had returned, and a second server registered while an earlier one was still connecting waited until that connection attempt had ended or timed out. Pi runs the first `mcp_servers_change` handler up to its first await inside the registering call, and every registration starts its own delivery: when `registerMcpServer` returns, the built-in MCP extension has listed the server, hidden the tools of a server it replaced and activated the discovery tool, and a server registered while another still connects starts connecting at once. PiG now does the same when the first handler runs in the PiG process (the built-in MCP extension, or a compiled-in Go extension). Still different from Pi: the handlers after the first run beside the registering code instead of after its synchronous run; and the call does not wait for a first handler that lives in a subprocess extension (possible only when the built-in MCP extension is replaced or disabled), nor when the registration is made on the interactive input loop. Affected release: v0.7.0, the only release with this code (it came with 3dd4d752e8; no earlier tag has `mcp_servers_change`). <!-- fix: 72bf4f2ebd5e8721bde804fd00fba33de81c2563 -->
