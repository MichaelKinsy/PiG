### Changed

- Chord and Durable JSON objects keep Pi's key order. A decoded or built object is an ordered `*delta.JsonObject` (`chord/delta`), whose iteration follows JavaScript own-key order: array-index keys first in numeric order, then the other keys in insertion order. Before, objects were Go `map[string]any`, so diffs, snapshots and wire output listed keys in an order Pi does not produce. This is a breaking Go API change. `durable.JsonObject` is now `*delta.JsonObject`. `delta.Track` takes a `*delta.JsonObject`. Chord state values, document values and decoded operations hold `*delta.JsonObject` where they held maps. Through `encoding/json`, a `delta.Ops` batch and a `durable.DocumentContent` decode the objects their operations carry in order; a plain `[]delta.Op` field holds Go maps. Build objects with `delta.NewJsonObject` or `delta.JsonObjectOf`, decode JSON text with `delta.DecodeJson`, and read members with `Value`, `Get`, `Has`, `Keys` and `All`. `chord.CopyJSON` and `chord.CopyJSONObject` still accept a Go map and copy it in own-key order, with non-index keys ascending, because a Go map has no insertion order.
- Chord service-provider updates are written with Pi's member order (`{type, instance?, member, sequence, ops}` and `{type, snapshot|instance}`) instead of alphabetical order.
- `harness.ConversationView.Docs` is a read-only `harness.ViewDocs` instead of `map[string]durable.JsonObject`. It keeps Pi's key order: mounted documents in mount order (`pi.agent`, `pi.live`, `pi.inbox`, `pi.provider`, `pi.usage`), then documents set later in the order they arrive. Read it with `Get`, `Has`, `Len`, `Keys` and `All`, and build one with `harness.ViewDocsOf`.
- Durable records read back from JSONL or SQLite storage, and values decoded by `durable.FromJsonValue`, keep the key order of their JSON text in every `JsonValue` member: entry data, task input, checkpoint and outcome result, and submission detail. These members now hold `*delta.JsonObject` where they held `map[string]any`.
