### Fixed
- Starting the interactive mode no longer writes cursor placements between its frames or frames of its own that Pi does not write. A terminal that answers nothing used to see the header frame, two bare cursor placements (`ESC[<n>G ESC[?25l`), the window title, and the same again after each later frame: `frame, cursor, cursor, title, frame, cursor, frame, cursor, cursor`; it now sees Pi's `frame, cursor, title, frame, cursor, frame, cursor`. The start now builds the header, binds the extensions and paints one frame at the end of its start, as Pi does, and the notices that follow it (resource diagnostics, the model fallback message, the crash notice) each request a frame. A plain start also no longer waits on the built-in MCP extension: its `session_start` handler returns without awaiting what it starts, as Pi's does, and an extension handler can now say the same of itself, so the session binds without taking a turn of the event loop. A handler of a subprocess extension, which can always wait, keeps the wait. <!-- fix: 7c140b3c41, 5edf81f2ab, b4b67844c7 --> <!-- cause: PiG painted a frame right after binding the session and painted each startup notice, warning and status line at once, where Pi only requests a frame and lets the next one carry them; it also took a turn of the event loop for every `session_start` handler, because the registry could not tell a handler that returns without awaiting (the built-in MCP one) from one that can wait, and no test compared the kinds of write around the startup frames, only the bytes up to the first frame -->
