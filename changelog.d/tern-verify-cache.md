### Changed

- A signed Piglet Binary no longer hashes its whole executable at every start. After a passing start it records the check in `state/piglet-verify/verified.json` under the PiG config root, keyed by the Binary's resolved path, file identity (device, inode, size, modification and status-change times; on Windows the volume serial number, file index, size, last write time and change time), signature block and trust policy. A later start with every field unchanged still checks the signature, signer and manifest but skips the hash: on an Apple M4 Pro a 63 MB Binary's `-p` start drops from 56.1 ms to 33.3 ms, against 31.1 ms for Stock PiG. Any change to the file or the trust policy, or a missing or damaged cache, causes a full check. A failed check is never recorded, `pig verify` and `pig piglet verify` always hash the whole file, and a cache that cannot be written prints a warning without stopping the Binary. The cache cannot detect in-place corruption that keeps the file's size and times, or an in-place write that restores the modification time on a file system without a status-change time such as FAT, and the startup check does not stop anyone who can rewrite the Binary. See "Verification cache" in `docs/site/docs/piglet-binaries.md`.

### Fixed

- After `pig piglet update` installs a new release of a pulled Piglet Binary, `pig piglet list` shows the Piglet once and `pig piglet show <name>` lists every installed release, including the one the update installed. Before, each release of a Piglet without a source was listed as its own Piglet and `show` printed only the first.
