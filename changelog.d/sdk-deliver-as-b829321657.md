### Fixed

- Extension SDKs: `send_user_message` / `sendUserMessage` with no delivery mode now behaves alike in every SDK and as Pi does. The Python and Lisp SDKs defaulted the mode to `"followUp"` (since 0.7.0), so an extension that sent while the agent was running got a queued follow-up where Pi, a Node extension and a Go extension get Pi's refusal. Python `send_user_message(content)` and Lisp `(ctx-send-user-message ctx content)` now send no `deliverAs`: an idle agent runs the message at once, and a running agent refuses it with `Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.`, reported as the extension error `send_user_message` while the call returns. The Python signature changes from `send_user_message(content, deliver_as="followUp", ...)` to `deliver_as=None`, so an author who relied on the default now gets Pi's refusal while the agent runs; the old behaviour is `deliver_as="followUp"` (Lisp `:deliver-as "followUp"`), and `steer` and `followUp` are unchanged. Interactive mode now reports a refused `sendUserMessage` and a failed `sendMessage` as those extension errors instead of returning the error to the extension, as print, JSON and RPC mode do, and the Lisp `host-call-error` prints `CODE: MESSAGE` as the other SDKs write a host error. <!-- fix: b8293216578c1689f576fedda27f68a93cdaff2f -->
