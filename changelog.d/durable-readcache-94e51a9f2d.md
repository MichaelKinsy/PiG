### Added

- SQLite storage keeps a bounded cache of the results of its reads (`Entry`, `VisibleEntry`, `FindLatestHeadMarker`, `ScanEntries`, `Conversation`, `ScanConversations`, `Task`, `ScanTasks`, `Submission`, `ScanSubmissions`, `SubmissionByRequest`, `FindDocument`, `Document`, `ScanDocuments`): 2 MiB of estimated size by default (`NodeSqliteStorageOptions.ReadCacheBytes`, 0 keeps nothing). A repeated read is answered from memory with a detached copy, as a read of the database is, and the stored rows, bytes and result order are the same. The cache stays correct when another connection or process commits to the file (Pi's node:sqlite, another PiG): it reads the commit state of the database, the wal-index header SQLite keeps in the `-shm` file, with one `pread` before every read and drops everything when it changed. On the Pi storage benchmark's twelve read scenarios a warm read takes 0.8 to 18.7 us, 0.00 to 0.16 of node:sqlite's time on the same host (an exact entry lookup 9.2 us to 0.9 us, an entry page scan of 100 475 us to 18.7 us, a document replay with a 1,024-delta tail 2.8 ms to 0.9 us), with a 0 to 9 MB higher peak resident set; a read the cache cannot answer costs about 1.4 us more than before. Commits are unchanged. A database that is not a WAL file, one in exclusive locking mode, an in-memory one, one on Windows, or one not opened by `chord/sqlite/node` keeps no cache.
