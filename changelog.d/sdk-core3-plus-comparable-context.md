### Added

- Every extension SDK (Go, Rust, Python and Node) gains `OnThemeChange` and `OnToolsExpandedChange` (a change of the host's replicated theme or tool-expansion state, pushed when it changes), `SetWidgetRenderer` (Go, Rust and Python: a widget laid out at the host's width; Node runs Pi's own factory form), `Bell` (`ui.bell`: BEL between frames in the interactive UI, nothing in print, JSON and RPC modes), `ToolCallIndex`, `ToolInput` and `ToolParams` (the tool call's position in its assistant message and its arguments in `Object.keys` order), `ExtensionSourceInfo` (the loader's provenance for the extension) and `OnLoaded` (handlers that run once the extension is registered and before it serves a request). 

### Fixed

- `Context` and the types that hold one (`EventBus`, `ModelRegistry`, `ReplacedSessionContext`, `SessionManager`, `SetupSessionManager`) in the Go extension SDK are comparable again: the tool-call input a `Context` carries (`ToolInput`, `ToolParams`) is a pointer to the request's arguments instead of a slice, so adding it is no longer an incompatible change.

- `pi.events.emit` in a Go, Rust or Python factory behaves as Pi's does: the first factory-time bus call connects to the host (as `parseFrontmatter` does) and `Run` reuses the connection; the call returns once the listeners of the extensions loaded before this one and then the factory's own listeners (run inline, in subscription order) have finished; a listener that throws or panics is written to stderr as `Event handler error (channel):` and reaches neither the emitter nor the next listener; an `error` emit that nobody hears fails with the emitted error. Before, the emit was queued until after ready, and its failure only reached stderr. A factory with no host (no `PIG_EXT_SOCKET`) gets an error from its first bus call. Go gains `sdk.ServeFactory(conn, factory)` for a fused binary, which gives the factory the pipe as its connection. <!-- fix: afdb030f -->
- The Python SDK test `test_provider_transport_shutdown_does_not_settle_owned_stream[True-*]` no longer fails when the worker thread is still returning at the moment the shutdown finds no thread to wait for: it waits for the worker, as the assertion means "ends", not "has already ended". <!-- fix: de19f796 -->
- A Go extension SDK loop that is served without `Run` (a test on its own connection) no longer waits for a loaded gate that never closes; `TestToolRequestAllocBudget` hung for the whole test timeout. <!-- fix: afdb030f -->
