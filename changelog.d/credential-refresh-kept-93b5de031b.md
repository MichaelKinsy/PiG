### Fixed

- A login refresh that took between ten and fifteen seconds while another pig process opened the credential file was thrown away, and the next request asked you to log in again. pig now saves the refreshed login for that provider into the file as it is at that moment, leaving every other provider's entry as the other process wrote it; for that provider the refreshed login replaces what the file holds, a later login or logout of it by the other process included, as in Pi. This holds while the lock's own renewal has not yet noticed the takeover: once it has, the refresh still fails with the lock error and writes nothing, as in Pi. <!-- fix: 93b5de031b --> <!-- cause: When another process took auth.json's lock while a refresh was in flight (the sync lock goes stale after 10 s, a slow refresh outlasts it), Modify returned the compromise error and dropped the credential the refresh had obtained, which may have spent a single-use refresh token. While the lock's heartbeat has not yet reported the takeover, Modify now writes that provider's entry alone, under a lock of its own, into the file as it is then; what the other process wrote stays, and Pi persists the credential in that case. Once the heartbeat has reported the takeover, Modify still returns the lock error and writes nothing, as Pi throws. An fn that fails still writes nothing. -->
