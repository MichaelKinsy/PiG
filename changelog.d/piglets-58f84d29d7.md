### Added

- A Piglet Binary can declare that it accepts overlay Piglets, so a custom base such as `pig-tern` is a base harness that behaves like stock PiG started with a different Piglet, and no longer needs a fused Piglet for every combination. Set `build.allowOverlays: true` in the Piglet you build (default off; like all of `build`, it is not inherited through `extends`), and its Binary takes `--piglet`, `PIG_PIGLET_PATH` and `PIG_PIGLET_NAME` as stock PiG does, with the same project trust, Piglet directories and Package install flow. The overlay merges onto the Binary's Piglet exactly as an `extends` child merges onto its base: `systemPrompt` replaces, `extends.remove` removes extensions, skills, Packages, strip entries and the frontend slot (the Binary then starts without its compiled-in frontend), and `extends.allowWiden: true` widens `tools`, `discovery`, `agentEnv` and an extension's `tools`. An `extends` block may omit `source` in an overlay; it then extends the Binary. Only what is compiled into the Binary is refused, with the field, the Binary and the reason named: setting a new `slots.frontend`, re-enabling a strip entry a build tag compiled out (`stripped(binary)`, such as `strip.extensions: [mcp]`; runtime strips of tools, commands, themes, skills and prompt templates can be re-enabled), and naming a fused or embedded extension again with origins. A Binary with `allowOverlays` accepts `--system-prompt` with stock precedence and discovers ambient extensions and skills from its Piglet's `discovery`, as stock PiG does; a Binary without it keeps its baseline and refuses both. `/piglet` prints `Overlay of: <Binary>` on an overlay run.
