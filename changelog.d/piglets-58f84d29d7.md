### Added

- A Piglet Binary can declare that it accepts overlay Piglets, so a custom base such as `pig-tern` no longer needs a fused Piglet for every combination. Set `build.allowOverlays: true` in the Piglet you build (default off; like all of `build`, it is not inherited through `extends`), and its Binary takes `--piglet`, `PIG_PIGLET_PATH` and `PIG_PIGLET_NAME` as stock PiG does: the selected Piglet resolves with the same project trust, Piglet directories and Package install flow, and merges onto the Binary's own Piglet as `extends` merges a child onto its base. An overlay can add extensions, skills and Packages, set `model`, narrow `tools` and strip more built-ins. It cannot replace or remove an extension or skill the Binary carries, set `slots.frontend` or `systemPrompt`, widen `tools`, `discovery`, `agentEnv` or an extension's `tools`, or re-enable a stripped built-in; each refusal names the field and the Binary, and a failed overlay never falls back to the Binary's own Piglet. The setting is part of the baked Piglet, so the Binary's signed Piglet digest covers it, and signature, closure and update checks are unchanged. A Binary built without the setting still refuses the selectors and now names the Binary and `build.allowOverlays` in the message. `/piglet` shows `Overlay of: <Binary>`, and `pig piglet show` lists `allowOverlays`. Additive record D202.
