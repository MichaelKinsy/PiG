### Fixed

- In the Go Chord v2 workers (`chord/nextnode/workers`), `Workers.Retry` and a plugin rollout no longer leave a crashed worker stopped when they run after the failed automatic resolve of the worker's address has read the crash and before the route has handled its rejection: the route started nothing for the retry because the address was still resolving, then forgot the address with the rejection, and the worker stayed down with no state until the next hold. The route now remembers a retry that finds the address's resolve running and, if that resolve rejects, handles the rejection as usual and resolves the address once more, so the worker starts once; a resolve that succeeds takes the retry with it and a healthy worker is not restarted. <!-- fix: 4463d9e40b --> <!-- cause: the route treated a retry that found its address resolving as satisfied by that resolve, which holds in Pi where a rejection and its handling are one chain of microtasks no retry can enter, but not in Go where the answer is handled in a later section a retry can precede -->
