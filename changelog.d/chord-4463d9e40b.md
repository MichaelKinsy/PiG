### Fixed

- In the Go Chord v2 workers (`chord/nextnode/workers`), `Workers.Retry` and a plugin rollout no longer leave a crashed worker stopped when they run after the failed automatic resolve of the worker's address has read the failure the workers recorded (the crash a start finds, or the failure of an address that is already failed) and before the route has handled the rejection: the route started nothing for the retry because the address was still resolving, then forgot the address with the rejection, and the worker stayed down with no state until the next hold. The route now remembers a retry that finds the address's resolve running, and the workers' rejection of a recorded failure tells it whether that failure was ended since: the route handles such a rejection as usual and resolves the address once more, so the worker starts once. Any other rejection, the application's own start failure included, takes the retry with it, as in Pi (one resolve, one `resolve_failed` report, one start, the address failed); a resolve that succeeds
