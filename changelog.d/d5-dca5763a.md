### Fixed

- A notification, status or message that an extension queues on `setImmediate` or `setTimeout(0)` from inside a tool now reaches an RPC client after `agent_settled`, as Pi's loop does, instead of before `tool_execution_end`. Pi runs those callbacks when its event loop turns, which a run's chain of microtasks never gives it. The Node runtime ran them as soon as the tool answered, because it is another process, and its host calls arrived mid-run. The host now holds such calls while the RPC run chains microtasks and runs them in arrival order at the next real wait: a model response's I/O, a built-in tool's run, a dialog, a compaction or an auto-retry delay, or the end of `agent_settled`. A `process.nextTick` callback's notification follows the `tool_execution_end` of the tool that queued it, as in Pi, and the callbacks of a tool that returns while a sibling tool of its batch still runs reach the client right after its `tool_execution_end`. <!-- fix: dca5763ac5, 38901751db -->

- A `setTimeout(0)` or `setImmediate` callback that an extension queues while an RPC stdin command runs (a `model_select` handler during `set_model`, say) now reaches the client after the command's response, as in Pi, instead of before it in about one run in ten. Pi runs the command's microtasks and writes its response before its loop runs a timer, so the Node runtime now holds its timer callbacks from the moment the host reads the command until the host has written the response, and the host waits for the runtime's acknowledgement of that hold before it sends the command's first event. A handler that is still awaiting real I/O (a child process, a dialog) is not held back, because Pi's loop turns while it waits and runs the timer. A call that a Go, Rust or Python extension makes through a context whose request returned runs on arrival while another request of the extension is in flight, instead of waiting for a loop turn that waits for that request: a handler that kept an earlier request's context and awaited a call through it used to hang the run. <!-- fix: d6aaf72307, 7a4ddb3733, 8506081bd3, 463879414a, 58563ba284, 5a182154fc -->

### Changed

- The wire carries two new optional fields on a host call: `timer` (`CallPayload.Timer`) and `tick` (`CallPayload.Tick`, set with `timer` by the Node runtime for `process.nextTick` callbacks and for timer callbacks that fire while a sibling tool runs). The Node runtime sets it on the calls of a `setTimeout`, `setInterval` or `setImmediate` callback that fires after its request's handler returned, and on the work such a callback starts. The Go, Rust and Python SDKs set it on a call made through a request's context after the request's handler returned. A new host notification `timer_defer` (host to Node runtime, `on` and `seq`) and its answer `timer_defer_ack` (`seq`) carry the command hold. The host and all four runtimes change together with no negotiation, so an SDK built from an older release does not set it and its calls run on arrival, as before. `subprocess.CallPayload` gains the exported fields `Timer` and `Tick`, so an unkeyed `CallPayload{...}` literal needs a fifth value.

### Upgrading

- If code outside this repository builds `subprocess.CallPayload` with an unkeyed literal, add the two fields (`false` keeps today's behaviour) or switch to keyed fields. `coding.ExtensionHost` gains `SetTimerTurns(*jsloop.Turns)`; an embedder that implements the interface adds a method that does nothing, because `internal/jsloop` is not importable outside the module: it cannot write the parameter type, so such an embedder cannot implement the interface and has no replacement to migrate to. Extensions in every SDK need no change.
