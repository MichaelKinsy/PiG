### Changed

- RPC mode holds its input from the start of a reload to the response of the command that awaited it, also while a reloaded extension's factory awaits a timer or I/O (D630). Pi reads stdin inside such a load: a prompt written then runs on the extension the reload has already invalidated and fails with the stale-context error, and the end of stdin exits without the response of the reloading command. In PiG the prompt runs on the reloaded extension after the reload, and the end of stdin is read after it.
- A reload ends a TypeScript extension whose handler holds its thread for more than 5 s across the reload, and loads it again in a new process. The command in flight on it is answered with an error that says the extension did not acknowledge a reload, and the reload says so in one line, `extension "<name>" did not acknowledge the reload within 5s and was restarted`: under Extension issues in the interactive `/reload` status, and on stderr in print, JSON and RPC mode. Pi has no such state, because its extensions run on the thread that runs the reload. This is the one case in which the host ends a running handler (D19; the exception to D56).

### Fixed

- RPC mode: a prompt written right behind an extension command that calls `ctx.reload()` is read after the reload, runs on the reloaded extension and answers after that command, as in Pi. PiG read it while the reload ran: it ran on the extension being replaced and answered first, and with a TypeScript extension neither prompt was answered and the stream stayed silent until stdin closed. A client that waits for each response before it writes the next record was not affected. Present since 0.5.2. <!-- fix: d04750891b39f6d01f26116bac727542e213c003 -->
- RPC mode: a prompt read while a `session_start` handler of a reload waits runs on the reloaded extension; it ran on the replaced one, whose `ctx` was stale. <!-- fix: d04750891b39f6d01f26116bac727542e213c003 -->
- Extensions: a host call that a handler of a TypeScript extension makes while a reload is replacing that extension is answered with Pi's stale-context error, from the point the reload has run the `session_shutdown` handlers; a call that was already waiting for its answer keeps it. PiG dropped such a call while the replacement was loading, so the handler's command never finished and, in RPC mode, its prompt got no response. <!-- fix: 095939f576f8ffc10909e11ac7770dba3f4c58e4, bf60a5312160b533cdf49ef288b38d7a43f5269e, de7a83636fa9c44713bae9132534712af2ed94e4 -->
- Extensions: a call that a handler of a TypeScript extension makes just before a reload invalidates the extension is served, as a call made before Pi's `invalidate()` is. The host marked the extension stale when it sent the notification, before the extension's runtime had read it, so the call was refused; a call the handler does not await, such as `ctx.ui.notify`, was dropped with a diagnostic where Pi throws, and in RPC mode the command's prompt answered with no `extension_error`. The reload now waits until the runtime has acknowledged the invalidation. <!-- fix: a31c30a42a3a283ad1e8f7e0f70096ec8028efba -->
- RPC mode: a dialog answer read in the same stdin chunk as a prompt, while a reload runs, is delivered after the lines of its chunk, as Pi delivers it, so the notifications and responses of the two commands come in Pi's order. PiG delivered the answer at once and the order was a race: the reloading command could answer before the prompt of its chunk, or the prompt could answer without its notification. <!-- fix: 2a1edc2dc00b64e92b96e8c24de75f956c959658 -->
- Interactive mode: a `/reload` that fails leaves the old extension instances stale, as in Pi: their captured `pi` and `ctx` throw the stale-context error, and a later `/reload` that succeeds loads live instances. PiG left the old instances in service after the failure. <!-- fix: 83d0c737059d6b0f610f800d175a5cb9183b95bb -->
