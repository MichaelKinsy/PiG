### Changed

- The ordered-object JSON readers (extension provider headers, login duplicate-field scan, model registry headers, the models store and catalog readers, theme loading, the model generators, `internal/orderedjson`, tool-call argument entries and the parity tools) now read with `encoding/json/jsontext` and the `internal/jsonopts` option set instead of `encoding/json` v1 tokens. They are closer to `JSON.parse` in two ways. A document cut off after a value (`{"a":1`, or `{"a":1]`) is now an error: the readers that returned once they had their keys never checked the closing token. A document that is not an object but an array (`[1]`) is now an error or no entries, where some readers answered with garbage or panicked. A number outside float64 range at the top level is not an error either: `JSON.parse` gives `Infinity` for `1e400`, so a reader that wants an object returns no entries for it, as Pi does. The extension login duplicate-field scan no longer rejects such a number itself; the typed decode that follows still does. Decoding cost and allocations are unchanged within benchmark noise.
- Six readers stay on `encoding/json` v1 on purpose: `ai/auth_store.go`, `ai/credential_json.go`, `coding/cli/rpc_object.go`, `coding/extension/builtin/codemode/execute.go`, `internal/codingagent/session_export.go` and the extension conformance test fixture. They share `extensions/sdk/json`, which keeps a lone surrogate (`"\ud800"`) as WTF-8 bytes the way JavaScript strings do. `jsonopts.Parse` turns invalid UTF-8, and so a WTF-8 lone surrogate, into U+FFFD, which would change a value Pi passes through unchanged.
