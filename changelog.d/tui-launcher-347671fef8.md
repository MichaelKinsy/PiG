### Fixed

- Cancelling the context of `tui.StartTerminal` now ends the terminal client as `Stop` does, as its documentation says: the loop used to stop on the cancelled context and nothing else, so the sandbox's Node child process kept running, the link sockets stayed open and the terminal was not given back (the child outlived the client until the embedding program ended). `Stop` and the exit code now wait for the client's end whoever began it. <!-- fix: 257263d016b1e41ad4bbae1c132ad8a770b0f01d --> <!-- cause: the terminal launcher's loop returned on its cancelled context without running the client's end, and Stop reaches the sandbox and the link sockets only through that end, so a cancelled context ended the loop and nothing else --> <!-- tests: TestCancellingTheContextEndsTheClientItsSandboxProcessAndItsSockets -->
- A terminal client no longer handles a message of its sandbox before it has installed the sandbox: a socket the sandbox opened in its first moments made the launcher post to a nil sandbox (a nil pointer panic that ended the embedding program), and a request it made then was dropped unanswered. The launcher holds what a sandbox sends while it is being started and handles it in order once installed, as Pi's `Sandbox.start` continuation does. <!-- fix: 347671fef856cb2214c21f11b529bbd5fe57687f --> <!-- cause: the launcher installed its sandbox on the loop after the sandbox had begun passing its child's messages to the loop, so a message could be handled with no sandbox installed, where Pi's launcher assigns the sandbox before any of its output is delivered --> <!-- tests: TestASandboxsFirstMessageThatComesBeforeItIsInstalledIsHandledWithItInstalled, TestAtMostAQueuesWorthOfMessagesAreHeldForASandboxThatIsNotInstalledYet, TestWhatASandboxSentBeforeARestartReplacedItIsNotHandledForTheNext -->
