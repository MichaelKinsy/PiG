### Fixed

- A `pi.events` listener's failure is reported before the command that emitted answers, as in Pi: an RPC client reads every `extension_error` line before the command's response (`E E E E R`, and `E R` for a listener that rejects after an await), and print and JSON mode write the error to stderr before the command's own output, whether the extensions share a Node process or each run in their own. Cause: a Node runtime writes the failing listener's `report_error` notification before the response, but the connection's read loop routed the response straight to its waiter while the notification went through the Host's loop; a shared Node realm sent the listener's report on the listener's connection and the emitter's response on another; and the quiesce that releases the emitter of a listener that rejects after an await was counted on the read loop before the Host's loop applied the report. The read loop now queues the response and the quiesce behind the unapplied report, and a shared realm sends the report on the emitter's connection, naming the listening extension (the Host takes the name only for an extension of the connection's own process and applies any other name's report as the connection's own). No released PiG has this: the `report_error` notification arrives with the same release. <!-- fix: 0aecafce0a, 447a4edc21, 6390f27ae9, 95a798f82a -->
