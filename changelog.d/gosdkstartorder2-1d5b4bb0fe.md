### Fixed

- The Go SDK's start-order tests no longer fail on a loaded machine since v0.5.2 (a test-claim fix: the SDK is unchanged). The SDK guarantees the order in which handlers are invoked: a handler is invoked only after every earlier request's handler was invoked or its request ended without one. The tests asserted the order of the handlers' first statements, which is more than that, and a goroutine the operating system holds back after its place was released is overtaken by the handlers behind it, so one of 300 runs failed under one-CPU pressure. The tests now read the order where the SDK keeps it, and a new test holds one handler back to show that the invocation order stays intact while the first statements do not. <!-- fix: 1d5b4bb0fe --> <!-- cause: the tests asserted first-statement order, which is more than the SDK's invocation-order contract, and a goroutine descheduled between the release of its place and its handler's first statement is overtaken --> <!-- tests: TestEventAndCommandHandlersStartInArrivalOrder, TestToolCallHandlersStartInArrivalOrder, TestOvertakenHandlerKeepsItsInvocationPlace -->
