# plugnode: what a Pi user or plugin sees differently from Pi (after the direction flip)

`chord/nextnode/plugins` against Pi `b556cfe5` (vendored at that pin) `packages/chord/src/next-node/plugins`. The owner decision (2026-11-01, docs/plan/chord-plugins-node-evaluator.md) covers "build in Go, evaluate in a Node subprocess". These were the observable consequences (2026-11-01, owner decision: support the feature fully, no divergences; the designs are in plan section 10, the evidence rows in plugfull-<slice>.md), each checked against the code or a test named here, with whether it can be closed now and the cost. No divergence rows are added for them (the reviewer's S2 asked for numbers; the owner's call is to list, not to number).

Not differences any more (the first port's, closed by the flip, `NodeHost.Link`): one Go host can own any number of NodeHosts, a Go host that has a parent can load plugins, and Pi's end-to-end case (`server.get(Notes)` routed to the worker, `notes.add`, the label frames on the server's reference) is ported with one observing server (plugins_endtoend_test.go).

## Differences

Status: **closed** (a test that failed before), **additive** (isolation, strictly more than Pi, stated), **open** (reason and owner call).

## Adaptations of Pi's tests (process boundary, not behavior)

- A case that reads a JavaScript object of the evaluated facet (`facet.made instanceof ChordError`, `facet.values`) reads it through the probe (plugins_probe_test.go), marked in each test's comment.
- `plugins.test.ts` "abort after the commit": Pi spies `batch.commit`; the port holds `Attempt.checked` in the subprocess.
- The end to end case runs the server kind's own plugins on a NodeHost of their own, and `server.get(Index)` is `NodeHost.Get` on it (difference 1).
