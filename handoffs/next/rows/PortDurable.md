## e50dc7af9 disposition (why no scheduler.go change)

Pi's bug is a yield between a decision region's result and the code that applies it (`await this.#region(...)` then `delete`/`clear`): a publication's observer runs in that gap and queues a waiter/holder the pass then erases. In Go a pass decides and applies under ONE hold of TaskScheduler.mu (regionLocked returns with mu held; reserve applies `s.runnable.Delete(dropped)` and finalizeLocked `s.finalizeChecks.Clear()` before any unlock), and every publication observer that adds to runnable/finalizeChecks (scheduler_index.go) takes mu. mu is released only inside waitGatesLocked, after which regionLocked re-runs decide over the CURRENT sets, so a stale decision is never applied. The core (durable/core/session) is single-stepped: reservation scans and deletes in one synchronous callback; finalize already takes `finalizeChecks` (j.round/j.taken, sched_obs.go:384) before its first region. So the take-before-plan restructuring has no Go counterpart; porting it would change nothing observable and diverge from the lock-based design. Loop-smell note: the two ported tests pass before and after because Go has no gap; they pin the ordering (a notification published as a pass plans survives it; holder ends only after the child it held) and fail if a pass is changed to release mu between decide and apply (see report for the mutation run).
