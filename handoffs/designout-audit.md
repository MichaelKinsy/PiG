## OWNER questions

**Q1. AgentSessionConfig.agent, .cacheWarmer, .extensionRunnerRef (3 rows).** Pi exports `AgentSession`, and its constructor takes an externally built `Agent` and an optional `CacheWarmer` (agent-session.ts:253,266,296). Only sdk.ts:461 calls it in Pi. Go's `coding.NewAgentSession(SessionOptions)` (session.go:350) builds its own agent and warmer.
- A: keep. Record a numbered divergence: Go sessions own their agent; `CreateAgentSession` is the SDK entry point, as Pi's docs/sdk.md shows.
- B (recommended under the 2026-10-08 owner direction 'port Pi's shape additively'): add optional `SessionOptions.Agent` and `SessionOptions.CacheWarmer`; NewAgentSession installs its hooks into the given agent. `extensionRunnerRef` stays designed out, because Go closes over the runner, and it gets a D-number.
- C: full Pi-shaped `NewAgentSession(AgentSessionConfig)` with a required Agent. This breaks the public Go API.

**Q2. AnthropicOptions.client (3 rows).** Pi lets a caller inject a pre-built Anthropic SDK client, such as `AnthropicVertex`, and skips its own client construction (anthropic-messages.ts:286-290,607-609). Go has only `StreamOptions.Fetch` (an *http.Client).
- A: keep with a D-number. Document that Fetch with a custom RoundTripper is the injection point. Anthropic-on-Vertex then needs user code for the URL, auth and body rewrite.
- B: port a Go `AnthropicClient` interface option (the Messages stream call). The provider uses it instead of its HTTP path and skips federation and OAuth, as Pi does.
- C: B plus a built-in Vertex client.

**Q3. StdinBuffer getMaxListeners/setMaxListeners (4 rows).** The lead ruled on 2026-10-08 01:30 not to add them with a magic 10. Pi inherits Node's limit and prints `MaxListenersExceededWarning` to stderr after 10 listeners per event. Under the 2026-10-09 rule this observable difference needs an owner D-number.
- A (recommended): keep, and ratify a D-number for the missing warning.
- B: port both methods with Node's default of 10 and the warning text.

**Q4. chord Context.toString (2 rows), with rev-designout-audit finding 10.** Pi's public `@earendil-works/chord/context` API has roots whose `toString` is `[Context BACKGROUND_CONTEXT]` and `[Context TODO_CONTEXT]`, and each layer appends `.WithValue(<key description>)` (`context/index.ts:28-30,50-56`). Pi's test asserts both strings. Go maps the API to `internal/chord/chordctx` over `context.Context`. Go library callers cannot import it, and its String() is Go's stdlib text, which also prints the value. A review probe printed `context.Background.WithValue(*chordctx.keyToken, one)` for the layer that Pi prints as `[Context BACKGROUND_CONTEXT].WithValue(first)`.
- A: keep the API internal and record a D-number for the toString text. Mark the ported test's adaptation with that D-number.
- B (recommended under the full-parity priority): add a public Go `chord/context` package with Pi's roots (`BackgroundContext` and `TodoContext`, with Pi's String()) and value and abort layers whose String() matches Pi. Rebind the Context, BACKGROUND_CONTEXT and TODO_CONTEXT rows to it and port Pi's exact strings in the test.
- C: B without the String() text, with a D-number for the text only.
