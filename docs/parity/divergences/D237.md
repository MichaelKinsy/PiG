## D237 Exit waits for a started OAuth refresh to be saved

What: PiG ports Pi main b2cb62923 (`fix(coding-agent): wait for a started OAuth refresh to be saved before exit`, #11812, fixing #11692), which is not in Pi 1.5.0.

1. `ai.RuntimeCredentials` tracks every `Modify` until it returns, written or failed (Pi's `pendingModifications`), and `Settled(ctx)` returns when the modifications started before the call have returned. A modification's own error stays with its caller. `ModelRegistry.SettleCredentialWrites` and `coding.ModelRuntime.SettleCredentialWrites` are Pi's `ModelRuntime.settleCredentialWrites`; `coding.Runtime.SettleCredentialWrites` reaches them from a Runtime.
2. The process's `coding.Runtime.Close` (Pi's `AgentSessionRuntime.dispose`) waits for them after it has closed the Session. Every mode exits through it: interactive mode and the startup benchmark return to main's deferred `Close`; print and JSON mode call it in the finally of `runPrintMode` and, after a SIGTERM or SIGHUP, in the signal's disposal before `exitProcess(128+signum)`; RPC mode waits in `rpcShutdown`'s dispose (stdin end, a signal or an extension's shutdown request) before it flushes and exits, and `Close` after that finds nothing pending. The low-level `Runtime` of a Session replacement (`Dispose` of a factory result) does not wait, as Pi's `teardownCurrent` does not.
3. No timeout of its own, as in Pi: the OAuth refresh (15 s) and the auth.json lock wait (30 s) bound the wait. A second signal exits at once: RPC mode's `rpcShutdown` removes its signal handlers before it disposes, so the next one takes the default action; print mode exits with 128+signum on the second signal while the disposal waits (Pi's handler stays registered and exits on the already-disposing runtime). Interactive mode ignores a signal during shutdown, as Pi's `shutdown()` returns when `isShuttingDown`.

PiG-only paths that Pi has no counterpart of, brought under the same rule: the Radius OAuth refresh now goes through the registry's credential overlay (`refreshRadiusOAuth`), so it is tracked; a subprocess extension's native provider refreshes the credential in the catalog refresh through `ai.ModifyCredentialDetached` and `ai.RefreshOAuthDetached`, which is `refreshStoredOAuthCredential`'s rule: the caller's cancellation ends only the wait for the auth.json lock, and a request that has started is bounded by the 15 s refresh timeout alone. Before, the cancellation of the RPC catalog refresh (stdin closed, a signal) cut that request or discarded the rotated token after it. Not covered: the standalone GitHub Copilot token manager (`copilotTokenManager`), which holds `*AuthStorage` directly and never goes through `RuntimeCredentials`.

Why: Pi main's rule, ahead of the pin. If the process exits after the token request went out but before the new token is written, the provider has spent the old single-use refresh token and auth.json keeps only that one; the next request fails with `invalid_grant`.

Pi bug: 1.5.0 exits without waiting (#11692, fixed on Pi main by the commit above).

Owner decision: approved by owner Michael Kinsy on 2026-11-05 for 0.7.1 (scope proposal M7, port of Pi main b2cb62923 ahead of the pin).
