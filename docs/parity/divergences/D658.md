## D658 The Go, Rust, Python and Lisp SDKs invoke handlers in request arrival order, but a descheduled thread can run its handler's first statement after a later request's

What: Pi runs a handler of an event, a command or a tool call synchronously up to its first `await` in the order the requests came: `runner.ts:1110` is `await handler(event, ctx)` with no await before the first handler, and a parallel batch invokes each call in source order (`agent-loop.ts:656-658`). The Node runtime serves frames on one thread and keeps that. The Go, Rust, Python and Lisp SDKs serve each request on a thread of its own. Each reserves a start place for a `tool_call`, `event` or `command` request in arrival order and invokes the handler only after every earlier request's handler was invoked or its request ended without one. That fixes the order of INVOCATION. It does not fix what a handler runs first: a thread descheduled between the gate's release and its handler's first statement can be overtaken by the thread of the next request, so a handler's own first-statement log can read [c2 c1] where Pi and Node never read it. Go: measured on 2026-11-18, about 5e-5 per start under one-cpu pressure, 0 in 600 unpressured runs; the gate arrived in v0.5.2 (before it, event and command requests had no gate). Rust: by reading, not measured: `extensions/sdk-rs/src/request_start_order.rs` states the limit itself ("a thread that the operating system preempts between its hand-off and its handler's first statement can still be overtaken, and no Rust construct closes that window"). Python: the same hand-off by the code's order (`_RequestStart.begin` in `extensions/sdk-py/pig_sdk/__init__.py` sets the place's event, then the request's thread calls the handler), and measured on 2026-11-18 (CPython 3.12.3, switch interval 5 ms): a handler that does not yield before its first statement was never overtaken, 0 of about 360,000 starts, in the three Python start-order tests (`test_tool_dispatch.py`: `tool_call` 16 x 24, event and command 18 x 24, the late request thread) run 300 times each free, pinned to one cpu, and pinned to one cpu with 8 busy loops (the form that broke Go in 7 of 300 runs): 900 of 900 under pressure; the conformance cell `TestToolBatchStartsInSourceOrderAcrossSDKs/subprocess-python` 100 of 100 free and 100 of 100 under pressure. The window is reached when the interpreter switches threads between the hand-off and the first statement, which a probe forced (a mixed batch of 16, one handler made to yield, 200 rounds each): a yield as the handler's first statement, `sleep(0)`, overtook 80 of 200 free and 178 under pressure, `sched_yield` 0 free and 195 under pressure, `sleep(1 ms)` 200 free; a yield placed inside `begin()` after `done.set()`, `sleep(0)`, 64 free and 172 under pressure, `sched_yield` 0 free and 196 under pressure; with no yield 0 of 200 free and under pressure; in all 2400 rounds the order through the gate was the arrival order. So in practice the interpreter keeps the handing thread running, which the code does not guarantee. Lisp: by reading, not run: `ticket-begin` in `dispatch.lisp` hands the place on before the handler runs, so the same window exists by the code's order.

Audience: an extension author whose handlers of two requests that arrive together (two `tool_call`s of a parallel batch, two commands, two events) record or act on their FIRST statement and depend on the order, and who runs under CPU pressure. A Node extension, and Pi, never see it.

Why: the order Pi keeps is a property of one thread running each handler to its first await; a runtime with one thread per request cannot hand the place on at the handler's first statement, because it does not know where that is. It is not made faithful now: holding the place until the handler's first host call was tried and rejected, because it stalls every later handler behind a handler that never calls the host and can deadlock when that handler waits for a later request.

Pi bug: none.

Scope: the Go, Rust, Python and Lisp SDKs, `tool_call`, `event` and `command` requests, in every load mode (isolated, packed, fused Go); the rate is measured for Go (about 5e-5 per start under one-cpu pressure) and for Python (none seen in 900 pressured runs, unless a handler yields before its first statement), by reading for Rust and Lisp. Not: D187, which holds a batch call's first host call until the earlier calls wrote theirs (a different place; this record is about the handler's first statement); the order of invocation, which is kept (`TestEventAndCommandHandlersStartInArrivalOrder`, `TestToolCallHandlersStartInArrivalOrder`, `TestOvertakenHandlerKeepsItsInvocationPlace`); Node.

Owner decision: 2026-11-18, owner Michael Kinsy approved the coordinator's recommendation "Start-order limit: give it a numbered record, covering Go, Rust and Lisp" with the words "proceed with recommendations"; on the same day, shown that the Python SDK has the same hand-off by reading, he chose "Cover Go, Rust, Python and Lisp. Python and Lisp are marked "by reading, not measured"; Pi and Node never reorder." (the coordinator's form, option text quoted). Python was measured afterwards (What). The wording of this record awaits the owner's read.

SCRUTINIZED:approved

Remove when: an SDK can invoke the handler and hand the place on in one step the scheduler cannot split, or a start place that is held until the handler's first host call without stalling later handlers or deadlocking.

Call-site markers (`pig divergence (D658): ...`): `extensions/sdk/extension.go` (`Extension.passStart`), `extensions/sdk-rs/src/request_start_order.rs` (`RequestStart::begin`, called at the begin sites of `extensions/sdk-rs/src/extension.rs`), `extensions/sdk-py/pig_sdk/__init__.py` (`_RequestStart.begin`), `extensions/sdk-lisp/src/dispatch.lisp` (`ticket-begin`).

Evidence: `extensions/sdk` `TestOvertakenHandlerKeepsItsInvocationPlace`, `TestEventAndCommandHandlersStartInArrivalOrder` (`extensions/sdk/request_start_order_test.go`) and `TestToolCallHandlersStartInArrivalOrder` (`extensions/sdk/tool_prepare_arguments_test.go`); Python `test_tool_call_handlers_start_in_arrival_order`, `test_a_request_thread_that_runs_late_does_not_let_a_later_handler_start_first` (invocation order; none asserts first-statement order, and none failed in the 900 pressured runs of What); the conformance helpers `startOrderStrict` (`test/extension-conformance/tool_dispatch_test.go`, true for Node and Python, used by `TestToolBatchStartsInSourceOrderAcrossSDKs`, whose Python cell passed 100 of 100 under pressure) and `firstStatementOrder` (`test/extension-conformance/ordering_test.go`, Node only, used by two ordering rows), which between them leave the first-statement order of Go, Rust and Lisp unpinned; the cure that made the invocation order hold, merged on the batch as `3fe84706cc`; Rust `extensions/sdk-rs/src/request_start_order.rs`; Lisp `extensions/sdk-lisp/src/dispatch.lisp`. The Go rate: about 5e-5 per start under one-cpu pressure and 0 in 600 unpressured runs (measured 2026-11-18). The Python figures are those of What (lane `PySdkStartOrder`, batch `3b5e51db29`, 2026-11-18).

Parity allowance: no parity scenario observes it: a scenario's extension handlers are written to read in order, and the window is a scheduler race of microseconds that no scenario can pin; the conformance helpers above say which realizations are held to the strict first-statement order.
