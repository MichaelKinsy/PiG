## D658 The Go, Rust, Python and Lisp SDKs invoke handlers in request arrival order, but a descheduled thread can run its handler's first statement after a later request's

What: Pi runs a handler of an event, a command or a tool call synchronously up to its first `await` in the order the requests came: `runner.ts:1110` is `await handler(event, ctx)` with no await before the first handler, and a parallel batch invokes each call in source order (`agent-loop.ts:656-658`). The Node runtime serves frames on one thread and keeps that. The Go, Rust, Python and Lisp SDKs serve each request on a thread of its own. Each reserves a start place for a `tool_call`, `event` or `command` request in arrival order and invokes the handler only after every earlier request's handler was invoked or its request ended without one. That fixes the order of INVOCATION. It does not fix what a handler runs first: a thread descheduled between the gate's release and its handler's first statement can be overtaken by the thread of the next request, so a handler's own first-statement log can read [c2 c1] where Pi and Node never read it. Go: measured on 2026-11-18, about 5e-5 per start under one-cpu pressure, 0 in 600 unpressured runs; the gate arrived in v0.5.2 (before it, event and command requests had no gate). Rust: by reading, not measured: `extensions/sdk-rs/src/request_start_order.rs` states the limit itself ("a thread that the operating system preempts between its hand-off and its handler's first statement can still be overtaken, and no Rust construct closes that window"). Python: by reading, not measured: `_RequestStart.begin` (`extensions/sdk-py/pig_sdk/__init__.py`) sets the place's event and the request's thread then calls the handler, with the same hand-off before the handler's first statement; the interpreter can switch threads between the two (the earlier sentence of the parity table, that the GIL keeps the handing thread running, is not guaranteed by the code and is withdrawn). Lisp: by reading, not run: `ticket-begin` in `dispatch.lisp` hands the place on before the handler runs, so the same window exists by the code's order.

Audience: an extension author whose handlers of two requests that arrive together (two `tool_call`s of a parallel batch, two commands, two events) record or act on their FIRST statement and depend on the order, and who runs under CPU pressure. A Node extension, and Pi, never see it.

Why: the order Pi keeps is a property of one thread running each handler to its first await; a runtime with one thread per request cannot hand the place on at the handler's first statement, because it does not know where that is. It is not made faithful now: holding the place until the handler's first host call was tried and rejected, because it stalls every later handler behind a handler that never calls the host and can deadlock when that handler waits for a later request.

Pi bug: none.

Scope: the Go, Rust, Python and Lisp SDKs, `tool_call`, `event` and `command` requests, in every load mode (isolated, packed, fused Go); the rate is measured for Go only. Not: D187, which holds a batch call's first host call until the earlier calls wrote theirs (a different place; this record is about the handler's first statement); the order of invocation, which is kept (`TestEventAndCommandHandlersStartInArrivalOrder`, `TestToolCallHandlersStartInArrivalOrder`, `TestOvertakenHandlerKeepsItsInvocationPlace`); Node.

Owner decision: 2026-11-18, owner Michael Kinsy approved the coordinator's recommendation "Start-order limit: give it a numbered record, covering Go, Rust and Lisp" with the words "proceed with recommendations"; on the same day, shown that the Python SDK has the same hand-off by reading, he chose "Cover Go, Rust, Python and Lisp. Python and Lisp are marked "by reading, not measured"; Pi and Node never reorder." (the coordinator's form, option text quoted). The wording of this record awaits the owner's read.

SCRUTINIZED:approved

Remove when: an SDK can invoke the handler and hand the place on in one step the scheduler cannot split, or a start place that is held until the handler's first host call without stalling later handlers or deadlocking.

Call-site markers (`pig divergence (D658): ...`): `extensions/sdk/extension.go` (`Extension.passStart`), `extensions/sdk-rs/src/request_start_order.rs` (`RequestStart::begin`, called at the begin sites of `extensions/sdk-rs/src/extension.rs`), `extensions/sdk-py/pig_sdk/__init__.py` (`_RequestStart.begin`), `extensions/sdk-lisp/src/dispatch.lisp` (`ticket-begin`).

Evidence: `extensions/sdk` `TestOvertakenHandlerKeepsItsInvocationPlace`, `TestEventAndCommandHandlersStartInArrivalOrder` (`extensions/sdk/request_start_order_test.go`) and `TestToolCallHandlersStartInArrivalOrder` (`extensions/sdk/tool_prepare_arguments_test.go`); Python `test_tool_call_handlers_start_in_arrival_order`, `test_a_request_thread_that_runs_late_does_not_let_a_later_handler_start_first` (invocation order; none asserts first-statement order); the conformance helpers `startOrderStrict` (`test/extension-conformance/tool_dispatch_test.go`, true for Node and Python, used by `TestToolBatchStartsInSourceOrderAcrossSDKs`) and `firstStatementOrder` (`test/extension-conformance/ordering_test.go`, Node only, used by two ordering rows), which between them leave the first-statement order of Go, Rust and Lisp unpinned (`startOrderStrict` expects Python to be strict; nothing here measured it, and no rate is claimed for it); the cure that made the invocation order hold, merged on the batch as `3fe84706cc`; Rust `extensions/sdk-rs/src/request_start_order.rs`; Lisp `extensions/sdk-lisp/src/dispatch.lisp`. The Go rate: about 5e-5 per start under one-cpu pressure and 0 in 600 unpressured runs (measured 2026-11-18). A lane (`PySdkStartOrder`) measures Python under one-cpu pressure on 2026-11-18; this record is updated with its rate when it reports.

Parity allowance: no parity scenario observes it: a scenario's extension handlers are written to read in order, and the window is a scheduler race of microseconds that no scenario can pin; the conformance helpers above say which realizations are held to the strict first-statement order.
