## D624 An opt-in screen writer sends the terminal only what changes the screen in fullscreen mode, where Pi sends every row a frame writes

What: in fullscreen mode Pi's renderer writes a frame as one synchronized update that holds, for every row it writes, the cursor address, an erase of the line (`CSI 2K`) and the row's line (`doRender` in `packages/tui/src/tui-alt-screen.ts`). PiG's renderers build the same frames, and with nothing selected the terminal is sent them as they are written, as Pi's terminal is: the screen writer is opt-in in 0.8.0 ("Selecting the writer" below). When it is selected, a `screenwriter.Writer` (`internal/screenwriter`) under `tui.ProcessTerminal.write` reads every write, keeps what the writes leave on the alternate screen (rows of cells, the pen, the cursor, the scroll region) and, for a frame it can read completely, sends the terminal other bytes than the frame's:

- A row rewritten with the cells it already shows is not written.
- A row whose cells change is written in place, from its first cell through its last changed one, as the first bytes of the frame's own line, only when the frame's line is no narrower than the row, has a cell that is not a blank under the default pen exactly where the row has one (same column, same width; a cluster of uncertain width must be the same cluster there), and has others only after the last of them; a line that has others is written through its last cell. For such a row the erase is not sent, and the bytes after the last written cell are not sent: the line's closing reset and hyperlink close, and, when the row neither grew nor got wider, the unchanged cells after the last changed one. A row as wide as the screen of which that would send every cell is not written in place but whole (the next item): the writer prints in the screen's last column only as the frame does.
- Every other changed row is written whole, as the frame wrote it: the line erased, then the row. A line with a hyperlink open, a cluster of several code points, a control character or a sequence other than SGR is not read: that row is sent as the frame wrote it.
- A frame that changes no cell, cursor position or cursor visibility is not written.
- Once 250 ms pass without a frame, every row that a frame rewrote and the writer did not write whole is written whole, as the frame wrote it, in one synchronized update that leaves the cursor where it is (the settle write). Pi makes no such write. A row the writer wrote whole is made whole by that write and waits for no settle write; the rows written in part, and the rows a frame rewrote without a change, are made whole by the settle write.

The writer makes no sequence of its own but the cursor address of a row's first column and a reset of the pen (`CSI 0 m`).

Conditions: frames are translated only while the alternate screen is shown and autowrap is known to be off: a write turned it off (`CSI ? 7 l`) and none since turned it on (`CSI ? 7 h`), switched to or from an alternate screen (modes 47, 1047, 1049), restored saved private modes (`CSI ? .. r`) or reset the terminal (DECSTR, RIS). While it is not known to be off every frame is sent as it came and the rows are forgotten; the first frame after it is turned off again writes its rows whole. Fullscreen mode, the default `tuiMode`, enters the alternate screen and turns autowrap off in one write. Regular mode never enters the alternate screen: every byte is sent as it came (a recorded run of 1,353 writes, 230,518 bytes, is the test data of `TestRegularModeIsSentAsItCame`). Before the alternate screen is entered and after it is left every byte is sent as it came. Print, JSON and RPC mode and `pig --version` build no screen writer, whatever the environment and the setting say (`TestNoScreenWriterOutsideInteractiveMode`, on the binary). `PI_TUI_WRITE_LOG` is above the writer and records the renderers' bytes.

What a user or a terminal can observe: nothing unless the writer is selected. With it selected, the bytes PiG sends while the alternate screen is shown, how many frames carry them, and one write Pi does not make. A program that reads PiG's raw output (`script`, `tmux pipe-pane`, a terminal's own log) reads other bytes than Pi's for the same frames: fewer, no frame where nothing changed, rows written from their first cell without an erase, and the settle write 250 ms after the last frame. Replay of the repository's recorded streams at 160 by 48, settle writes included (a replay, not a benchmark): the `md:20000` stream 485,204 of 543,833 bytes (89.2 %), the `write:50` stream 140,764 of 710,981 bytes (19.8 %). Where every frame is followed by a pause of 250 ms the settle write follows every frame: in a replay of two recorded sessions of twenty keys typed 400 and 255 ms apart (the writer's record log of each, settle writes where the log has them) the writer sends 15,463 of 16,271 and 15,572 of 16,509 bytes (95.0 % and 94.3 %), 213 bytes for a key whose frame has 219: the editor's row is as wide as the screen and changes through its last cell, so it is written whole and no settle write follows it. Recording runs at a9e540a32 on the lane's host (not benchmark rows): `write:200` 201,032 of 731,106 bytes (27.5 %), `write:400` 344,914 of 1,361,994 bytes (25.3 %).

What the terminal keeps of a line: tmux keeps, for a line, the cells it has (`capture-pane -N` prints them, and `capture-pane -e` ends the row's pen there) and how far cells were stored in it (`capture-pane -J` prints them); with autowrap off both depend on the order in which the cells arrived since the line was last erased whole, not only on what the row shows. The in-place rule is the one under which tmux keeps the lines the frame's own bytes leave it. Measured on tmux 3.4 (the Linux container the tests run in) and tmux 3.6 (host xd670): 51 cases, 1,794 rows each, identical on the two versions and recorded in `internal/screenwriter/gridterm/testdata/tmux-3.4.json` and `tmux-3.6.json`; `TestLinesAreWhatTmuxShows` asks the tmux of the machine it runs on and fails on a tmux whose lines differ. With autowrap on tmux stores runs of text as it reads them: not modelled, and the writer translates nothing then. A cluster whose width terminals disagree on keeps its place for a row to be written in place; this is shown on the tests' width models, not on a terminal. Terminals other than tmux: what was run with this rule is under the owner's condition (b) below.

Selecting the writer: the writer is opt-in in 0.8.0. The global setting `terminal.screenWriter` selects it with `"writer"`; `"pi"` is the renderers' bytes; the key left out, and any other value, mean the default, which one constant names (`TerminalScreenWriterDefault` in `internal/codingagent/settings.go`, now `"pi"`: with nothing selected the terminal is sent the bytes Pi sends). `PIG_TUI_SCREEN_WRITER`, when set and not empty, decides in the setting's place: `pi` (or `0`) sends the terminal the renderers' bytes as they are written; any other value selects the writer. The writer becomes the default when the owner's real-terminal condition is shown: Kitty, Ghostty and iTerm2 on his Mac, which only he can run (condition (b) below). A project settings file cannot set the key. The setting is read once, when interactive mode starts, before the alternate screen is entered; a change of the setting, `/reload` and a change applied in `/settings` take effect at the next start. `PIG_TUI_SCREEN_WRITER_LOG=path` records, with the writer on, every write as it came and as it was sent: it writes the screen's bytes, typed text included, to the file the user names.

Why: through tmux or ssh the bytes of a frame are what the terminal and the multiplexer read and parse, a row's unchanged cells included; the writer sends between a fifth and nine tenths of them on the streams above.

What the writer costs PiG, and what was cut: the writer reads every frame. For a row a frame writes it finds where the line ends, compares the line with the one the row keeps, reads what changed into cells and compares cells. Replay of the two recorded streams through the writer alone (`BenchmarkTranslate`, 160 by 48, median of 6 runs beside other jobs, 0 allocations a replay before and after): the `write:50` stream (3,262 frames, 1,499 rows written) 2.58 ms before the changes of a6e5efaad and 1.22 ms after, the `md:20000` stream (846 frames, 2,222 rows) 2.38 and 1.60 ms; a recorded session of the benchmark's write cell (559 frames, 1,598 rows) 1.65 and 1.10 ms, of its tmux cell 4.98 and 2.96 ms, of typed keys (37 frames) 95 and 63 microseconds. The changes send the same bytes: the SHA-256 of everything the writer sends for the two streams and the three sessions, settle writes included, is the same before and after, and the corpus of 292 recorded sessions (584 stream pairs) is the same file for file. They are: (1) `writeDiff` compares only the cells `parse` did not take over from the row's line: in a row of as many cells, the last cells `parse` kept are the cells of the same index; (2) a line's cells through the last one that is not a blank under the default pen are counted while the line is read; (3) a row that is written whole whatever its cells are keeps its line unread, and its cells are read when a later frame's write of the row depends on them, never for a row that is scrolled away, erased or forgotten first: a row of a frame that is sent as it came, a row no cursor address follows, a row that is not known, and a row without a cell written with a line of as many printable ASCII bytes as the screen has columns (read, such a line has that many columns and the row is written whole; not read, it is written as the frame wrote it: the same bytes); the line ends with a reset, so the pen after it is the default one, read or not; (4) `commonSuffix` compares sixty-four bytes at a time first. Where the replay's time went (CPU profile of the `write:50` stream): before, `writeDiff` 52 %, `parse` 23 %, finding the line's end 10 %; after (1) and (2), `parse` 33 %, the line's end 23 %, `writeDiff` 15 %. In the recorded session of the write cell 799 of 1,598 rows are written onto a row without a cell, which is what (3) spares. A rule that sends a whole frame as it came when most of its rows changed was measured and not built: the renderers write no row that shows its line already (2,222 of 2,222 rows written in the `md:20000` stream differ from the row's line, 1,499 of 1,499 in `write:50`, 105 of 105 in a session of typed keys, where a key's frame writes one row), so the share of changed rows is the same for a typed key and for a streamed answer. Pi bug: none. Pi has no layer under the terminal's write; its bytes are correct, only more.
