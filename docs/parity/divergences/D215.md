## D215 A local Package typed by absolute path is stored as typed, and one that does not exist warns at startup

What: Pi's `pi install <path>` records every local Package in `packages[]` relative to the settings directory as it was spelled at install (`package-manager.ts` `normalizePackageSourceForSettings`). An install made through one spelling of the agent directory (a symlinked `PIG_HOME`, such as an XDG link) writes, for example, `../../../../../../pkgsrc/my-pkg`; a start through another spelling at another depth resolves it to a path that does not exist, and the Package's tools are gone. PiG stores a path typed absolute (`/abs/pkg`, `~/pkg`, a `file://` URL) as typed, trimmed; a path typed relative (`./pkg`, `../pkg`) is still stored relative to the settings directory, as Pi stores it. Pi also skips a configured local Package whose directory does not exist without a word; PiG reports it as a startup warning, `Extension package "<source>": failed to install (Path does not exist: <resolved path>). Run "pig remove <source>" to remove it from settings.json.`, the warning Pi gives an npm or git Package that fails to install, and leaves it out of the `[pig] Could not install` line, whose advice (`run pig update when online`) does not apply to a path.

Why: 20 of 21 Packages on one host disappeared after a re-registration run through a symlinked `PIG_HOME`, with only a boot line on stderr to show it (#389). An absolute path resolves the same way from every spelling of the agent directory, and a missing Package is now visible in the session.

Pi bug: Pi writes the same relative record (`package-manager.ts` `normalizePackageSourceForSettings` at the pin, b3a29f11); not reported upstream.

Scope: `PackageManager.NormalizeSourceForSettings` (`pig install`, `pig remove` matching is unchanged: both forms resolve to the same path), through `resolvepath.IsAbsolutePackagePath`; the startup of the CLI (`coding/cli/cli_runtime_build.go`) for the warning. Entries already in `settings.json` are read as before; running `pig install <absolute path>` again rewrites an entry that still resolves to the absolute form. The SDK resource loader is unchanged.

Owner decision: approved by owner Michael Kinsy on 2026-10-30 (store an absolute path as typed rather than always absolute or symlink-resolved relative; warn about a missing local Package in the session, "whichever is optimal UX").

Call-site markers: `internal/packagemanager/package_manager.go` (`NormalizeSourceForSettings`), `coding/cli/cli_runtime_build.go` (the startup Package check).

Evidence: `TestInstalledAbsoluteLocalPackageResolvesThroughAnotherAgentDirSpelling` and `TestStartupWarnsAboutAConfiguredLocalPackageThatDoesNotExist` (`coding/cli/package_local_path_test.go`, both red with the two call sites reverted), `TestNormalizePackageSourceForSettings_UsesScopeBase` (`coding/cli/package_commands_test.go`), `TestPackageManagerAddAndRemoveSourceInTheScopeSettings` (`internal/packagemanager/package_manager_ops_gaps_test.go`: an absolute spelling of a relative entry replaces it with the absolute path).

Parity allowance: the ported case `package-command-paths.test.ts:431` ("allows local package install to initialize fresh project settings", `TestPortWave10PackageCommandPaths`) installs an absolute path and expects the entry relative to `.pi`; PiG's port asserts the path as typed. Scenario `cli-utils/04-package-install-local` installs a relative path, which is stored as Pi stores it, and no paired scenario starts with a configured local Package that does not exist.

Remove when: Pi stores an absolute local path as typed and warns about a missing local Package, or the owner reverses the decision. Then the two branches, the call-site markers and the tests' D215 cases go.
