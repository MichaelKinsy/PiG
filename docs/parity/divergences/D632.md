## D632 Resource loader operations that overlap wait for each other, where Pi's reloads interleave and can mix their results

What: Pi's `DefaultResourceLoader.reload()` (`packages/coding-agent/src/core/resource-loader.ts:541-710`) has no lock. A reload suspended at one of its awaits (the extension load, `:618`) lets a later `reload()` run to its end, and when the first resumes it assigns what it resolved before the await next to what it reads after it: the skill, prompt template and theme paths resolved before the extension load (`:585-590`, assigned at `:635`, `:650`, `:669`) and the context files and system prompt read after it (`:678-705`). A loader whose first reload finishes last therefore ends with the first reload's skills and the second reload's system prompt. PiG's `ReloadWith`, `LoadProjectTrustExtensions`, `ExtendResources` and `Close` take one operation lock (`opMu`): operations that overlap from outside wait for each other, each is whole, and the loader ends in the state of the operation that started last.

A call made from inside an operation runs inside it, as Pi's runs at once: a call on the operation's goroutine (an override function or any other callback that gets no context) and a call that carries the context the operation handed to its project-trust callback or extension load. That context marks the operation only while it runs; used after it, the call is one from outside and waits.

Why: Pi's interleaving is safe in one thread, where a reload gives up control only at an await. PiG's reloads run on goroutines, so two of them inside the loader at once would read and write its fields in parallel; the lock that prevents that also removes the mixed final state, which no caller can want.

Pi bug: not reported. Pi's mixed state after overlapping reloads looks unintended, but no upstream issue records it. A draft for the owner to file is in `docs/parity/gap-closure/ledger-coding-agent-pi-issue-drafts.md` (D632).

Scope: `coding` (`DefaultResourceLoader.ReloadWith`, `LoadProjectTrustExtensions`, `ExtendResources`, `Close`).

Limit: the lock does not cover a goroutine that a callback starts with its context and does not wait for. While the operation that handed out the context runs, a loader call that goroutine makes with it counts as made from inside the operation and runs beside the rest of it, without the lock. A callback that hands its context to another goroutine must wait for that goroutine before it returns, as a Pi callback awaits the reload it starts. Once the operation has ended the context marks nothing, and the call waits like any call from outside.

Remove when: Pi serialises `reload()` or orders its fields, so that overlapping reloads end in the state of one of them.

Call-site markers: `coding/resource_loader.go` (`takeOperation`).

Evidence: `coding/resource_loader_reentry_async_test.go` (`TestPiOverlappingReloadsMixTheirResultsD632` records Pi's mixed state through the oracle and fails when Pi stops mixing; `TestDefaultResourceLoaderOverrideMayCallTheLoader`, `TestDefaultResourceLoaderCallbackMayExtendAndClose`, `TestDefaultResourceLoaderCallbackMayReloadWithItsContextOnAnotherGoroutine`, `TestDefaultResourceLoaderContextOfAnEndedReloadDoesNotBypassTheOperationLock`) and `coding/resource_loader_overlap_async_modelsb_test.go` (`TestDefaultResourceLoaderOverlappingReloadsEndInTheLastInputsState`, `TestDefaultResourceLoaderManyOverlappingReloadsEndInTheSameState`, `TestDefaultResourceLoaderCallbackMayReloadWithItsContext`). Before the calls from inside an operation were let through, every one of them waited for the lock its own operation held: `TestDefaultResourceLoaderCallbackMayReloadWithItsContext` fails in its three cases without that, each at its 5 second bound.

Parity allowance: after reloads that overlap with different inputs PiG's loader holds the last reload's skills, prompt templates, themes, context files and system prompt, where Pi's can hold the earlier reload's paths next to the later one's prompt; with unchanged inputs both end in the same state.
