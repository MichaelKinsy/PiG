## D186 A hung-up terminal: PiG gives extensions `session_shutdown` for at most a second and exits 129; Pi's exit code and event depend on its event loop and on which event arrives first

What: when the terminal's master closes under an interactive session, the kernel sends SIGHUP and ends the session's input. Pi's SIGHUP handler (`registerSignalHandlers`, `packages/coding-agent/src/modes/interactive/interactive-mode.ts:4402-4417`) runs a graceful shutdown whose terminal writes meet EIO and take `emergencyTerminalExit` (exit 129, `:4346-4352`). Node's signal watcher does not keep the event loop alive. A session with no other referenced handle (a plain directory, no extension timers or sockets, no git watcher) has an empty loop when its input ends, and Pi exits 0 before the handler runs unless a write is still pending. Measured on Pi 1402973a, idle plain-directory hangups taken after the status render settled: 16 of 20 exited 0 and 4 exited 129. In a git repository, whose footer watches `.git/HEAD` (`footer-data-provider.ts:316`), 20 of 20 exited 129. PiG always exits 129 (`exitIfDeadTerminal`) and writes the `exit.log` line `terminal gone: <error> (exit 129)` (D102). Extensions: when Pi's SIGHUP handler runs it awaits `runtimeHost.dispose()`, which settles the interrupted run and emits `session_shutdown` with the reason `quit`, before any terminal write and without a limit (`interactive-mode.ts:4475-4496`, `agent-session-runtime.ts:415-424`, Pi 1.5.2 and main 275dde41); a write to the dead terminal during that await takes `emergencyTerminalExit` and cuts the handlers; with an empty loop Pi exits 0 with no event. PiG usually reads the end of input on the hung-up terminal before the signal (95 of 96 measured runs; in the other the SIGHUP came first) and takes one path either way: the interrupted run settles, `session_shutdown` with the reason `quit` reaches every extension once, the exit waits for the handlers for at most one second (the wait of a SIGINT, D51), then kills the extension processes and exits 129. Measured with an extension whose handler appends a line, awaits a timer and appends again, after one turn (Pi 1.5.2 and this change, 4 runs per cell; tmux kill-session, tmux kill-pane, a closed pty master as session leader and under a shell):

| Session | Pi 1.5.2 | PiG |
|---|---|---|
| idle, git repository, 200 ms handler | handler ran and its awaited line landed 16 of 16, exit 129 after 210-258 ms | handler ran and its awaited line landed 16 of 16, exit 129 after 208-244 ms |
| idle, git repository, 3 s handler | awaited in full 8 of 8, exit 129 after 3.01-3.06 s | handler started 8 of 8 and was cut at the bound 8 of 8, exit 129 after 1.01-1.04 s |
| a turn in flight, git repository, 3 s handler | handler started 8 of 8 and was cut by the next terminal write 8 of 8, awaited line never written, exit 129 after 23-28 ms | handler started 8 of 8 and ran until the bound, exit 129 after 1.00-1.02 s; with a 200 ms handler its awaited line landed 4 of 4, exit 129 after 209-213 ms |
| idle, plain directory, 200 ms handler | no event 20 of 20, exit 0 after 11-61 ms | handler ran and its awaited line landed 4 of 4, exit 129 after 210-212 ms |
| idle, plain directory, the extension holds a timer, 200 ms handler | handler ran and its awaited line landed 16 of 16, exit 129 after 211-220 ms | as the plain-directory row |
| idle, git repository, under a shell that ignores SIGHUP | no event, still running after 120 s | handler ran and its awaited line landed 4 of 4, exit 129 after 238-247 ms |

The case of filing #25 of the copiglet request (tmux kill-session; the pane's non-interactive bash runs the binary as its foreground child; a plain directory; idle after a turn) is the empty-loop row, which is why its author saw no event from Pi: in that launch Pi 1.5.2 gave no event and exit 0 in 16 of 16 (15-49 ms), and with a git repository or with an extension that holds a timer it gave the event, awaited, and exit 129 in 16 of 16 each (211-220 ms); PiG gave the event, awaited, and exit 129 in 16 of 16 in each (206-219 ms, an extension in a Node process and one fused into a Piglet Binary).

So a handler slower than one second is cut where an idle Pi waits for it; a handler of a working session finishes inside the second where Pi cuts it at once; the event is emitted where Pi's empty loop emits none; and under a shell that ignores SIGHUP, where no signal reaches Pi and it stays alive until something writes to the terminal, PiG exits 129.

Why: Pi's 0 is a timing outcome of an empty Node event loop, not a decision, and it contradicts the purpose of `emergencyTerminalExit`. PiG has no such loop whose emptiness it could reproduce. Exiting 0 on a dead terminal would leave no `exit.log` trace, which D102 forbids. This follows the owner ruling (D146) that a confirmed Pi bug is fixed whether or not Pi has it. A process whose terminal is gone cannot be seen or stopped by its user, so no handler may hold it: the one-second bound. Which of the hangup's signs PiG sees first (the end of input, a failed read, a failed write, the signal) varies from run to run, and an extension's last write must not depend on it: the event is always emitted.

Scope: a terminal that went away under an interactive session (the end of input on a hung-up output terminal, a dead-terminal error from a read or an ioctl, a failed terminal write). A live SIGHUP or SIGTERM (handlers awaited without a limit, exit 0) matches Pi and is unchanged. An idle session that holds a handle (a git repository, extension timers) matches Pi in exit code and event when a SIGHUP reaches Pi (Pi leads the session, or its shell forwards the hangup or dies of it) and its handlers finish inside the second. It differs from Pi in the empty-loop case and in the three cases above: a handler slower than a second, a working session, and a shell that ignores SIGHUP (Pi stays alive, PiG exits 129).

Owner decision: approved by owner Michael Kinsy on 2026-10-20 (the exit code of a session that no user action ended is 129 and leaves a trace, rather than a code that depends on Node's event-loop state). The `session_shutdown` emission, its one-second bound and the corrected scope were approved by the owner on 2026-11-13 ("Proceed"): the dead-terminal exit emits `session_shutdown`, waits at most the shared 1 s, and exits 129.

Call-site markers: `internal/codingagent/interactive_input.go` (`exitIfDeadTerminal`, `emergencyTerminalExit`).

Evidence: `36-terminal-disconnect-idle-repo` (a git repository: 129 on both sides), `10-terminal-disconnect-exit` (a working session in a plain directory: 129 on both sides) and `TestHungUpTerminalEOFExits129`. The idle plain-directory outcome is not compared, because Pi's own result varies between runs. For the event: `38-terminal-disconnect-shutdown-event` compares the idle git-repository row only (both sides: the handler's reason `quit`, its awaited line, exit 129); the other rows are held on PiG's side by `TestDeadTerminalEmitsSessionShutdownToExtensions` (tmux kill-session under a real pig, idle and with a turn in flight, 20 runs per setup, Pi's measured table in its comment) and `TestDeadTerminalExitGivesExtensionsTheirShutdownFirst` (once, bounded, an emission a SIGHUP started is joined inside the bound, a handler's failed terminal write does not start a second exit).

Parity allowance: none.

Remove when: Pi exits 129 for a hung-up terminal regardless of event-loop state.
