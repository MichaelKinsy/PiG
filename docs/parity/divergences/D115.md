## D115 Gemini 2.x tool-result images follow the whole run of function responses

What: for a Google (Generative AI and Vertex) model without multimodal function responses (a `gemini-*` or `gemini-live-*` id with a major version below 3; `google-shared.ts:180-186` `supportsMultimodalFunctionResponse` returns true for every other id, so Gemini 3 and non-Gemini ids nest the images in the function response), PiG sends the "Tool result image:" turns of a run of tool results after the last function response of the run, in result order, so every function response of one model turn stays in the single user turn after it. Pi 1.3.0 pushes each image turn right after its result (`packages/ai/src/api/google-shared.ts` `convertMessages`, the `toolResult` branch: "For Gemini < 3, add images in a separate user message"), so the next result starts a new turn. Pi's own test asserts that shape (`packages/ai/test/google-shared-image-tool-result-routing.test.ts:80-88`: contents[2] function responses, [3] image turn, [4] a function response). Pi main (earendil-works/pi, 2026-10-10) is unchanged.

Pi bug: with a Gemini model below version 3, a parallel tool batch whose results carry an image in any result but the last splits the function responses of one model turn across user turns, and Gemini rejects every later turn of the session with HTTP 400 (`google-shared.ts` `convertMessages`, the `toolResult` branch).

Why: Gemini answers the function calls of one model turn only when the user turn directly after it holds a function response for every call ("Please ensure that the number of function response parts is equal to the number of function call parts of the function call turn", Google function-calling documentation; the same file's comment: "Cloud Code Assist API requires all function responses to be in a single user turn"). A parallel tool batch with an image in any result but the last gets HTTP 400 on every later turn of the session. A single call, and a run whose images all belong to the last result, produce Pi's request byte for byte.

Scope: `geminiConvertMessages` in `ai/google.go`, used by `google-generative-ai` and `google-vertex`. Gemini 3 models, which nest images in the function response, are unchanged.

Owner decision: 2026-10-10, owner rule "fix every confirmed bug now, Pi's included", relayed by the lead; number assigned by the lead.

Call-site markers: `ai/google.go` (`flushImageTurns`, `geminiConvertMessages`).

Evidence: `TestGoogleImageToolResultsKeepFunctionResponsesInOneTurnD115` and `TestGoogleImageToolResultOfASingleCallMatchesPiD115` (`ai/google_image_tool_results_d115_test.go`), `TestGeminiToolResultImageOrderingMatchesUpstream`, the payload oracles `TestGoogleGenerativeAIPayloadMatchesPi` and `TestGoogleVertexPayloadMatchesPi` (Pi's payload rewritten by `piPayloadWithD115`), and the differential fuzz `TestPipelineMatchesPi` / `TestAIPipelineMatchesPi` (`test/pipeline-diff`, Pi's request rewritten by `withD115`, PiG's request checked against the Google contract without an allowance).

Parity allowance: the paired scenarios send no Gemini 2.x image tool results.

Remove when: Pi keeps the function responses of one model turn in one user turn (Pi's routing test changes), at which point delete the deferral and the two rewrites.
