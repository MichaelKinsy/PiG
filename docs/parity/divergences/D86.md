## D86 RPC settle tail and command admission: a handler of a runtime that cannot report its wait is taken to wait once it outlives a quantum

What: in RPC mode Pi emits `agent_settled` in the microtasks that follow a published `agent_end`, so its stdin reader, which runs between macrotasks, reads no line between them (`agent-session.ts:1143-1165` `_emitAgentSettled`, called from the run's `finally` at `:1995-2001`; `rpc-mode.ts:792-798,824`). When an `agent_before_settle` or `agent_settled` handler, or an extension command, awaits a timer, I/O or another real wait, Pi reads stdin while it waits (`rpc-mode.ts:792-798,824`: `activeCommands++`, the `finally` that decrements it, and `void handleInputLine(line)` start every line without waiting for the one before). PiG reads stdin on its own goroutine, so `rpcSettleGate` holds each stdin batch, and stdin's end, from a published `agent_end` until `agent_settled` is written, and `rpcAwaitHandler` admits the next line only once a command, an input handler or a before_agent_start handler suspended or finished. The gate is open during a compaction, an auto-retry delay, a new run, an extension dialog and a settle-tail handler that waits. A Node runtime reports the end of its event-loop window for a command, an input handler, a before_agent_start handler and the settle tail: a window that closes with the handler unanswered is the handler awaiting a timer, I/O or another real wait, and is reported as blocked, which releases `rpcAwaitHandler`; a handler that only runs microtasks never closes its window unanswered, so it holds stdin as in Pi. The host sees a Node handler's waits exactly. A Go, Rust, Python or Lisp handler blocks in the language's own call (`net/http`, a socket read, a sleep), which nothing but the language tells from computing, so the host takes such a handler to be waiting once it has run for `subprocess.HandlerWaitQuantum` (250 ms) without answering: it acknowledges the invocation as suspended, which admits the next stdin line, and counts a settle-tail handler as waiting, which opens the gate. A handler that answers within the quantum is Pi's microtask-only continuation and holds stdin as before. After stdin's end, a running handler of such a runtime counts as waiting at once, so shutdown does not wait for it.

Why: the host learns of a wait only from a runtime's report, and those runtimes have no equivalent of the Node window that closes unresponded. Without a bound, a Go handler that awaits the network (the LangSmith extension's `agent_settled` PATCH with `LANGSMITH_TRACING_BACKGROUND=false`) left every later stdin line unanswered for as long as the wait lasted, where the same handler in Node answers `get_state` during it. Without the gate, a command sent on seeing `agent_end` would be answered before `agent_settled`, which Pi never does for a handler that does not wait.

Rejected options (each surveyed against the failing case, a plain `net/http` or socket wait in an `agent_settled` handler or command):
- Waits reported only where an SDK mediates them (the `blocked` report of a host call, as the Node runtime reports `WINDOW_CLOSING_CALLS`): exact for `ctx.exec`, dialogs and model calls, blind to the stdlib I/O that caused the report; the ported LangSmith client dials with a plain `*http.Transport`.
- Instrumenting the language's I/O (`httptrace` on the handler's context, wrapping `http.DefaultTransport`, patching `socket`): covers one client of one language; a custom transport, a raw socket, a sleep or a file read escapes it, and Rust and Lisp have no equivalent hook.
- Reading the language scheduler (Go `runtime/metrics` goroutine states, an `asyncio` idle loop): the Go counters are documented as approximate and process-wide (a fused extension shares the host's goroutines), Rust and Lisp expose nothing, and every reading needs a sampling interval anyway.
- Polling the extension process's thread states (`/proc/<pid>/task`, `libproc`): platform-specific, still needs an interval, and impossible for a fused extension, which shares the host process.
- Dropping the gate for these runtimes: removes the deterministic order for a handler that does not wait, because the host handles a command as soon as it is read while the handler runs.
- A longer bound (the 2 s heartbeat interval): the same behavior with a client stall of seconds.

Value of the quantum: a no-op `agent_settled` handler's request to response took 0.2 to 0.8 ms at the median, at most 3.1 ms at the 99th percentile and at most 8.7 ms at the maximum in 150 runs per SDK (Go, Rust, Python, Lisp, Node; xd670, idle and with twice as many busy loops as CPUs). 250 ms is about 29 times the slowest run, and bounds the delay a waiting handler adds to the first line it holds back. `TestRPCSettleHandlerLatencyProbe` in `coding/cli/rpc_settle_latency_probe_test.go` repeats the measurement (`PIG_PROBE_SETTLE_LATENCY=1`).

Value of the quantum for the two events Pi emits with `void emit` (`session_info_changed`, `thinking_level_select`; RPC `set_session_name`, `set_thinking_level`): the reply of the command waits for the first handler's first suspension (`Session.dispatchUnawaitedEvent`), so the quantum is the longest a reply is held by a Go, Rust, Python or Lisp handler that waits or never returns (Pi replies in under 1 ms); the same 250 ms is kept, one constant for every use of the record. Measured at 25, 50, 100, 250 and 1000 ms (50 calls per cell, xd6702 container): a waiting handler holds the reply for the quantum plus 1 ms at the median and at the 95th percentile in every SDK; a handler that computes for 50 ms keeps Pi's order (its notification first) only at a quantum above 50 ms; a handler that computes for 700 ms writes its notification after the reply at every quantum below 700 ms. `TestRPCUnawaitedEventLatencyProbe` in `coding/cli/rpc_unawaited_event_test.go` repeats the measurement (`PIG_PROBE_NAME_LATENCY=1`).

Observable effect for those two events: in the Go, Rust, Python or Lisp SDK, `set_session_name` and `set_thinking_level` reply up to 250 ms after the request while an extension handler of the event waits or never returns, where Pi replies at once. A handler whose wait ends at once writes its notification before the reply, where Pi writes it after; a handler that computes for more than 250 ms without awaiting writes its notification after the reply, where Pi, whose caller the computation blocks, writes it first. The handler's effect is neither lost nor dropped: it arrives, late or reordered. Node handlers report the end of their synchronous part and are as in Pi.

Observable effect: in the Go, Rust, Python or Lisp SDK, a command sent during the first 250 ms of an `agent_before_settle` or `agent_settled` handler that waits on a timer or I/O is answered after `agent_settled` instead of before it, and a stdin line sent during the first 250 ms of a command, input or before_agent_start handler that waits is answered after that handler instead of before it; later in the wait both match Pi. A handler that computes for more than 250 ms without waiting is taken to wait, so a command sent meanwhile is answered during it, where Pi, whose loop the computation blocks, answers it afterwards. Output order for every other case, including every Node handler (command, input, before_agent_start and settle tail: a line sent during its wait is answered during it, at once), is as in Pi. The quantum does not apply to Node runtimes, which report their waits.

Scope: only a settle-tail handler, command, input or before_agent_start handler of a runtime that reports no window, and only a command or stdin end sent while it runs; and the first handler of a `session_info_changed` or `thinking_level_select` event of such a runtime, and only for the reply of the command that emitted it. Outside that case the gate matches Pi and is not waived.
