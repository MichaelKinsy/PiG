## D165 The durable image processor is native Go, not Photon's WebAssembly

What: `images.CreatePhotonImages()` (`durable/images`, `images/node`, `images/cloudflare`) decodes with the Go image decoders (PNG, JPEG, GIF, WebP, BMP), resamples with `photonimage.ResizeLanczos3`, a Go port of the image crate 0.24.9 `imageops::resize` Lanczos3 that reproduces Photon's pixels byte for byte, encodes PNG with `photonimage.EncodePNG`, a Go port of the encoder Photon's `get_bytes()` runs (image 0.24.9 `PngEncoder` defaults: png 0.17.14 `Compression::Fast` with adaptive filtering over fdeflate 0.3.6), and encodes JPEG with Go's `image/jpeg`, dropping the alpha channel as Photon does. `internal/photonimage` is shared with the coding agent's image path (`internal/imageprocessing`). Pi's `createPhotonImages(wasm)` (`packages/durable/src/images/index.ts`) runs `@silvia-odwyer/photon` 0.3.3, Rust compiled to WebAssembly, for the same steps. Pi's pipeline is reproduced step for step: EXIF orientation (`exif.ts`), inline passthrough once the image decodes, `Math.round` target size, JPEG qualities 80, 70, 55, 40 (JPEG first for JPEG sources), 3/4 shrink until the base64 fits, BMP to PNG. The JPEG bytes and the resampled pixels differ from Photon's: Go's JPEG encoder writes other bytes than the Rust `image` crate, and the Go Lanczos3 rounds differently from Photon's. Equal pixels encode to Photon's PNG bytes, so a PNG's size, which decides whether it fits the byte limit or the next encoding is tried, is Photon's. The `wasm` argument of `createPhotonImages` has no Go counterpart (the Go processor has no binary to load), and `createNodePhotonImages` and `createCloudflarePhotonImages` take none and read no file.

Why: Photon under wazero reproduces Pi byte for byte (measured: the same SHA-256 as Pi's Node Photon for a 12 MP photo), but it costs a 1.8 MiB embedded binary, about 0.9 s of JIT compile on first use (34 ms with a disk cache), 1.3 times Node's time per image, 229 MiB of WebAssembly memory for one 12 MP image that never shrinks, and it needs wazero's JIT compiler, which exists on amd64 and arm64 only: its interpreter takes 3.5 minutes for the same image. The native pipeline adds about 0.6 MB, runs a 12 MP photo in 1.7 s, and works on every platform Go builds for. `internal/imageprocessing`, the coding agent's image path, is native Go for the same reasons and uses the same `internal/photonimage` resize and PNG encoder. The owner chose the native pipeline on 2026-10-10 after these measurements (`questions/designout-port.md`).

Observable effect: for one input and set of limits, the image the model receives has Pi's dimensions, `resized` and `convertedFrom` records, and the same `Read image file [...]` notes. A PNG written from unresampled or resampled pixels has Photon's bytes (`TestResizeLanczos3MatchesPhoton`: 300 images and sizes, every byte; `TestEncodePNGWritesPhotonsBytes`). A JPEG differs: the two encoders quantize differently, so the pixels differ by a mean of 4.0 of 255 per channel at q80 and the bytes and sizes differ (149,789 bytes against Photon's 156,471 for a 1000x2000 gradient). The coding agent returns the smaller of the PNG and the JPEG candidate (Pi e7a0df27, `image-resize-core.ts`), so for a resize whose two candidates are close in size PiG can return the other format than Pi. Measured against Pi on seeded corpora: 0 of 600 realistic images differ (200 photos as JPEG, 200 screenshots and 200 icon sheets with transparency as PNG, 100 to 2,900 pixels a side, limits 2,000, 1,024 and 640: `TestResizeFormatChoiceMatchesPiOnRealisticImages`), 0 of 200 resize-strategy cases, and 1 of 400 process-image cases (case 59, a 62x106 image resized to 16x28: `TestProcessImageMatchesPi`). A model sees the same picture either way; a test that compares JPEG image bytes with Pi's does not pass.

Scope: `durable/images` (`images.go` `Prepare`, `encodeJPEG`), `internal/imageprocessing` (`images.go` `encodeJPEG`), and the JPEG choice they feed; `internal/photonimage` is Photon's own. `tools.CreateReadTool`, `tools.CreateCodingTools`, the limits, the notes and the error results follow Pi exactly.

Owner decision: 2026-10-10, option A: the native Go pipeline (lead ruling 18:16Z, LEAD-RULINGS-1520.md: D165 for it; the `wasm` parameter design-out accepted).

Rejected alternative, measured 2026-10-10 on a loaded linux/amd64 host with Pi's pinned Photon 0.3.3 `photon_rs_bg.wasm` run in-process by wazero v1.12.0 (a Go host for the 42 `wbg` imports; only `__wbindgen_throw` and the externref init are called) on a synthetic 12 MP (4000x3000) JPEG:

| | native Go (chosen) | Photon under wazero JIT | Pi's Photon under Node |
|---|---|---|---|
| output bytes | not Photon's | identical (same SHA-256) | reference |
| binary size added | about 0.6 MB (1.1 MB as wasip1) | 1.88 MB embedded (669 KB gzip) | n/a |
| cold cost | none | compile 0.94 s (34 ms with a 6.1 MB disk cache), first image 3.7 to 5.0 s | n/a |
| warm 12 MP prepare | 1.67 s | 3.03 s | 2.26 s |
| memory for one 12 MP image | transient | 229 MiB WebAssembly memory, never shrinks, plus 175 MiB Go heap | same WebAssembly memory |
| without wazero's JIT (not amd64 or arm64) | works | interpreter: 3 min 30 s | n/a |

Workers: neither option goes into the Durable core wasm that runs on Workers (Workers cannot run wazero's JIT or compile WebAssembly at run time), so a Workers host keeps Pi's own Photon in JavaScript. The measuring harness is not committed.

Call-site markers: `durable/images/images.go` (`Prepare`, `encodeJPEG`), `internal/imageprocessing/images.go` (`encodeJPEG`).

Locked by: `TestPreparedPixelsStayCloseToWhatPhotonProduces` (`durable/images/photon_differential_test.go`) against Photon 0.3.3 output committed in `durable/images/testdata/` (a regenerating Node script is in the test comment; JPEG mean error 3.97, limit 4.5); `TestResizeLanczos3MatchesPhoton` (`internal/photonimage/lanczos_oracle_test.go`, against Photon under Node); `TestEncodePNGWritesPhotonsBytes` (`internal/photonimage/png_test.go`: Photon's PNG bytes for the committed fixture, and Photon's lengths and SHA-256s for three inputs); the behavior tests in `durable/images/images_test.go` (orientation 1 to 8, shrink chain, JPEG-first order, BMP to PNG, extreme aspect ratio, give-up, undecodable bytes), `durable/tools/read_images_test.go` (notes and error results through `read`) and the Pi 1.4.0 `tools-images.test.ts` port (`durable/images/node/tools_images_test.go`, including the noisy PNG that Photon's size sends to JPEG).

Parity allowance: none. No paired scenario reads an image through `createCodingTools({ images })`.

Remove when: the owner moves the processor to Photon under wazero (it then matches Pi's bytes), a Go port of the image crate's JPEG encoder writes Photon's bytes (then the format choice matches in every case), or Pi's pipeline stops being byte-defined by Photon.
