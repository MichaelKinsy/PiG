## D165 The durable image processor is native Go, not Photon's WebAssembly

What: `images.CreatePhotonImages()` (`durable/images`, `images/node`, `images/cloudflare`) decodes with the Go image decoders (PNG, JPEG, GIF, WebP, BMP), resamples with `photonimage.ResizeLanczos3`, a Go port of the image crate 0.24.9 `imageops::resize` Lanczos3 that reproduces Photon's pixels byte for byte, encodes PNG with `photonimage.EncodePNG`, a Go port of the encoder Photon's `get_bytes()` runs (image 0.24.9 `PngEncoder` defaults: png 0.17.14 `Compression::Fast` with adaptive filtering over fdeflate 0.3.6), and encodes JPEG with `photonimage.EncodeJPEG`, a Go port of the encoder Photon's `get_bytes_jpeg(quality)` runs (image 0.24.9 `JpegEncoder::new_with_quality`: the IJG integer forward DCT, the standard Huffman tables, the libjpeg quality scaling, the f32 colour conversion), dropping the alpha channel as Photon does. `internal/photonimage` is shared with the coding agent's image path (`internal/imageprocessing`). Pi's `createPhotonImages(wasm)` (`packages/durable/src/images/index.ts`) runs `@silvia-odwyer/photon` 0.3.3, Rust compiled to WebAssembly, for the same steps. Pi's pipeline is reproduced step for step: EXIF orientation (`exif.ts`), inline passthrough once the image decodes, `Math.round` target size, JPEG qualities 80, 70, 55, 40 (JPEG first for JPEG sources), 3/4 shrink until the base64 fits, BMP to PNG. The decoded pixels of a JPEG and of a WebP differ from Photon's, because Go's decoders for those two lossy formats are not the Rust `jpeg-decoder` 0.3.1 and the `image` 0.24.9 VP8 decoder. Every later step is Photon's own, byte for byte: an image that decodes to the same pixels (PNG, GIF, BMP, TIFF) is resampled and encoded to Photon's PNG and JPEG bytes, and what depends on their sizes (whether an encoding fits the byte limit, how far the quality ladder and the 3/4 shrink go, which of the PNG and the JPEG candidate of a resize is smaller) is Pi's. The `wasm` argument of `createPhotonImages` has no Go counterpart (the Go processor has no binary to load), and `createNodePhotonImages` and `createCloudflarePhotonImages` take none and read no file.

Why: Photon under wazero reproduces Pi byte for byte (measured: the same SHA-256 as Pi's Node Photon for a 12 MP photo), but it costs a 1.8 MiB embedded binary, about 0.9 s of JIT compile on first use (34 ms with a disk cache), 1.3 times Node's time per image, 229 MiB of WebAssembly memory for one 12 MP image that never shrinks, and it needs wazero's JIT compiler, which exists on amd64 and arm64 only: its interpreter takes 3.5 minutes for the same image. The native pipeline adds about 0.6 MB, runs a 12 MP photo in 1.7 s, and works on every platform Go builds for. `internal/imageprocessing`, the coding agent's image path, is native Go for the same reasons and uses the same `internal/photonimage` resize and PNG and JPEG encoders. The owner chose the native pipeline on 2026-10-10 after these measurements (`questions/designout-port.md`).

Observable effect: for one input and set of limits, the image the model receives has Pi's dimensions, `resized` and `convertedFrom` records, and the same `Read image file [...]` notes. When the input decodes to Photon's pixels the returned bytes are Photon's, PNG and JPEG alike: 0 of the 106 PNG, 56 GIF, 65 BMP and 89 unrecognized inputs of `TestProcessImageMatchesPi` differ from Pi in any byte (SHA-256 compared), 0 of the 200 cases of `TestResizeImageDimensionStrategyMatchesPi` (bytes compared; JPEG qualities 1, 40, 85 and 100 among them), and every JPEG of `TestEncodeJPEGWritesPhotonsBytes` is Photon's (835 encodings of 96 pictures: every quality from 1 to 100, sizes from 1x1 to 12 MP). A JPEG or a WebP input differs: the Go decoders give other pixels than Photon's (measured on the 73 of the 84 JPEG and WebP inputs of `TestProcessImageMatchesPi` that Go decodes: Photon's decoded pixels differ from Go's in every one), so the 44 that are re-encoded rather than returned as they are (26 of 47 JPEG, 18 of 37 WebP) differ from Pi's bytes and sizes, and at a byte limit between the two sizes the encoding or the number of 3/4 shrinks can differ too. Their format, dimensions, records and notes are Pi's in every measured case (`TestResizeFormatChoiceMatchesPiOnRealisticImages`: 0 of 72 realistic images differ, 24 photos as JPEG among them). The coding agent returns the smaller of the PNG and the JPEG candidate (Pi e7a0df27, `image-resize-core.ts`); the candidates' sizes are Photon's, so that choice differs from Pi's only for an input whose decoded pixels differ. A model sees the same picture either way; a test that compares re-encoded JPEG or WebP input bytes with Pi's does not pass.

Scope: `durable/images` (`images.go` `Prepare`) and `internal/imageprocessing` (`bmp_bitfields.go` `DecodeImage`), which decode with Go's decoders, and the JPEG and WebP inputs they feed; `internal/photonimage` is Photon's own. `tools.CreateReadTool`, `tools.CreateCodingTools`, the limits, the notes and the error results follow Pi exactly.

Owner decision: 2026-10-10, option A: the native Go pipeline (lead ruling 18:16Z, LEAD-RULINGS-1520.md: D165 for it; the `wasm` parameter design-out accepted).

Rejected alternative, measured 2026-10-10 on a loaded linux/amd64 host with Pi's pinned Photon 0.3.3 `photon_rs_bg.wasm` run in-process by wazero v1.12.0 (a Go host for the 42 `wbg` imports; only `__wbindgen_throw` and the externref init are called) on a synthetic 12 MP (4000x3000) JPEG:

| | native Go (chosen) | Photon under wazero JIT | Pi's Photon under Node |
|---|---|---|---|
| output bytes | not Photon's | identical (same SHA-256) | reference |
| binary size added | about 0.6 MB (1.1 MB as wasip1) | 1.88 MB embedded (669 KB gzip) | n/a |
| cold cost | none | compile 0.94 s (34 ms with a 6.1 MB disk cache), first image 3.7 to 5.0 s | n/a |
| warm 12 MP prepare | 1.67 s | 3.03 s | 2.26 s |
| memory for one 12 MP image | transient | 229 MiB WebAssembly memory, never shrinks, plus 175 MiB Go heap | same WebAssembly memory |
| without wazero's JIT (not amd64 or arm64) | works | interpreter: 3 min 30 s | n/a |

Workers: neither option goes into the Durable core wasm that runs on Workers (Workers cannot run wazero's JIT or compile WebAssembly at run time), so a Workers host keeps Pi's own Photon in JavaScript. The measuring harness is not committed.

Call-site markers: `durable/images/images.go` (`Prepare`), `internal/imageprocessing/bmp_bitfields.go` (`DecodeImage`).

Locked by: `TestPreparedImagesAreWhatPhotonProduces` (`durable/images/photon_differential_test.go`: the PNG and the JPEG q80 that Photon 0.3.3 wrote, committed in `durable/images/testdata/` with the Node script in the test comment); `TestEncodeJPEGWritesPhotonsBytes` (`internal/photonimage/jpeg_oracle_test.go`: 835 JPEGs, with the regenerating script `internal/photonimage/testdata/jpeg_oracle.mjs`, the same under Photon 0.3.3 and photon-node 0.3.4); `TestResizeLanczos3MatchesPhoton` and `TestResizeLanczos3MatchesPhotonOnStripsAndNearOneRatios` (`internal/photonimage`, 551 resizes, the second with `testdata/resize_oracle.mjs`); `TestEncodePhotonPNGWritesPhotonsBytes` (`internal/photonimage/png_test.go`: Photon's PNG bytes for the committed fixture, and Photon's lengths and SHA-256s for three inputs); the oracles `TestProcessImageMatchesPi` and `TestResizeImageDimensionStrategyMatchesPi` (`internal/imageprocessing`) and `TestPhotonImagesMatchPiOnACorpus`, `TestPhotonImagesMatchPiOnTheJPEGQualityLadder` and `TestPhotonImagesMatchPiAtTheLimitBoundaries` (`durable/images`), which compare every byte for the inputs Photon decodes as Go does; the behavior tests in `durable/images/images_test.go` (orientation 1 to 8, shrink chain, JPEG-first order, BMP to PNG, extreme aspect ratio, give-up, undecodable bytes), `durable/tools/read_images_test.go` (notes and error results through `read`) and the Pi 1.4.0 `tools-images.test.ts` port (`durable/images/node/tools_images_test.go`, including the noisy PNG that Photon's size sends to JPEG).

Parity allowance: none. No paired scenario reads an image through `createCodingTools({ images })`.

Remove when: the owner moves the processor to Photon under wazero (it then matches Pi's bytes), Go decoders for JPEG and WebP write Photon's pixels (ports of `jpeg-decoder` 0.3.1 and of the `image` 0.24.9 VP8 decoder; the encoders and the resample already do), or Pi's pipeline stops being byte-defined by Photon.
