## D187 A native SDK holds a batch's first dialogs and responses in call and answer order, where Pi's single thread lets a call that awaits real work be overtaken

What: the Go, Python and Rust extension SDKs keep, for the tool calls of one parallel batch, the orders Pi's one thread gives: the first dialog of each call opens in call order, and calls whose dialogs were answered back to back respond (and end) in the order of the answers. They hold a call to do it. A call's first dialog waits until every earlier call of the batch has written its first dialog or ended; a call whose dialog was answered holds the responses of the calls answered after it until it returns or makes its next host call. In Pi a call that awaits real work before its dialog (a `fetch`, a timer, a child process) yields the thread, so a later call's dialog opens first; and a continuation that awaits again yields at once. A native handler's blocking work (an HTTP request, a sleep, a wait on a channel) is invisible to the SDK, so the SDK holds the later calls until the earlier handler reaches a dialog, a host call or its return. The order of the dialogs and of the responses is never different from Pi's single-thread order; only the moment a later call's dialog opens or its response is written can be later.

Why: Pi runs every extension on one thread, so the order of a batch's synchronous prefixes and of its continuations is a fact of the language, and no hand-off is needed (`agent-loop.ts:586-647`, `rpc-mode.ts:91-130, 771-777`). A native SDK runs each request on a thread of its own, and the OS scheduler decides which first dialog is written first and which of two back-to-back answers a handler resumes on first, so without a gate a port opens its second dialog first and ends its calls in no order. The gate can only be placed at the points the SDK sees: its host calls and the end of the handler. It cannot know that a handler is blocked in its own work, so it cannot release the later calls at the moment Pi's thread would. The owner chose the ordering with this latency cost over leaving the orders to the scheduler.

Scope: the tool calls of one parallel batch whose handlers open a dialog (`ui.select`, `ui.confirm`, `ui.input`, `ui.editor`, `ui.custom`), in the Go, Python and Rust SDKs, isolated and packed. Unchanged: the Node SDK, which one thread orders as Pi's does; a batch whose handlers open no dialog (no slot, no queue wait); calls of other batches, other sessions' calls (a subagent's tool calls on the same connection) and nested calls, which take part in no order (the host names the batch on each `tool_call` request, and a request without one is ungated); the start order of the handlers, which the SDKs already kept; and the tool-result messages, which follow call order.

Workaround: open the dialog before blocking work, or do the blocking work in a host call (`exec`), which the SDK treats as the handler's next await.

Owner decision: approved by owner Michael Kinsy on 2026-10-20 (choice, not impossibility: the SDK cannot observe a handler's own blocking work; user impact: only the moment a later call's dialog opens or its response is written, never their order; parity cost: a native handler that blocks before its dialog delays the later calls' dialogs of its batch).

Call-site markers: `extensions/sdk/tool_start_order.go` (`toolStart.beforeCall`, the dialog wait, and `toolStart.respond`, the response gate), `extensions/sdk-py/pig_sdk/__init__.py` (`_ToolStart.before_call` and `_ToolStart.respond`), `extensions/sdk-rs/src/tool_start_order.rs` (`ToolStart::before_call` and `ToolStart::respond`).

Evidence: `TestToolBatchDialogsOpenInCallOrderAndResumeInAnswerOrderAcrossSDKs` (`test/extension-conformance`) fails for every native realization without the gates (the Go dialogs open as `[T0 T2 T3 T4 T5 T1]`, the ends follow no answer order) and passes for all nine with them; the gate tests `TestToolDialogsOpenInCallOrder`, `TestToolResponsesFollowTheOrderTheAnswersWereRead` and `TestToolBatchOrdersAreIndependentAcrossBatches` (`extensions/sdk/tool_dialog_order_test.go`), `test_tool_dialog_order.py` (`extensions/sdk-py/tests`) and the `tool_start_order` and `tool_dispatch_wire` tests (`extensions/sdk-rs`) pin the held orders without a sleep and the independence of batches, including that a long call with no dialog in one batch never holds another batch's dialog.

Parity allowance: none: no Pi scenario asserts the moment a later call's dialog opens while an earlier call blocks.

Remove when: a native SDK's handlers run where a blocked handler yields to the next one (an async handler model with the SDK's scheduler), or the SDK is told when a handler blocks, so a later call's dialog or response is released at the point Pi's thread would release it; then the gates in the three SDKs and this record go.
