## D651 Credential and state files are replaced through a temporary file where that changes nothing but the inode, where Pi writes every file in place

What: in the files pig and Pi share (`auth.json`, `settings.json`, `trust.json`, `keybindings.json`, the MCP credential store, `mcp.json`, the models store `models-store.json`, and the two start-up migrations that write them) pig and Pi write differently. The record has two parts: part A and part C (the lock heartbeat) are built and landed.

### Part A: the writes (landed)

Pi writes each of these files with `writeFileSync`: it opens the file, truncates it and writes. A write that stops after the truncate (a full disk, a size limit, a kill, a power loss) leaves the file empty or cut short, and the next login or token refresh of one provider then saves a file that holds that provider alone (the owner's report of being signed out of every provider). pig writes a temporary file in the same directory (a new file is created with the mode its writer asks for under the umask, as Pi's open does; a file that exists is replaced through a private 0600 temporary file that then takes the mode, owner, group, attributes and access of the file it replaces), syncs it, syncs the directory, and renames it over the file (`internal/atomicfile` `WriteFile`), so a failed write leaves the old file. The rule: pig replaces the file when that changes nothing but the inode; otherwise it writes the file in place with the same bytes, exactly as Pi does, once, and says so in one line of the debug log (`PIG_DEBUG`, `internal/codingagent/atomic_debug_log.go`); that is not an error and not a warning. In place is the answer where

- the file has more than one hard link (a rename would leave the other names with the old bytes);
- an extended attribute cannot be copied onto the replacement, for a reason other than a file system that keeps none (they are copied when the file system takes them: POSIX ACLs on Linux, the user's attributes on macOS; the file keeps exactly the access it had, so an ACL entry that the directory's default ACL would give the new file is removed when the replaced file had none);
- on Windows, the DACL's entries (with each entry's flags) or SE_DACL_PROTECTED cannot be given to the temporary file, which is read back before anything is replaced (see "Windows security descriptor" below);
- the temporary file cannot be created in the directory (EACCES, EROFS, EPERM: a directory the process cannot write, holding a file it can), or the rename is refused (EBUSY, EXDEV, ETXTBSY: a file mounted into a container on its own is a mount point);
- the file is not a regular file (a device such as /dev/null, a named pipe): a rename would replace the node itself with an ordinary file that has its mode, and the bytes would never reach it.

A write that fails for a real reason (ENOSPC, EIO) is an error, in place or not, as in Pi; a read-only file is refused as Pi's write refuses it. A directory flush that fails for a real reason is an error; EINVAL, ENOTSUP, EOPNOTSUPP and ENOSYS on the flush and EACCES on opening the directory are accepted as a file system that has none. What is kept as Pi leaves it: the bytes, the mode, owner and group (where the process may set them), a symbolic link (its target is replaced and the link stays; a link to a missing file creates the file, a link to a missing directory fails with ENOENT and a loop with ELOOP, as Pi's open does), the extended attributes, and on Windows the security descriptor (owner, group, DACL entries with their flags, SE_DACL_PROTECTED, and SE_DACL_AUTO_INHERITED where the file system takes it back) and user-settable Win32 file attributes (HIDDEN, SYSTEM, ARCHIVE, NOT_CONTENT_INDEXED) of the replaced file. EXDEV cannot happen for the same-directory temporary file; it is on the list only for a file system that reports it for a rename within one directory (an overlay or a FUSE mount). The writers that take no lock (the keybindings save and migration) write in place in a directory the process cannot write, as Pi does.

Windows: on Windows the temporary file is moved over the existing file in one `MoveFileExW` call (`MOVEFILE_REPLACE_EXISTING|MOVEFILE_WRITE_THROUGH`) after the existing file's security descriptor and user-settable attributes (`HIDDEN`, `SYSTEM`, `NOT_CONTENT_INDEXED`; `FILE_ATTRIBUTE_ARCHIVE` is intentionally left set on the newly written file even when the old file had it cleared, so backup tools see the rewrite as an in-place write leaves it) have been carried onto the temporary file; `ReplaceFileW` is not used because it leaves the path without a file between its two renames (moving the old file to a backup name and moving the replacement into place). `MoveFileExW` refuses with `ERROR_ACCESS_DENIED`, `ERROR_SHARING_VIOLATION` or `ERROR_LOCK_VIOLATION` when another process holds the file open without delete sharing (an editor, an indexer, a sync client); pig retries the move for `fsretry.RenameBudget`. On Windows, when the file's access cannot be carried onto the replacement, or another process keeps the file open for the whole retry budget, the file is written in place, as Pi writes it (reporting the refusal and removing the temporary file); in that case alone a crash in the middle of the write leaves a short file and an unlocked reader can see an empty one (Pi's exposure). Non-busy errors stay failures. Accepted differences of moving a new file over the old one instead of `ReplaceFileW` or in-place write: file creation time, 8.3 short name, NTFS object ID, alternate data streams, and NTFS compression/EFS encryption flags (properties not set on pig's JSON config and credential files) are not carried onto the replacement; hard-link count above 1 is already written in place, and a symbolic link is followed to its target so the link stays. A credential file another program keeps open without delete sharing is retried for `fsretry.RenameBudget` and then written in place as Pi writes it.

Windows security descriptor: a write leaves the whole security descriptor of the file as Pi's in-place write does. The parts that decide who may open the file (the DACL's entries with each entry's flags, and SE_DACL_PROTECTED) are carried onto the temporary file before any data is written to it and read back there; if the temporary file cannot take them nothing has been replaced yet, and the write goes in place as Pi writes it, without an error. Before `MoveFileExW` replaces an existing file, the descriptor of the file as it is now is carried onto the temporary file and read back again, so the live path never has an instant with a wider DACL. A file that already has the descriptor is not touched. The carry sets the entries and SE_DACL_PROTECTED with SetKernelObjectSecurity (a call that runs no inheritance), which the first Windows run (the matrix, run 43699097748) showed keeps them in every starting descriptor and clears SE_DACL_AUTO_INHERITED whatever the source had. SE_DACL_AUTO_INHERITED is bookkeeping, not access, and is carried too: when the source has it and the call left it off, the same call is made with the request for auto-inheritance in the descriptor's control, and then SetNamedSecurityInfo (on the temporary file only, never on the live path), which the run showed sets the flag but also runs inheritance (it adds the parent's inheritable entries to an unprotected DACL and clears the inherited flag of the entries of a protected one); a call that changes the entries is undone by the first call, which leaves the flag off, and a carry that leaves only the flag different is a success. A source that is not protected, has no flag and whose DACL equals the temporary file's leaves the temporary file protected (the call does not unprotect it then): the write goes in place, as Pi writes it. The owner and group are carried as far as the token may set them (ERROR_INVALID_OWNER, ERROR_INVALID_PRIMARY_GROUP, ERROR_PRIVILEGE_NOT_HELD and a file that cannot be opened for WRITE_OWNER are ignored, as EPERM from chown is on Unix). ### Part C: the async lock renewal (approved 2026-11-14; landed with `fix/credential-lock-heartbeat-on-line`)

Pi's async credential lock (an OAuth refresh in flight) is renewed by proper-lockfile every stale/2 = 15 s with a 30 s stale window, while Pi's sync acquirers (every process that opens a credential store: the constructor, a footer render, a login selector) take any lock older than 10 s. A refresh that runs more than 10 s therefore has its lock taken by the next process that opens a store, and the holder learns of it only at its next heartbeat. pig renews the async lock every 5 s (`asyncUpdate` in `internal/pilock/lock.go`), so a live holder is never taken over.

What a user observes: with two pig processes on one `auth.json` and a provider that rotates a single-use refresh token, a refresh that takes more than 10 s is the only one that spends the token (Pi 1.5.2 spends it twice, and the provider then revokes the login); a process that opens the credential store while the refresh runs waits 180 ms (the sync acquirer's ten attempts, `SyncAttempts` 10 at `SyncDelay` 20 ms) on the fresh lock and then carries on, where Pi takes the lock at once. A refresher that starts late reads the holder's credential and keeps it; Pi overwrites it.

What was run (2026-11-14, xd670, tern-ci:v11; logs in `~/lanes/CredStore3.out/` on xd670; scenario `hbjob2.sh` with `zz_hb_probe_test.go.ai` and `pi_hb_probe.mjs`): one `auth.json` with four providers; `slow` refreshes openai-codex (single-use refresh token `r-old`) and holds the async lock for 12 s; `queued` is a second refresher of the same provider started at 1 s; `late1`, `late2`, `late3` start at 10.2, 10.6 and 10.9 s; `newstore` opens a credential store at 11 s. Why: (A) a credential or settings write must not be able to destroy the file it replaces, and every setup in which Pi's in-place write works (a single file mounted into a container, a hard link, an ACL, a directory the process cannot write) keeps working as before (and on Windows a file another program holds open without delete sharing for the whole `fsretry.RenameBudget` also falls back to an in-place write as Pi writes it). (C) with a provider that rotates a single-use refresh token, a lock taken from a live holder lets a queued refresher spend the same token a second time, and the provider then revokes the login.

Pi bug: yes for part A: Pi's truncate-then-write can empty `auth.json` on a failed write, and part C's double spend of a single-use token.

Scope: pig's writes of the listed files through `internal/atomicfile`. Pi's file formats, names and locations are unchanged.
