## D651 Credential files are replaced through a temporary file where that changes nothing but the inode, where Pi writes every file in place

What: in the credential files pig and Pi share (`auth.json` and the MCP credential store) pig and Pi write differently. The release line's record also covers the atomic writes of `settings.json`, `trust.json`, `keybindings.json`, `mcp.json`, the models store and the two start-up migrations, and the lock heartbeat; they reach main with the 0.8.0 merge-back.

### The writes

Pi writes each of these files with `writeFileSync`: it opens the file, truncates it and writes. A write that stops after the truncate (a full disk, a size limit, a kill, a power loss) leaves the file empty or cut short, and the next login or token refresh of one provider then saves a file that holds that provider alone (the owner's report of being signed out of every provider). pig writes a temporary file in the same directory (a new file is created with the mode its writer asks for under the umask, as Pi's open does; a file that exists is replaced through a private 0600 temporary file that then takes the mode, owner, group, attributes and access of the file it replaces), syncs it, syncs the directory, and renames it over the file (`internal/atomicfile` `WriteFile`), so a failed write leaves the old file. The rule: pig replaces the file when that changes nothing but the inode; otherwise it writes the file in place with the same bytes, exactly as Pi does, once, and says so in one line of the debug log (`PIG_DEBUG`, `internal/codingagent/atomic_debug_log.go`); that is not an error and not a warning. In place is the answer where

- the file has more than one hard link (a rename would leave the other names with the old bytes);
- an extended attribute cannot be copied onto the replacement, for a reason other than a file system that keeps none (they are copied when the file system takes them: POSIX ACLs on Linux, the user's attributes on macOS; the file keeps exactly the access it had, so an ACL entry that the directory's default ACL would give the new file is removed when the replaced file had none);
- the temporary file cannot be created in the directory (EACCES, EROFS, EPERM: a directory the process cannot write, holding a file it can), or the rename is refused (EBUSY, EXDEV, ETXTBSY: a file mounted into a container on its own is a mount point);
- the file is not a regular file (a device such as /dev/null, a named pipe): a rename would replace the node itself with an ordinary file that has its mode, and the bytes would never reach it.

A write that fails for a real reason (ENOSPC, EIO) is an error, in place or not, as in Pi; a read-only file is refused as Pi's write refuses it. A directory flush that fails for a real reason is an error; EINVAL, ENOTSUP, EOPNOTSUPP and ENOSYS on the flush and EACCES on opening the directory are accepted as a file system that has none. What is kept as Pi leaves it: the bytes, the mode, owner and group (where the process may set them), a symbolic link (its target is replaced and the link stays; a link to a missing file creates the file, a link to a missing directory fails with ENOENT and a loop with ELOOP, as Pi's open does), the extended attributes, and on Windows the DACL, attributes and streams of the replaced file (ReplaceFileW). EXDEV cannot happen for the same-directory temporary file; it is on the list only for a file system that reports it for a rename within one directory (an overlay or a FUSE mount).

Windows: ReplaceFileW refuses with ERROR_ACCESS_DENIED, ERROR_SHARING_VIOLATION or ERROR_UNABLE_TO_REMOVE_REPLACED (another process holds the file open without delete sharing: an editor, an indexer, a sync client) and ERROR_UNABLE_TO_MOVE_REPLACEMENT; pig retries the replacement for `fsretry.RenameBudget`, then returns the error, and never turns a refusal into an in-place write there. A ReplaceFileW that Windows stops half way (ERROR_UNABLE_TO_MOVE_REPLACEMENT_2, 1177: the replaced file under its backup name, nothing at the path) is finished by moving the replacement into place, or reversed by moving the backup back; when neither works the error names the kept files and nothing is deleted. The case that may break a working Pi setup is a credential file another program keeps open without delete sharing: Pi writes it in place and pig fails after the retry budget. NOT RUN (no Windows host in the lane); a Windows run is the evidence needed before this entry is called final on Windows.

Why: a credential write must not be able to destroy the file it replaces, and every setup in which Pi's in-place write works (a single file mounted into a container, a hard link, an ACL, a directory the process cannot write) keeps working as before.

Pi bug: yes: Pi's truncate-then-write can empty `auth.json` on a failed write.

Scope: pig's writes of the credential store `auth.json` and of the MCP credential store through `internal/atomicfile`. Pi's file formats, names and locations are unchanged.
