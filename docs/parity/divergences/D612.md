## D612 The p2 cache-warming plugin never arms a refresh timer longer than Node's setTimeout maximum

What: Pi's p2 cache-warming plugin (`apps/p2/plugins/cache-warming/warmer.ts` at c9552c7d, line 84 in `start` and line 122 in `#refresh`) arms `setTimeout(refresh, delayMs)` with `delayMs = getCacheWarmingDelayMs(ttlMs)` (`packages/ai/src/cache-warming.ts:46`: `floor(min(ttl*0.9, ttl-10_000))`). Node sets a `setTimeout` delay above 2147483647 ms to 1 ms and prints `TimeoutOverflowWarning` (Node timers docs, https://nodejs.org/api/timers.html#settimeoutcallback-delay-args: "When `delay` is larger than `2147483647` or less than `1` or `NaN`, the `delay` will be set to `1`."; observed on Node 24.19.0: `setTimeout(f, 3e9)` fires after 2 ms with the warning). A models.json `promptCache` lifetime above 2386092 s (about 27.6 days, where 90% of the TTL passes 2^31-1 ms) therefore makes Pi's refresh fire after 1 ms, send a paid one-token request, and re-arm at 1 ms (`#refresh` end, line 122) after each round trip until `#wanted` (line 131-132) hits the 30-minute (idle) or 60-minute (streaming) cap. Pi's coding-agent warmer (`packages/coding-agent/src/core/cache-warmer.ts:218-224`) is not affected: `schedule()` stops when `nextWarmAt` is past the cap before it calls `setTimeout`.

PiG (`apps/p2/plugins/cache-warming/warmer.go`, `armLocked`) clamps the arm delay to 2147483647 ms instead of 1 ms. Such a timer fires after the cap, `wanted` returns false (`now > startedAt + maxAge`), and the run stops with no paid request. This is what Pi's code intends: the delay is "refresh shortly before the lifetime ends", and for a lifetime beyond the cap no refresh is ever wanted. Skipping the arm (as the coding-agent warmer does) is equivalent for requests and also releases `keepAlive` at once; the clamp is chosen because it is the smallest change to the ported control flow (one timer per run, `Stop` and `Close` unchanged) and gives the same observable requests: none. Only the idle `keepAlive(1)` lasts until the timer or a Stop.

Why: Pi bug (a timer API limit its code does not handle); the upstream issue is drafted for the owner to post. Reproducing the 1 ms re-arm would send paid requests back to back for up to an hour per conversation.

Pi bug: yes, a delay above 2^31-1 ms re-arms at 1 ms in `warmer.ts` (`start` and `#refresh`); Pi has no test for it.

Owner decision: owner approved 2026-11-09 (the clamp, over reproducing Pi's 1 ms).
