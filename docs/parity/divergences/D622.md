## D622 The process-exit input drain ends on the terminal's reply to a DA1 query written after the input disables, where Pi waits for 50 ms of input silence

What: Pi's interactive shutdown calls `terminal.drainInput(1000)` (`packages/coding-agent/src/modes/interactive/interactive-mode.ts:4268` and `:4279`, `shutdown`). `drainInput(maxMs = 1000, idleMs = 50)` (`packages/tui/src/terminal.ts:391-427`) writes the Kitty pop and the modifyOtherKeys disable, then discards input until 50 ms pass without any, at most 1000 ms; the bracketed-paste, mouse, focus and light/dark disables are written only afterwards, by `stop()` (`terminal.ts:429`, `tui.ts:971-979`, `tui-alt-screen.ts` `beforeTerminalStop`). PiG's `ProcessTerminal.ExitDrain` (`tui/terminal_exit_drain.go`) writes, in this order, the Kitty pop and modifyOtherKeys disable, bracketed paste off (`?2004l`), light/dark reports off (`?2031l`, when on), the fullscreen renderer's mouse and focus disable (`?1006l?1004l?1003l?1002l?1000l`), and then one DA1 query (`ESC[c`); it reads and discards input until the reply to that query has been read and 5 ms (`exitSentinelSettle`) pass without input, and not a byte past that. Terminals handle their input in order, so the reply proves the terminal handled every disable and that every byte it sent before them has already been read and discarded. The wait is one terminal round trip, not 50 ms, and it is bounded by Pi's 1000 ms maximum and by nothing shorter: a timer under the round trip would end before the reply and leave it for the shell. The 5 ms of silence after the reply discards a second reply to the query (a terminal or multiplexer that answers DA1 twice) and an earlier reply still in flight that the count missed. DA1 replies owed to earlier queries arrive first and are counted, not mistaken for the sentinel: the keyboard-protocol and OSC 7501 queries (`pendingKeyboardProtocolDeviceAttributes`) and the renderer's terminal-color queries (`ExitDrainFacts.DeviceAttributesOwed`). A reply the input reader read the start of is finished by the drain (`inputTail`). The sentinel is used only when the terminal answered the startup DA1 query of this raw session (`deviceAttributesAnswered`, which proves it answers exactly `ESC[c`) and the renderer is one that reports its state; otherwise Pi's timer drain runs unchanged. Input is read one byte at a time so that what the user typed after the reply stays queued for the shell.

Why: the 50 ms wait is about a tenth of an interactive run (about 54 ms of 520-570 ms) and a fifth of a default-theme run (about 220-240 ms). A conditional skip never fires in real runs: modifyOtherKeys is on after the DA1 fallback, and the fullscreen renderer keeps mouse and focus reporting on until `Stop`, which runs after the drain. The timer cannot be shortened safely, because it guesses how long a terminal or a link takes; the reply does not guess. It also closes two windows that Pi's order leaves: mouse, focus and light/dark reports are stopped before the wait, not after it, so a mouse moved while the process exits no longer reaches the shell after the timer ends, and the wait follows a slow link (a reply 400 ms away is waited for; Pi's 50 ms timer ends before it).

Difference in observable behavior: keys typed while the exit is in flight, up to the reply and the 5 ms after it, are discarded, as in Pi's 50 ms window; keys typed after that stay queued and reach the shell, where Pi discards everything typed within 50 ms of the last input. The window is one round trip (well under a millisecond on a local terminal) instead of at least 50 ms, so a key typed 1-50 ms before the process exits reaches the shell here and is lost in Pi. The query's reply is consumed, never echoed, and nothing is written to the screen.

Pi bug: none claimed. Pi's wait is the price of a guard that a reply to an ordered query makes exact.

Residual risk: (1) a terminal that sends a key event from a different thread than the one that writes the reply can send an event encoded before it handled the disable after the reply; one such event reaches the shell, where Pi's 50 ms silence would usually have caught it; (2) an extension that writes its own DA1 query through `terminal.write` and whose reply is still in flight at exit ends the wait one reply early, and the exit's reply (`ESC[?...c`) reaches the shell; PiG counts only the queries it writes itself; (3) a link whose round trip exceeds Pi's 1000 ms maximum ends the wait before the reply, which then reaches the shell, where Pi, with nothing in flight, would have printed nothing; (4) a terminal that answered DA1 at startup and not now costs the full 1000 ms at exit, as Pi's drain can (`TestExitDrainWaitsForTheReplyUpToPisMaximum`, "the reply never comes": a terminal marked as having answered at startup, no reply, ExitDrain returns after exactly 1000 ms with one query written; the cap is kept at 1000 ms because a shorter one would leak the reply on a slow link); (5) a second DA1 reply that follows the first by more than 5 ms reaches the shell; (6) the `pig config` raw-mode exit (`coding/cli/config_command.go`) keeps Pi's timer drain.

Scope: `tui` (`ProcessTerminal.ExitDrain`, `ExitDrainFacts`, `deviceAttributesScanner`, `noteInputTail`, `ProcessTerminal.drainClock`), `internal/codingagent` (`stopInteractiveTui`, `exitDrainFacts`).
