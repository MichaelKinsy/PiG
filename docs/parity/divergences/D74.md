## D74 Pi-ai's builtin API implementations run in PiG's host

What: inside an extension process, pi-ai's compat layer, API registry, lazy API wrappers, model catalog and env-key lookup are Pi's own code (D73). The ten builtin API implementations they load (`anthropic-messages`, `openai-completions`, `openai-responses`, `azure-openai-responses`, `openai-codex-responses`, `google-generative-ai`, `google-vertex`, `mistral-conversations`, `bedrock-converse-stream`, `pi-messages`) are replaced by a bridge. For each request the bridge applies that API's upstream credential check (`options.apiKey`, the headers that stand in for one, or ambient credentials for Vertex and Bedrock) and upstream's `Request aborted` for a signal that already fired, then streams the request through PiG's Go port of the same provider: `options.apiKey` owns the request ahead of every configured credential, `options.reasoning` sets the thinking level (a `stream()` call and a `streamSimple()` call without one run without reasoning, not at the session's level), headers and env pass through, and an aborted `options.signal` cancels the host request. `openrouter-images` `generateImages` returns an error result, because PiG has no image-generation provider.

Why: the upstream implementations import the vendor SDKs (`@anthropic-ai/sdk`, `openai`, `@google/genai`, `@aws-sdk/client-bedrock-runtime`), which PiG does not ship to extensions, and PiG already carries parity-tested Go ports of these providers, which its own agent uses. Running every builtin API through one bridge keeps credential resolution and request behavior uniform. Owner-directed launch P0 fix (Reddit report on 2026-09-26: pi-hermes-memory calls `completeSimple` from `@earendil-works/pi-ai/compat`).

Observable effect: an extension's `stream`/`complete`/`streamSimple`/`completeSimple` sends the same request (credential, model, messages) and receives the same event and result shapes as under Pi, from PiG's provider; a request aborted in flight carries the Go provider's abort message rather than the vendor SDK's. A model whose provider an extension registered with its own `streamSimple` still reaches the API implementation its `api` names, as under Pi, and never re-enters that `streamSimple`. Provider-specific `stream()` options beyond the common ones (for example Anthropic `thinkingEnabled`) are not forwarded, results lack `responseId` and `rawStopReason`, and `generateImages` for OpenRouter returns an error result where Pi generates images. A direct pi-ai call carries only the identity's `User-Agent` and no attribution headers, as under Pi's pi-ai without an `identity` option; the bridge does not forward `identity`. A process with no extension runtime (a detached helper, a forked child or a worker an extension starts) streams through `pig provider-bridge`, which calls the API implementation directly (`StreamAPILeaf`, not `coding.BuildModel`): its requests carry no attribution headers, as under Pi, and a request with a `fetch` option ends with an error event on the same stream, where Pi sends it with that `fetch`. The vendored `api/<api>.js` stubs export `stream` and `streamSimple`, and the pure values Pi's module of that API also exports, taken from Pi's own file: `openai-completions` `convertMessages` and `pi-messages` `PiMessagesResponseError` (vendored as `api/openai-completions.impl.js` and `api/pi-messages.impl.js`), and every value of `api/google-shared` (vendored as `api/google-shared.js`). Each of the three is Pi's file with at most one `import` line of a vendor SDK replaced (`openai` by a class that throws when constructed, `@google/genai` by the SDK's `FinishReason`, `FunctionCallingConfigMode` and `ThinkingLevel` declarations copied byte for byte), pinned by the hashes of the vendor manifest. Where these names are reachable differs by process and is as under Pi: an extension's own `import "@earendil-works/pi-ai/api/<name>"` fails in Pi's extension runtime and in PiG's alike, while a process that resolves `@earendil-works/pi-ai` as plain Node does (pi-subagents' detached runner) reaches the harness's peer; in a worker thread or forked child an extension starts, the loader hooks it inherits serve `@earendil-works/pi-ai`, `/compat`, `/models`, `/oauth` and `/providers/all` from PiG's runtime where Pi loads the extension's own copy of the package (or fails when the extension has none), with the same export names and kinds. `api/openai-codex-responses` also exports Pi's three WebSocket helpers, which act on the Go provider's cache of the provider-bridge child that serves the helper's streams (the child's own, as Pi's Maps are per process): `closeOpenAICodexWebSocketSessions(sessionId?)` and `resetOpenAICodexWebSocketDebugStats(sessionId?)` are one-way lines to that child (with no child nothing is sent and none is started, as Pi's helpers on an empty map), and the synchronous `getOpenAICodexWebSocketDebugStats(sessionId)` reads a replica the child pushes after every change of its counters, written before the terminal result line of the stream that made it, so the replica is exact once a stream's result has been read and, during a stream, as of the last line read. A reset clears the replica at once and the child's counters and SSE-fallback flag when it reads the line; a close reaches the child before the session's next request, which travels the same pipe. Pinned by `TestProviderBridgeClientCodexWebSocketHelpers` (the lag window, both cases) and `TestCodexWebSocketHelpersOfTheHarnessPeerActAsUnderPi` (Pi's module and the peer's against one local Codex WebSocket server, member for member).

Call-site markers:
- `coding/extension/host/subprocess/runtime-node/shims/pi-ai-bridge.mjs`: the bridge the vendored `api/<api>.js` stubs load. With no extension runtime in the process it streams through `shims/provider-bridge-client.mjs` and `pig provider-bridge` (`coding/cli/provider_bridge.go`, `internal/codingagent/provider_bridge.go`); see docs/extension-api-parity.md "Provider bridge for processes with no extension runtime".
- `coding/model.go`: `requestOptionsProvider.Stream`, which streams a direct pi-ai call that the bridge sends through `coding.BuildModel`, without attribution.
- `automation/gen/vendor-pi-ai-apis.mjs`: writes the stubs and the three Pi modules they re-export from (`api/openai-completions.impl.js`, `api/pi-messages.impl.js`, `api/google-shared.js`), each with its one replaced SDK import line, and `shims/google-genai-enums.mjs`.

Locked by: `coding/extension/host/subprocess` `TestVendoredPiDistMatchesThePinnedPackage` (every vendored pi-ai file is verbatim except the listed bridge stubs and the three Pi modules with one vendor-SDK import line replaced), `TestRestoredAPIValuesBehaveAsUnderPi` (`convertMessages`, `PiMessagesResponseError` and the google-shared values give the results Pi's own modules give on the inputs of Pi's tests of them), `TestHelperResolvingPiAiFromTheHarnessSeesPisExports` (every `api/*` subpath of the pinned package exports the same names and kinds from the harness peer), `TestExtensionImportsOfPiAiSubpathsResolveAsUnderPi` and `TestChildAndWorkerImportsOfPiAiResolveAsUnderPi` (the real extension load, the worker and the forked child, against Pi's two resolution modes), `TestVendoredModulesImportOnlyWhatTheBridgeStubsExport`, `TestNodeRuntimeShimsExportEveryPinnedPiValue` (the compat surface), and `TestNodeCompatCompletionAbortCancelsHostRequest` (the extension's `apiKey` reaches the host, no session thinking level is applied, and an aborted signal cancels the host request). The provider bridge is locked by `coding/cli` `TestProviderBridge*` (provider order, the aborted terminal event before the result, callbacks, the strict request shape, exit with the starter) and `coding/extension/host/subprocess` `TestProviderBridgeClientHonoursTheBridgeWire` (the client side, the `fetch` error and an idle bridge that does not keep its caller alive).

Parity allowance: no paired scenario runs an extension's direct provider call; the Pi-extension end-to-end run compares pi-hermes-memory's consolidation request and result against the pinned Pi over a scripted OpenAI-compatible server.

Remove when: PiG ships the vendor SDKs to extensions and runs upstream's API implementations, or upstream removes the compat entry point's global dispatch.
