## D462 The server and each worker have two stores, not one

What: Pi's host has one store, one commit queue and, for the server's data of an address, one SQLite commit (`packages/chord/src/store/host-data.ts:316-336` `importHostData`, `:341-354` `deleteHostData`, both through `commitOperation` `:359-374`; `packages/chord/src/node/app/app.ts:865` and `:891` call them). PiG has two hosts per server or worker (the Go host, the plugins' NodeHost), and a store has one writer (a singleton meta row: `last_seq`, `next_id`), so each has its own: the kit's (`kit.sqlite` in a worker's directory, `store.sqlite` on a server) and the plugins' (`store.sqlite` in a worker's directory, `plugins.sqlite` on a server). Nothing commits across them. Three things still differ from Pi because of that. (1) The data directory holds both files. (2) `importData` and `deleteData` commit twice: the NodeHost's store, then the Go host's (the NodeHost runs Pi's `exportHostData`, `importHostData` and `deleteHostData` for its side through three control requests of its process, `plugins_node_host_data.go`; the Go host's side is the owners it serves, `Host.Serves`). A failure the process survives is undone as Pi's flow undoes it: a definite failure before either commit, or of the NodeHost's, puts the old directory back; a definite failure of the Go host's commit after the NodeHost's put its part undoes the NodeHost's (a refused import's part is deleted, with `existing: "replace"` the old part is put back), so the end state is the one Pi's undo leaves; if that restore fails too, nothing is undone (the new directory in place, the old one aside) and the rejection carries both errors; an unknown outcome (`unavailable/storage_failed`) of either commit undoes nothing and says so with Pi's text. A kill is covered by an intent, which Pi, with one commit, has no need of: a file in `server/imports/` (`<kind>.<key>.json`, with the address's old data in both hosts beside it as `.node` and `.go`) written and flushed (file, then its directory) before the first commit and removed, with its directory flushed, right after the second. At start, after the plugins' load and before the server serves anything (`resolveIntents`), a leftover intent is resolved with the code of the live undo: an import is UNDONE (both stores restored from the saved parts, the staging or new directory removed, the old directory back from where it was set aside), a delete is COMPLETED (the NodeHost's rows, the Go host's, the directory: Pi leaves the repetition of a delete to its caller too, `app.ts:889-890`). An import is undone and never completed because a kill cannot say which commit ran, and an import that refuses an address that has data would read its own first commit as "has data". Every step of the resolution is safe to repeat, so a kill during it is finished by the next start. (3) A running worker's export (`PackRunning`) takes the kit's commit queue (its export's first part), then has SQLite copy the plugins' file at one instant (`VACUUM INTO` over a read-only connection, a read transaction the NodeHost's writes do not disturb) and exports the copy, so the two stores' export is one point; the kit's writes wait for its archive, the plugins' writes proceed meanwhile and the archive does not contain them (the store keeps them). Pi holds its one store's commit queue (`store.export`, `archive.ts:3-4`). The copy costs the plugins' store's size in temporary space (`.chord-export-*`, beside the archive).

No longer a difference: the archive. PiG's data archive is Pi's one format in both directions. The export writes one `store.archive` (the plugins' records and the kit's tables together, merged at one point) and one `server.archive` (both hosts' records), the entries Pi's `unpackEntries` accepts (`archive.ts:178-222`: the manifest, `store.archive`, `server.archive`, `files/`); `kit.archive` and `kit-server.archive` are gone, with their readers. Pi's own unpack and its host-data import accept an archive PiG made, and PiG imports an archive Pi made, with the kit's Files tables routed by owner into the kit's store (so the Files index arrives) and the server part's records to the host that serves their owner. The sentence that the owner decides whether to build a converter is gone: it was built, decided under the owner's rule of 2026-11-13T22:52:04Z ("fix all bugs") and decision 29 of 2026-11-17.

Observable effect: an operator finds two SQLite files per host directory and, after the first import or delete, a `server/imports/` directory that is empty between operations. After a kill in the middle of an import or a delete the next start reports one app error of kind `interrupted_data_change` per interrupted operation: "undone" (the address's directory, plugins' records and server rows are as they were before the import) or "completed" (a delete: all gone). On macOS and the BSDs, a hard-killed server's own lock file must be removed before the next start, as in Pi; the stale address locks of interrupted operations are cleared automatically by that start under the held server lock. That kind is PiG's own member of `AppErrorKind` (`chord/nextnode/app/app.go`); Pi's `AppError` at the pin has `host`, `http`, `workers`, `plugins`, `base_build` and `server_scan` (`app.ts:115-121`). A consumer written for Pi's kinds gets it in its `OnError` like any other and reads `Kind` and `Error`: one that logs every report generically prints it (the importing child of the kill tests does, `fmt.Fprintln(os.Stderr, err.Kind, err.Error)`; `TestAStartReportsTheInterruptedImportItUndid` shows the report arrive), one that switches on Pi's six kinds with no default ignores it. A kill before the intent is durable leaves the address as it was (a staging directory `.chord-import-*` may stay: nothing refers to it). A kill between the commits, or after the second and before the intent is removed, undoes the whole import: Pi's single commit would have kept that import; PiG undoes it, because the caller never received success. An import whose intent cannot be removed after the second commit is reported as an error ("the import is done but its record cannot be removed") and the next start undoes it. An intent that cannot be used (it does not parse, has another shape, names another address, a saved part is missing or does not restore, a store fails again) is never guessed at: its address does not start and its import, delete and export are refused with an error that names the file, the other addresses serve, the start reports it, and the intent stays for the next start; an operator fixes the cause or removes the three files. That is how the app treats one unusable address today, not a new policy: a worker whose start fails fails that address's worker with the public error `worker failed to start` until a retry or a rollout, and the server and the other addresses run on (Pi `packages/chord/src/node/workers/workers.ts:454-470` and `:499`, `START_FAILED` `:251`; PiG `chord/nextnode/workers/workers_workers.go:894-972`). With store files that hold garbage in one worker directory, a start serves the other address, a hold of that address fails with `worker failed` when the ready timeout (an app option, `AppOptions.Timeouts.ReadyTimeout`) ends, and the app reports a `workers` error (`file is not a database`) and a `host` error (`resolve_failed`): `TestOneAddressWhoseStoreFilesAreGarbageFailsItsOwnWorkerAndTheOthersServe` (about 13 seconds, the timeout being set to 10 by the test). A blocked address fails its hold the same way (`TestAnIntentThatCannotBeUsedBlocksItsAddressOnly`). The window between the plugins' load and the end of the resolution allows nothing to read or write an address's data: a plugin's facet setup only declares the types it serves (it has no documents, routines or natives, `packages/chord/src/host/facet.ts:1-4`), so no plugin object is live and no plugin code touches a store, the HTTP component answers 503 until the load is reported done and the delegation to the NodeHost's link waits for it, and a worker starts only when a request holds its address, which cannot come before; `TestNothingIsServedAndNoWorkerStartsUntilTheStartHasResolvedItsIntents` probes the port at every step of the undo (every answer 503) and records the first worker start after "resolved". The archive of an address is importable by Pi and by PiG whichever made it. An export of a running worker needs the plugins' store size in free space beside the archive, and the archive does not contain the plugins' writes made during it.

Scope: only apps built with the kit (`chord/nextnode/app`): `ImportData`, `DeleteData` and `ExportData` of an address, and the start's resolution of what a kill left. The refused import, the definitely failed one, the unknown outcome and the refused delete keep Pi's flow and Pi's messages; the intent adds only the kill, and a request of an address with no intent behaves as before. The archive format is Pi's, not a divergence. Pi's server, with one store, never needs any of this.

Why: the node-evaluator design (`docs/plan/chord-plugins-node-evaluator.md` §store): the Go store is an in-process engine and a store is not shared over the link; sharing one sqlite file between two engines would corrupt the id allocator. Nothing commits across two SQLite stores, and neither can hold a record that the other's commit clears, so the intent is a file beside both.

Pi bug: Not a Pi bug.

Owner decision: approved by the owner (Michael Kinsy) on 2026-11-08, OWNER-DECISIONS #19, for the two stores; the one archive format and the intent that makes a kill all or nothing by the owner's rule of 2026-11-13T22:52:04Z and decision 29 of 2026-11-17.

Remove when: (1) the files: the plugins run in the server's (or worker's) own host process with one store, or one store file can be shared by two hosts. (2) the two commits and the intent: the same condition, or Pi imports and deletes an address's server data in more than one commit and adds the same guard. (3) the export at one point across two stores and its temporary space: the same condition.
