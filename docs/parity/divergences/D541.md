## D541 A message object is one per Node process and one per ExtensionRunner call; Pi's extensions and callers all share one realm

What: In Pi every extension and every caller runs in one JavaScript realm, so the message of `message_start`, `message_end`, `turn_end` and `agent_end`, the session entry's `message` and anything passed on `pi.events` are one object. PiG shares that object between every handler and every extension packed in one Node process, between the events of the Session's own run and the session entry, between the handlers of one `ExtensionRunner` emit (Go, Rust, Python and Node callers alike), and across Node processes for a message passed on `pi.events` (the receiver that holds the message resolves it to its own object). What it cannot share:

| Case | Pi | PiG |
|---|---|---|
| A Go, Python or Rust caller of `ExtensionRunner.emitMessageEnd` (or `emit`, `emitBoundary`) passes a message it built or read from `getEntries()`, and compares it with the `event.message` a Node handler holds, or a later emit's | `===` when it is the same object | false: the caller passes a value (a Go map, a Python dict, a Rust `Value`), and `getEntries` returns a fresh decode on each call, so there is no object a number could name |
| A Node handler of `ExtensionRunner.emitMessageEnd` edits `event.message` in place | the caller's object holds the edit | the edit is made to the message decoded for the call; the caller sees it only in a replacement the result carries |
| Node extensions in two processes (isolated cells, a member quarantined after a fault, different runtimes): one edits its message in place after the other holds it | both hold the one object, so the edit is on it | each process holds its own object for the message, with its own edits; a later payload that carries the host's value does not undo an edit of the process's own, and a `message_end` handler's edit goes back to the host and reaches the other process as a new value |
| A Node, Go, Python or Lisp handler of `message_update` edits, in place, the content of the partial message (`event.message.content`: a block's text, a block added or removed) | `agent-loop.ts:436-438` emits `{ ...partialMessage }`, a shallow copy that holds the very `content` array object of the provider's partial; a provider that pushes one `output` message for every partial (`ai/src/api/openai-completions.ts:313,384,442`: `partial: output`, and `output` is the message the stream ends with) therefore has the edit in the assistant message that `agent-session.ts` persists and in the next provider request, and the next handler of every extension reads it from the same `event.message`. The sharing is of the content array object, so it depends on the provider: a provider that builds a new partial per event shows none | the edit stays in the process of the extension that made it: the next handler of the same or of another extension, the assistant entry and the next request do not hold it (the measured provider is the OpenAI-completions shape above, in `TestInPlaceMessageEventEditsMatchPi`, row `message_update/deep`; observable in every SDK named, isolated, packed, and the fused Go extension) |
| A Rust handler of `message_update` makes the same edit | the same | the edit CAN be written and is lost, as in the other SDKs: the Rust handler is an `EventHandler`, `Fn(&Context, &mut Value)` (`extensions/sdk-rs/src/extension.rs:190`), called with `&mut data` (`extension.rs:3601`), and `data` is a copy the connection rebuilt for this dispatch (`extensions/sdk-rs/src/event_stream.rs:48`, `req.args = Some(root.clone())`, while the replica keeps the root as the host sent it); for `message_update` nothing compares that copy with what was received, so the reply carries no edit (a message edit is returned only for `message_start`, `message_end`, `agent_end`, `extension.rs:3712-3726`). Pinned by `a_message_update_handlers_edit_of_the_partial_stays_in_its_copy_and_is_not_sent_back` (`extensions/sdk-rs/tests/event_stream_wire.rs`: the handler changes the partial's text; the reply carries neither the edit nor `_pigEventEdits`, and the next delta of the stream applies to the text as the host sent it). Observable in the Rust SDK isolated and packed; listed on its own because the owner's decision names it |
| A Rust handler of `message_start` or `agent_end` replaces the member wholesale (`event.message = {...}`, `event.messages = [...]`) | later handlers of the same extension and of other extensions see the new object; the session keeps the original: no entry, no provider request and no listener of the session carries the change (runner.ts `emit`, one event object for every handler) | later handlers see it, and the session SAVES it as an edit inside the message: for `message_start` the entry, both provider requests and the session's listeners carry it, for `agent_end` the entry and the listener do (not the requests). A Rust handler owns its event as a value (`Fn(&Context, &mut Value)`, `extensions/sdk-rs/src/extension.rs`) and a value has no identity, so the reply cannot tell "replaced the member" from "edited inside the member"; the Go, Node, Python and Lisp SDKs (isolated, packed, fused) do what Pi does |
| A Rust handler of `message_update` replaces `event.assistantMessageEvent` wholesale | later handlers see the new object; the session keeps the original | later handlers do NOT see it and the session does not hold it: the SDK's snapshot of that member compares scalars and key presence only, because the streaming partial inside it grows on every delta and a full compare per delta is the cost measured for the case above (23 to 46 microseconds and 15 to 30 KB per delta) |
| An extension passes a message on `pi.events` to a Node extension in another process that has not yet received that message's `message_end` | `===` its own message later | a proxy to the sender's object, as for any object on the bus (D83); the receiver's own object, once it receives the message, is another |
| A Node extension whose only message handlers are `turn_end` or `agent_end` compares `agent_end.messages[i]` with `entry.message` | `===` | false: the host numbers a message when a Node handler receives `message_start` or `message_end`, and persists it before any later handler asks |

Why: A JavaScript object cannot cross a process boundary, and a value passed by a Go, Python or Rust caller has no identity. The host numbers each message (`RequestPayload.message_seqs`, from one process-wide counter, so two Sessions or runners never share a number in a Node process), and a Node process resolves a number to the object it holds: that carries identity wherever the host holds a message object (a Session's run, a graph emit's decoded event) and wherever a Node process holds the number (`pi.events`). The rows above are what has no such object or no such process. Matching packed to isolated would remove behavior Pi has.

Why: a faithful form must find out, for every `message_update` of every run, whether the handler changed the partial: a snapshot before the handler and a comparison after it (the way `message_end` does it once per message). The measured cost of that form, on a 2,000-delta stream with one handler that edits nothing (`BenchmarkNodeMessageUpdateStream`, the host side, per delta): base 193 to 208 microseconds and 88 allocations; with the detection +23.1 microseconds and +14.9 KB of heap, that is +11 to +24 % per delta (range over the repeated runs), paid by every run whether or not any handler edits. The owner chose to record the two cases instead of spending that on the hot path.

The two Rust replacement rows are a limit of the Rust handler's type, recorded narrowly (option (a) of the owner's decision of 2026-11-17): in-place edits inside the message, the common case, behave as Pi in Rust, and a replacement of `message_start.message` or `agent_end.messages` or of `message_update.assistantMessageEvent` is the only thing a Rust value cannot tell from an edit. The Rust rows are pinned to this behaviour in `TestInPlaceMessageEventEditsMatchPi` (`rustRecorded`), which fails if the Rust SDK starts doing something else.

Pi bug: none.

Scope: `ExtensionRunner` of the Go, Rust and Python SDKs (`sessionGraph.new` kind `ExtensionRunner`) over Node extensions, for the first two rows; Node extensions in different processes, for the third row; handlers of `message_update` that edit the partial's content in place, in every SDK, for the fourth and fifth rows; a Rust handler that replaces `message_start.message`, `agent_end.messages` or `message_update.assistantMessageEvent` wholesale, for the sixth and seventh; Node extensions that handle neither `message_start` nor `message_end`, for the last. Not: an assigned member of the `message_update` event object (cured), the message of `message_start`, `turn_end`, `agent_end` and `message_end` (cured), a Go, Node, Python or Lisp handler's wholesale replacement of a member (as Pi); Node extensions packed in one process; the Session's own run seen by one extension; a Node caller (it uses Pi's own in-process ExtensionRunner, D73); other SDKs' payloads, which are unchanged.

Owner decision: 2026-11-17, row 3 (the in-place edit of the streaming partial at message_update, including Rust): option 3, a narrow record of the two cases with the measured figures; and the Rust wholesale replacement of `message_start.message`, `agent_end.messages` and `message_update.assistantMessageEvent`: option (a), a narrow record of exactly those three rows. Approved as written. Owner decision: 2026-11-08, owner list item #8 (isolated message identity) approved as written, in the narrowed form; proposed by PaseoIdentity and narrowed after the review in `reviews/paseo-identity-f4.md` (the per-emit numbering and `pi.events` resolution the first draft listed here are ported).
