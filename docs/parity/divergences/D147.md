## D147 Compactions requested in one input batch run one after another

What: Pi's `compact()` awaits `abort()` before it creates its abort controller, so two `compact` lines of one input batch both start, and neither aborts the other. For a Session that is too small both answer "Nothing to compact", and for a Session with enough history Pi compacts twice at the same time. PiG chains the compactions through `rpcAwaitInOrder`: each starts after the previous one settled. Both answer "Nothing to compact" for a small Session, as in Pi (measured on the previous pin, 6 of 6 runs; Pi 1.3.0's `compact()` is unchanged). For a Session with enough history Pi answers both compacts with success and writes two compaction entries (previous pin, 3 of 3 runs). PiG starts the second compaction after the first one wrote its entry, so the second answers "Already compacted" and the Session has one compaction entry.

Why: Concurrent compactions of one Session write overlapping compaction entries and cancel each other when the second claims the Session while the first starts (PiG answered "Compaction cancelled" in 2 of 3 runs).

Scope: `coding/cli/rpc_mode.go` (`RPCCommandCompact`, `compactResolved`).

Owner decision: 2026-10-10, lead order to route the compact race through the one ordering mechanism.

Call-site markers: `coding/cli/rpc_mode.go` (`compactResolved`).

Evidence: `TestRPCCompactsOfOneBatchDoNotCancelEachOther`, red before the change (10 runs).

Parity allowance: none.

Remove when: Pi serializes the compactions of one Session.
