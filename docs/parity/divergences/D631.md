## D631 A command run by `pi.exec` or the bash tool gets pipes for its output, where Pi gives it socket pairs

What: Pi starts a command with Node's `spawn` and `stdio: ["ignore", "pipe", "pipe"]` (`packages/coding-agent/src/core/exec.ts:58-62`; the bash tool spawns the same way). On Linux and macOS libuv makes each such "pipe" a Unix socket pair (`uv_socketpair` in `uv__process_init_stdio`), so the command's stdout and stderr are sockets. PiG gives the command the write end of a pipe (`childwait.NewPipe`, `os.Pipe` on Unix). A command can tell the two apart, and two effects were measured (Linux container of the lane image, dash as `sh`, Pi 1.5.2 with the post-release backports, 96-CPU host xd6702):

1. Reopening its own output. `sh -c 'echo x > /dev/stdout'` through `execCommand`: Pi resolves code 2, stdout empty, stderr `sh: 1: cannot create /dev/stdout: No such device or address` (a socket cannot be opened through `/proc/self/fd/1`, ENXIO); PiG resolves code 0, stdout `x`. Every run, both sides. The same holds for `/dev/stderr` and `/proc/self/fd/N`, so for `tee /dev/stderr`.
2. The code of a command cut off at `maxBuffer` while it writes stdout. When the reader closes a socket that still holds unread data, the writer's next write fails once with ECONNRESET and raises no SIGPIPE; a pipe raises SIGPIPE at once. `sh -c 'exec yes'` over the cap: in Pi `yes` goes on to report `yes: standard output: Connection reset by peer` and exits 1 when it gets that far, is ended by Pi's SIGTERM while it reports (143), or its report meets the closed stderr (141). Pi's code was 1 in 257 of 3600 runs (7%) inside one Node process of 34800 calls and in 167 and 159 of 360 runs (46%, 44%) inside Node processes of 240 calls; of 1200 runs with stderr in a file, the 16 that ended 1 all held the full report and 664 of the 920 that ended 143 held its beginning. PiG's code was 141 in 3571 of 3600 runs and 143 in 29: never 1, and no report. Measured again on Linux 7.0 (tern-ci:v11 on xd670, lane ExecSigpipeFlake job m2, 200 calls per Node process): 11 of Pi's 20,000 runs alone and 3 of its 10,000 beside 32 busy loops reported `yes: standard output: Broken pipe` instead of the reset (code 143, once 1), because `unix_release_sock` marks the writer's end shut down (`net/unix/af_unix.c:707`) one statement before it posts ECONNRESET (`:709`), and a write that reads the two in between fails with EPIPE in `sock_alloc_send_pskb` (`net/core/sock.c:2979-2981`), which `unix_stream_sendmsg` returns without raising SIGPIPE (`af_unix.c:2431-2432`); PiG's 20,000 and 10,000 runs ended 141 or 143 and reported nothing.

macOS measured (macOS 26.7.3; `/usr/bin/yes` with stdout on one end of a Unix socket pair, stderr to a file, the other end closed; 160 runs): when the reader read some bytes and then closed, 61 of 80 runs died by SIGPIPE with empty stderr and 19 of 80 exited 1 writing `yes: stdout: Socket is not connected` (ENOTCONN); when the reader closed with the data unread, 80 of 80 died by SIGPIPE. In the nightly `Race / macos-15 / host` job (`TestExecCommandMatchesPi`, 360 runs of `exec yes 2>"$1"`), 31 runs of Pi were filtered and 1 leaked with exit code 1. Measured for `/usr/bin/yes`, inferred for Pi's exec path on macOS until the nightly's `host` group runs on a head that holds this. Effect 1 (`/dev/stdout`) remains unmeasured on macOS. Windows has named pipes on both sides and is not part of this record.


Measured at the Node level, not tested through the tools: `pi.exec` gives the command no stdin on either side (`"ignore"`, `/dev/null`). The bash tool gives it one only when the shell takes the command from stdin (`packages/coding-agent/src/core/tools/bash.ts:129`), and Node's is then a socket pair too. Measured once with Node's `spawn` and a `"pipe"` stdin: `stat -L -c %F /proc/self/fd/0` prints `socket` and `cat /dev/stdin` fails with `cat: /dev/stdin: No such device or address`; through a pipe, which is what PiG's bash tool gives the shell, the same command prints `fifo` and reads the input. It is not one of this record's effects until a test on each side holds it.

Why: a faithful port would make commands that work on Linux fail (`> /dev/stdout`, `tee /dev/stderr`), which no PiG user gains from. The cost of keeping pipes is that a command which fails under Pi for that reason succeeds under PiG, and that an exit code 1 which Pi shows in a share of cut-off runs never appears.

Pi bug: none. The socket pair is libuv's choice for every Node child; Pi does not ask for it.

Scope: `coding/extension` (`ExecCommand`, both output pipes) and `internal/codingagent/tools` (the bash tool's output pipe). Unix only.
