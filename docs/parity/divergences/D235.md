## D235 A session-graph client's runs share one ctx.signal when its SDK sends no run token, and when two runs were aborted before the host read them

What: in a Host whose run signal comes from a session-graph client (an ExtensionRunner an extension constructed), Pi's `agent.signal` is a new AbortSignal for every run (`agent.ts:345-347`: one `AbortController` per `activeRun`, made at `agent.ts:518-527`), so a handler that holds run 1's `ctx.signal` never sees run 2's abort, and sees run 1's own abort even when run 2 began before anyone read it. The wire is the answer of the client's `getSignal` (an opaque callback result the host reads leniently; no frame changes): `null` while no run is active, else `{"aborted": bool, "run": <positive integer>, "endedAborted": true}`.
- `run` is minted by the client's SDK, in the wrapper of the bound `getSignal` function, from one counter for the whole client process (extensions packed in one process never share a token). A token is new when the function returns another signal object than the wrapper's last answer, and the same object keeps its token; a `null` answer touches nothing. The wrapper holds the last signal object.
- `endedAborted` is present (and omitted when false) with a new token when the signal object of the previous answer had aborted by then, and is repeated on every answer of that token, so a lost read cannot lose it.
- The host (`graphSignal.read`) makes a new context for a token other than the held one, cancelling the held one first when `endedAborted` is set.
Where PiG still differs from Pi, and D235 applies: (1) a client that sends no `run`, or zero (a `run` is positive, so the host reads an explicit zero as no token, not as a malformed answer; an SDK built before this change, or a client that answers the wire by hand, sends none) keeps the old rule: two live runs with no read of "no run" between them are one context, and a handler that holds run 1's `ctx.signal` sees run 2's abort. The mixes degrade to today's behaviour: a new SDK with an old host (the old host ignores the members), an old SDK with a new host (no token). (2) Two runs that are both aborted when the host first reads them, with no live read between them, are one context: `ctx.signal === held` is true where Pi's two aborted signals differ (pinned by `TestGraphTwoRunsAbortedAtBirthShareOneContext`).

Why: (1) the host cannot tell runs apart without an identity from the client; an SDK before the token sends none. (2) A client whose `getSignal` returns a new signal object on every call (a derived signal) has a new token on every read. Once its run is aborted, a context made for every aborted read would be cancelled at birth, and the watcher (`context.AfterFunc` fires at once for a cancelled context) would sync, read, renumber the run and read again without end (the busy loop fixed in 892827ff8c). The storm guard bounds it: a read makes at most one context, and a token other than the held one makes none while the held context is cancelled and the answer is aborted, so an abort costs at most 4 reads of the client's `getSignal` (the sync that sees it, the watcher of the context it made, the watcher of the context it replaced, one more sync) and each request one read; case (2) is the price of that bound.

Per SDK (the porting rules: the same interface and the same behaviour in every SDK; only the implementation differs). Interface: the wire members above. Behaviour: the token and `endedAborted` rules above, the last signal held, a `null` answer touching nothing, one counter per client process. Implementation: Go `signalRuns` in `extensions/sdk/extension_runner.go` (a mutex per bound function; identity is `==` guarded by `reflect.Type.Comparable`, so a signal whose type cannot be compared is a new run on every answer; counter `atomic.Uint64`; the token is boxed once per run, not once per answer), Python `_signal_wire` in `extensions/sdk-py/pig_sdk/extension_runner.py` (a lock per wrapper and one for the `itertools.count`; identity is `is`), Rust `SignalRuns` in `extensions/sdk-rs/src/extension_runner.rs` (a `Mutex` per bound function; identity is `ProviderSignal` equality, which is `Arc::ptr_eq`; counter `AtomicU64`), Lisp `runner-signal-wire` in `extensions/sdk-lisp/src/extension-runner.lisp` (an `sb-thread` mutex per bound function; identity is `eq`; counter by `sb-ext:atomic-incf` on a global). Node: none; Pi's own `ExtensionRunner` runs in the Node process over real AbortControllers and there is no wire.

Pi bug: none. The difference comes from the wire and from the bound that keeps a derived signal from looping.

Scope: a session-graph client's ExtensionRunner only (a client of the host, not an extension's own `ctx.signal`); case (1) for clients without a token, case (2) for two runs aborted at birth with no live read between them. A Host over a Session reads the agent's own context, one per run.
