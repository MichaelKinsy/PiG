# lw-tui3: streamed write card per-frame work, equivalence proof

Slice lw-tui3 (LW roadmap S25, finding E14), commit d2d4384c0e on base 1166362571. It changes how a streaming tool card reads its partial arguments and how the write renderer reaches its lines. No byte the terminal receives changes.

| Change | Argument | Evidence |
|---|---|---|
| The card keeps the streaming parser's argument object (`StreamedToolArgs.Object`); the built-in write renderCall receives it in `context.Args` with no text (`ToolDefinitionRenderers.CallReadsFields`, set for the built-in write renderCall only, found by code pointer as `markdown_resume.go` does). Every other renderer, the call fallback and a non-object value still get the JSON text, encoded once per update. | Before, the renderer received `ArgumentMembers` JSON of that same object and decoded it with `encoding/json`. Strings, numbers and nested objects decode to the values the object holds, with one exception: a lone surrogate escape, which the parser keeps as one UTF-16 unit (WTF-8 bytes) and `encoding/json` decodes as U+FFFD. The write renderer maps those bytes to U+FFFD in the content and the header path (`replaceLoneSurrogates`), which is also what Pi's terminal writes for a lone surrogate. | `TestWriteRenderCallMatchesTheEagerRendererAtEveryPrefix`: the new renderer fed the parser's object against the previous renderer fed the JSON text, at every prefix of 48 random streams (random chunk sizes; `.ts`, `.go` and `.txt` paths; a path rewritten mid-stream; collapsed and expanded; CR, tabs, multi-line comments and template strings, blank tails; lone high and low surrogates, adjacent ones and a pair), then twice after completion. `TestStreamedArgsReachAFieldsReaderDecoded`, `TestStreamedArgsEncodeOncePerDraw`. |
| `ArgsPreview`, the read card's compact label and a frontend's arguments are filled from streamed arguments only when a reader needs them (a card without a definition when it draws, `frontendTool`), once per update; for write and edit from the object. | A card drawn by a definition's renderers never reads them; the write and edit headers name the path only (`FormatWriteHeader`/`FormatEditHeader` = title + `renderToolPathFromArgs`), so reading the path from the object or from the decoded text gives the same string. | `TestStreamedArgsReachAFieldsReaderDecoded`, `TestStreamedArgsDrawTheHeaderOfACardWithoutDefinition`, the tui `ToolExecution`, `ToolArgs`, `ToolDefinition`, `ToolCard`, `TuiSurface` tests by name. |
| The write highlight cache highlights a line past the 50-line leading block when a frame first reads it, not when it arrives. | Upstream sets such a line to `highlightSingleLine(line)` and never changes it until a rebuild; the cache keeps the line and computes exactly that value on first read. The prefix-block fallback (`prefixHighlighted[i] ?? highlightSingleLine(...)`) is deferred the same way. | `TestWriteHighlightCacheHoldsWhatUpstreamHolds` (every line equals upstream's value at every update of 40 random streams), `TestWriteRenderCallMatchesTheEagerRendererAtEveryPrefix`. |
| Once the lines pass the leading block, the block is highlighted again only when its text or the highlight epoch (active theme, loaded languages: `tui.CurrentHighlightEpoch`) changed since the last refresh, not on every update. | An update past line 50 changes only lines at or after the old last line, so the 50 leading lines are the text the last refresh highlighted. `HighlightCode` returns the same lines for the same code and language within an epoch (the memo already relies on this: a miss returns what a hit would). A rebuild clears the flag, so the first update after it refreshes as upstream does. | `TestWriteHighlightCacheHoldsWhatUpstreamHolds`, `TestWriteRenderCallRebuildsTheCacheWhenTheArgumentsComplete`, the Pi oracle case past the leading block (below). |

## Pi oracle

`TestInteractiveStreamedWriteCardMatchesPiOracle` streams the arguments 16 characters at a time through `handleAgentEvent` and the provider's streaming parser and compares every frame, and the frame after `setArgsComplete`, with Pi 1.1.0's `ToolExecutionComponent` fed `parseStreamingJson` of the same prefixes. It now has four cases: a `.ts` file inside the leading block (the original case), a `.ts` file that grows past the leading block with a block comment after line 50, drawn expanded so every lazily highlighted line is drawn, and a `.txt` file with CR line ends, tabs and a blank tail, collapsed and expanded. All frames match.
