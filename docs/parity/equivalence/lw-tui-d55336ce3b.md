# lw-tui: render-path changes, equivalence proof

Slice lw-tui (LW roadmap S9), commits 246bffdb7e, 800e355d56, 318a3ed69f and d55336ce3b on base a5df22bd3a. None of them changes a byte the terminal receives; one changes when the terminal size is read, to the rule Node already follows.

| Change | Argument | Evidence |
|---|---|---|
| `nodeurl.PathToFileURL` resolves an absolute path without `process.cwd()` | Node's `path.resolve` reads `process.cwd()` only when no argument is absolute (lib/path.js; `nodepath.Resolve` already applies the rule). `path.win32.resolve` of a drive-absolute path also stops before reading it. The href is the same; only the getcwd syscall is gone. | `TestPathToFileURLAbsolutePathReadsNoCwd` (Node 24.19.0 hrefs, including percent-encoding, a trailing separator, `..`, drive and UNC paths; resolve with and without the process state agree; 0 cwd reads), `TestPathToFileURLRelativePathReadsCwd` |
| The process terminal keeps its size between SIGWINCHs while the interactive resize handler holds it | Node's `process.stdout.columns` and `rows` are fields that `WriteStream._refreshSize` updates on SIGWINCH (lib/tty.js); Pi reads them per frame. PiG read TIOCGWINSZ per frame instead. The handler drops the kept size before it posts the resize render, and a read that a SIGWINCH overtakes is not kept (generation check). Windows (no SIGWINCH) and terminals no handler holds read the size every time, as before. | `TestProcessTerminalKeepsSizeUntilResize` (1 read for 100 frames; kept until the SIGWINCH as in Node; new size after it; reads every time after stop), `TestProcessTerminalWithoutResizeHandlerReadsSizeEveryTime`, `TestProcessTerminalDropsSizeReadAcrossResize`, `TestResizeHandlerFrameSeesTheNewSize` (resize, SIGWINCH, handler, next frame is 120x40), `TestProcessTerminalOnPseudoTerminal` |
| Fullscreen frame rows written without fmt; the frame buffer starts at the last frame's length; no per-frame changed-row slice | `fmt.Fprintf("\x1b[%d;1H\x1b[2K%s")` and `"\x1b[%d;%dH"` are replaced by the same bytes written directly; the changed-row test is the same comparison done in place. One write per frame, as before. | the tui `AltScreen`, `Fullscreen`, `ProcessTerminal`, `ResetAndClamp` and `Upstream` tests by name (green), `TestAltScreenStreamingFrameAllocationCeiling` |
| The assistant block keeps its spacers, thinking-run regions and diagnostic lines across updates; `SetHasToolCalls` with an unchanged value does nothing; `SetChildren` keeps the cached lines of the children it keeps | A kept child is the one that would be built again: the region of run *i* is rebuilt whenever its Markdown, hidden state, hidden label (theme colors included) or padding changes, and its click handler captures the same run index and state. A kept container child's cached lines are invalidated by its dirty flag, the rule `renderBorrowedLocked` already relies on for every cached child. | `TestStreamedAssistantMessageMatchesFreshBlock` (40 random streams of text, thinking, tool calls and terminal errors, hidden and visible: the streamed block renders what a fresh block renders after every delta, at two widths), `TestContainerSetChildrenMatchesFreshRender` (3000 random replace/reorder/edit/invalidate steps against fresh child renders), the tui `Assistant`, `Thinking`, `MouseRegion`, `Container`, `Markdown`, `Windowed` and `WholeFrame` tests by name |

## Recorded session

The interactive-5 scenario (Pi-Bolt `bench/benchmark.py` interactive, fake model, 5 prompts, 25 turns) was recorded on a pty for the base and the new binary. The raw byte streams differ from run to run on the same binary (frame boundaries depend on timing: 165-208 KB, 78-92 frames), so the comparison is of the settled screens: the pyte screen (text and per-cell colors and attributes) after start-up and after each of the 5 prompts, plus the set of OSC 8 hyperlink targets. Three base runs and the new run give the same digest, `9fe1e81303e566123d142ddccbc706f4`.
