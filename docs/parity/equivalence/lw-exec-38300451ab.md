# lw-exec: continuation turns hand off by coroutine switch, equivalence proof

Slice lw-exec (LW roadmap S1). The executor's reaction order, and every byte that depends on it, is unchanged. What changes is which goroutine runs a turn's body. Before, each turn ran on the goroutine that called `run`, and a grant woke that goroutine through a `permit chan bool` (the baton). Now a turn started by `run` is an `iter.Pull` coroutine. A goroutine that waits for its own turn (in `run`, `runDirect` or an await) serves the executor: it drains reactions and resumes coroutine turns in place. A grant is then a coroutine switch instead of a goroutine wake.

## What stays the same, and why

| Property | Argument | Evidence |
|---|---|---|
| One body runs at a time | `executor.active` is still the single owner. A body resumes only when its grant sets `active` (`grant`, or a serving goroutine taking a `needsDriver` turn), and gives it up only by suspending, detaching or returning (`advance`). `next` is called by one goroutine at a time: the state machine (`turnWaiting`/`turnRunning`/`turnDetached`/`turnDone`, guarded by `executor.mu`) hands a body to exactly one driver. | All executor, observation, js_promise and tslib_async tests by name (75 tests), plus the ordering suites below |
| Reaction order (microtasks, nextTick phase, I/O completions, watchers) | `popLocked`, `pollWatchersLocked` and the queues are untouched. A grant is still the same queued job at the same FIFO position. The only change is what happens when the job runs: the drain resumes the body in place instead of stopping to wake a goroutine. The body runs until it gives up execution, as before, and the drain then continues with the next job, as the released goroutine's drain did before. | `TestExecutorScheduleMatchesBaton` (new): a fixed program uses every turn and await kind (I/O-granted response turn; awaits of a resolved promise, an I/O completion and a JS promise; a stream continuation on another goroutine with Yield, AwaitTick, AwaitContinuation with a RunOwned callback on a third goroutine, and ResultContext). It records each step, microtask and I/O completion. The order equals the order recorded on the baton executor at 4cfaf24153, run 20 times. |
| Await on an already resolved promise (`suspendContinuation`) | When the awaiting turn holds execution and no ready reaction or nextTick callback is queued, the release's drain would poll the watchers and then pop the turn's own grant. Nothing else can run in between. `resumesNext` performs those effects (watcher poll, end of the tick phase, the trace's microtask) without the round trip. | ticks.json, sdk_sse and executorTrace tests unchanged (they count the microtask the elision still reports) |
| Detached segments (StreamObservation Await*, ResultContext) | A detached segment still runs on the turn's own goroutine (its home). The release still lets the queued reactions run first, as `release()` drained inline before the segment continued. Reacquire is still the acquire reaction in the completion-class queue (ready, tick, external), now a grant. | `stream_observation*` tests, AwaitTick/AwaitExternal oracle tests, `TestExecutorScheduleMatchesBaton` |
| Goroutine identity (`ownedByCaller`) | `Run` (coroutine) identifies the goroutine inside the callback, once per callback, as the old `Run` did on the caller. `RunOwned` keeps running the callback directly on the calling goroutine, so its `owner` is still that goroutine. `observeEvents` already identified the goroutine inside its body. | `TestRunOwnedIdentifiesTheGoroutineOnce`, `TestRunIdentifiesTheCallingGoroutine` |
| Panics | A coroutine body's panic is recovered in the coroutine and rethrown on the turn's home goroutine after the body releases execution. It surfaces where `run` was called, as before. | existing panic-path tests in the ordering suites |

## Known difference (not observable by a Pi program)

A goroutine that waits for its own turn may now run other turns' bodies while it waits. A body that blocks its goroutine while holding execution (a Go-side wait, not an await) already stalled every turn under the baton. Now it also delays its driver goroutine's own turn, which could not run anyway while execution was held.

## The other two commits

- `03d349c779`: the event iterator owns its promises and waiter, and registers one `context.AfterFunc` per consumer loop. A wait on an already-canceled context ends at once, as the hook firing immediately did. A cancellation after a push assigned an event leaves that event, as `cancelWaiter` did. The acquire after a suspension is a queued job value. An await of a resolved promise uses the executor's shared one or resumes at once (`awaitResolved`, above). Each reaction hop is unchanged: the same promises settle in the same order. `TestAssistantMessageEventStreamAssignedWaiterWinsCancellationResolution` and the iterator tests in `event_stream_continuation_test.go` cover this, together with the ordering suites.
- `0e0499bd1c`: when an `AwaitContinuation` callback returns, its waiter is marked as about to serve. A coroutine turn granted by a goroutine that cannot resume it then waits for that waiter instead of waking a sleeping goroutine. Only the goroutine that resumes the turn changes; the reaction order does not. Same suites.
