# lw-pfast-registry equivalence (slice S23, base f22240330e)

Pi 1.1.0 reads the same files in the same operations; this slice changes how many times Pig stats them, which goroutines run the reads, and which lock they wait on. Stdout, session files, provider requests, RPC output and extension events are unchanged. Each change below has the reference or oracle that pins it.

| Change | Why the observable behaviour is the same | Proof |
|---|---|---|
| L1: the auth.json and models-store.json stat runs before the read-state mutex (`ai/auth_reload.go`, `ai/models_store_read.go`) | A read takes effect at its stat, which is still inside its own call window. A stat that a concurrent reload overtakes differs from the published revision and starts one more reload, so a reader never returns data older than its stat. The models-store reload stats before the mutex but still under the file lock. | `TestAuthStorageReadStatsOutsideTheReadLock`, `TestFileModelsStoreReadStatsOutsideTheReadLock` (TryLock at the stat, on the reading goroutine), existing `TestAuthStorage*`, `TestFileModelsStore*`, `TestResolveProviderAuthSharesFileReloadIsolation` |
| L2: `registryCredentials.current` loads the runtime-key overlay without the registry lock (`ModelRegistry.runtimeCredentials` is an `atomic.Pointer`) | The pointer is still stored only under `mu`: `SetCredentialStore` clears it, `runtimeCredentialsLocked` creates it, and runtime-key setters still order under `mu`, so `SetCredentialStore` discards runtime keys exactly as before. A reader that loads the overlay just before a swap reads as one that took the lock just before it. | `TestRegistryCredentialReadsDoNotTakeTheRegistryLock`, `TestRegistryCredentialOverlayRacesStoreSwapsAndRuntimeKeys` (-race), `TestCredentialRuntime*`, `TestNativeRefreshCredentialTransactionDoesNotReenterRegistry`, `TestLoginCancelWhileCredentialStoreLocked` |
| L4: one auth.json and models-store.json view per offline operation (`ai.WithFileReadSnapshot`; installed by `queueAvailabilityRefresh` through `AvailabilityReadContext` when no extension provider takes part, and by `RefreshCatalogs` for the Radius and built-in remote restore when offline) | Lever Q3. Pi stats on every read (`auth-storage.ts:401-439`), but its warm catalog restore and availability pass make every stat in one macrotask (the oracle counts async_hooks callbacks between them: none). Nothing in the process runs between those reads, and a write by another process is ordered against them only by time, so publishing what the operation read at its first stat is Pi's outcome when the write lands after the operation's last stat; a write before the first stat reaches the whole operation in both. In-process writes (Modify, Delete, Write) and reloads by other readers replace the published data, so the next read stats again; the operation never reads older than what the process already returned. A stored `!command` key runs its command on read, so a view holding one is not reused; the models-store view is held only after an auth.json view. A pass with an extension provider, the native collection, and network refreshes read as before. | `TestAvailabilityPassAuthViewMatchesPiUpstream` (Pi 1.1.0 `ModelRuntime`: one-macrotask premise; rewrite by another process before the first read, after it, after the pass, and the next pass; corrupt auth.json rejection and `getError`), `TestFileReadSnapshotFreshness`, `TestFileReadSnapshotStatsEveryReadAfterACommandKey`, `TestAvailabilityReadContextOnlyWithoutExtensionProviders`, `TestFileReadSnapshotStatsOncePerOperation` |
| L5a/b: a provider's restore runs on the collection's operations and settles through its signal's `AfterFunc`; a publication with nothing queued and nothing to persist runs on the caller (`ai/models_runtime_refresh.go`) | The refresh still settles a provider when its operation returns or its signal is cancelled, whichever is first (Pi's `raceWithAbortSignal`), and still records an error only when the signal is live. The inline publication is Pi's: a publication chained on an already settled promise with no I/O (`models.ts:504-531`); it still checks the generation and the signal under the collection lock. | `TestModelsOfflineRefreshStartsOneGoroutinePerProvider`, `TestModelsRuntime*`, `TestModels*Refresh*` (-race) |
| L5d: `AwaitModelTasks` starts its tasks on the owner and collects the results itself | First rejection or the caller's cancellation still settles the wait; success still needs every task; the owner still joins every task on Close; the result channel holds every result, so no task waits for a caller that settled early. | `TestAwaitModelTasksStartsOneGoroutinePerTask`, `TestModelTask*`, `TestCredentialRuntime*` (-race) |
| L5c: inside an operation with a view, providers run one after another on the caller (`Models.Refresh` offline, `awaitProviderTasks` for the availability fan-out) | Such an operation runs no extension code and, offline, no I/O but reads of its one view. Pi settles those providers at one await depth, so they complete in provider order and `Promise.all` reports the first provider's rejection; within one view every credential read fails or none does. A check writes nothing, so not running the providers after a rejection is not observable. | `TestAvailabilityPassAuthViewMatchesPiUpstream` (corrupt auth.json: rejection and `getError` equal Pi's), `TestOfflineModelPassesRunProvidersOnTheCaller`, availability and runtime suites in `./coding` |

Not taken: L3 (one read per check) is subsumed by L4 on the passes that carry a view and would change Pi's second read after extension code on the others; L6 (models.json order kept from the loaded bytes) needs `model_registry.go`/`request_auth_runtime.go` changes outside this slice (requests.tsv); L7 is visible when an extension host starts.

Found while proving Q3, not changed here: `coding.ModelRuntime.HasConfiguredAuth` reads the credential store live for built-in providers, where Pi reads `snapshot.configuredProviders` (`model-runtime.ts:544-546`); the oracle compares the pass's published configured set instead (requests.tsv).

Measured on the Linux lab host with `TestPrintReadToolsProcessGate` (lw-pfgates counters merged onto 1a98e19408, GOMAXPROCS=1): base f22240330e 535 goroutines, 433 auth.json and 85 models-store.json stats per run; this slice 107 goroutines, 15 auth.json and 3 models-store.json stats. The 15 are one per offline operation (4), one per request (5), two at the store's construction, and four live reads at startup model resolution and `ValidatePromptModelAuth` outside this slice's paths (requests.tsv).
