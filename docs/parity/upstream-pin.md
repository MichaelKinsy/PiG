# The upstream Pi pin

PiG targets one Pi build. `.upstream/pin` names it, and every other statement of the pin is read from it or derived from it. The pin is a Pi release tag (now `v1.5.0`) or a pinned commit of Pi's main branch, which is reported as the package version followed by `+` and the first eight characters of the commit (`Pi <package_version>+<commit[:8]>`).

## The pin file

`.upstream/pin` is the one committed setting. It is tracked even though the rest of `.upstream/` is the ignored source mirror.

| Key | Meaning |
| --- | --- |
| `ref` | What the pin was bumped to: a release tag, or the full commit of a commit pin. |
| `commit` | The exact 40-digit commit. |
| `package_version` | What Pi's `package.json` files and `pi --version` report (`1.1.0`). |
| `version` | The display and ledger version: the package version for a tag, `<package_version>+<commit[:8]>` for a commit. Ledgers and inventories are named by it (`mapping-v1.1.0+42a3497d.json`), and so is the mirror (`.upstream/v1.1.0+42a3497d`). |

In Go, `coding.UpstreamVersion` is the display version, `coding.UpstreamPackageVersion` the package version, `coding.UpstreamCommit` the commit and `coding.UpstreamRef` the ref. A parity comparison against `pi --version`, an npm dependency or a `package.json` uses the package version. A file name, ledger field or the coverage label uses the display version. `pig --version` prints the package version, as `pi --version` does.

## Reading and overriding the pin

Every consumer reads the pin through `automation/pin/pin.py` (`pin.py get <key>`, `pin.py env`, `pin.py make-vars`) or through the generated `pigversion.go`. `make pin-show` prints the effective pin.

`PI_UPSTREAM_REF=<tag|commit|branch>` overrides the pin for one run without editing a file:

```bash
make pin-show PI_UPSTREAM_REF=v1.1.0
make parity-deps upstream-mirror PI_UPSTREAM_REF=42a3497d   # the oracle and source mirror of that pin
make test PI_UPSTREAM_REF=42a3497d
eval "$(PI_UPSTREAM_REF=42a3497d python3 automation/pin/pin.py env)" && go test ./coding/...
```

An override resolves a tag through `git ls-remote`, a commit through the GitHub API and its tarball, and remembers the result under `~/.cache/checkouts/github.com/earendil-works/pi/resolved/`. A run that overrides the pin builds Go with a `-overlay` that replaces `pigversion.go` (the overlay lives under `$TMPDIR/pig-pin-overlay-*`), so no tracked file changes. Make and the env command export `PIG_UPSTREAM_*` for child processes.

`make parity-deps` installs the Pi oracle of the effective pin into `extensions/sdk-ts/node_modules` (a link into a cache) and points `.upstream/current` at the pin's mirror when that mirror exists:

The oracle is always **Pi built from source at the pin**, for a release tag and a commit alike (`automation/pin/oracle.py`). The source is the exact commit tarball from GitHub (`codeload`), whose root names the commit and is checked against the pin, so no `.git` is needed. The build runs `npm ci` with Pi's own lock, builds with Pi's scripts, `npm pack`s the workspace packages `pi-coding-agent` depends on, and runs `npm ci` of the pin's frozen dependency closure with those packs in place of the registry packages. The closure is a `package.json`/`package-lock.json` pair in `automation/pin/frozen/<commit>.closure.json.gz`: a release's is the lock of the published install (`pin.py freeze-closure --from-published-lock extensions/sdk-ts/package-lock.json`), so the third-party tree is the one `npm install @earendil-works/pi-coding-agent@<version>` gave and the install is laid out as that package's (`install-strategy=shallow`) is; a commit's is derived once from its packs with `npm install --package-lock-only --before=<commit date>` (`pin.py freeze-closure`) and committed, so it is the tree a published install of that commit would have had. Each workspace pack entry in the closure carries the sha512 integrity of its tarball (a release's is the published package's; a commit's is the digest of the packs the freeze built), so `npm ci` rejects a source build that is not byte-for-byte the frozen one. A commit with no frozen closure is derived on its first build and frozen there; a release with none is an error. Pi's own `install-lock` is not used: it comes from the monorepo's workspace resolution and lays packages out differently (for example `openai` inside `pi-ai`), which the tests and the vendored runtime do not read. `check-oracle` compares the installed tree with the closure, package by package. It is cached under `$PIG_PI_BUILD_STORE` (default `~/.cache/pig-dev/pi-builds`) per commit and frozen inputs (the model data and closure digests), and carries `.pig-pi-oracle.json` (`commit`, `source: "build"`, the digest of the model data). Each build goes into a fresh directory that is published by an atomic ref write and never rewritten or removed afterwards, so worktrees with different frozen files, a forced rebuild (`install-oracle --force`, which publishes another directory) and a parity test reading an oracle never disturb one another; concurrent builders of one identity wait on a lock and build once. A failed build is an error: nothing falls back to another Pi, the stamp is written only after the whole build, and `make parity-deps` exits non-zero.

Pi regenerates `packages/ai/src/providers/data/*.json` from live models.dev while it builds, so two builds of one commit differ. Every pin therefore freezes that directory in `automation/pin/frozen/<commit>.provider-data.tgz` (a reproducible archive with a recorded digest), unpacked in place of the hydrate step. A release tag's snapshot is the data its published package shipped (`pin.py freeze-oracle --from <pi-ai dist/providers/data>`); a release tag with no snapshot fails the build, naming the command. A commit's snapshot is taken from its first build: the build hydrates once and freezes that data itself. `check-oracle` and the parity runner reject an oracle built with other data, and an oracle that is not the source build of the pinned commit.

The published npm package is an explicit opt-in: `PIG_PARITY_PI_PUBLISHED=1 make parity-deps` installs the locked release of a tag pin (`automation/ci/npm-locked.py`), and the runner then accepts an unstamped oracle (or the exact mise-installed release when `PIG_PARITY_PI_BIN` is unset). A commit pin has no published package, so the opt-in does not apply to it. For v1.1.0 the source-built tree is the published one: `diff -r` of the two `node_modules` trees differs only in npm's bookkeeping files (`.package-lock.json`, the dependency-ready marker), and every package is the same name and version at the same path.

## Following Pi main (pin-follow)

`automation/pin/follow.py <commit>` prepares everything a pin move needs, without moving the pin. `automation/pin/watch.py` runs it for each new head of Pi's main branch (`git ls-remote`, so no API token; cron every 5 minutes under `flock -n`).

| Step | Command | Result |
| --- | --- | --- |
| oracle | `pin.py install-oracle` | the source build; the first build of a commit freezes its provider data and dependency closure in `automation/pin/frozen/`; the step fails, and the ready log names the file, when either is missing afterwards |
| mirror | `make upstream-mirror` | `.upstream/v<version>` |
| inventories | `make interface-proposals`, `make test-inventory-generate` | extracted per package (`PIG_INTERFACE_EXTRACT_INCREMENTAL=1`): a package keeps its earlier extraction while the files its TypeScript program reads (its own and its reachable workspace packages' code, declarations and manifests, and the third-party files the last extraction read) are unchanged |
| ledgers | `pin.py ledgers` | pending mapping carried from the committed pin, gap baseline (`make ledger-update` twice), deltas; the upstream-sync manifest is generated against the earlier pin (`from`), whose mirror `make upstream-delta` builds |
| sdk-vectors | `node automation/gen/generate-sdk-vectors.mjs`: Pi's own helpers run on the oracle write `test/parity/sdk-vectors/*/*.json`, each stamped with the pin; the `generated` step's SDK surface page refuses a vector stamped with another pin (86 problems at the first dry run). A changed vector is content: the Go helper port it tests must follow. |
| gaps | `pin.py gaps` | the gap list: `make ledger-update`, then `make ledger-check` (the check alone stops on every reviewed exception the earlier pin's mapping made stale, which only the update prunes; under the override the committed pin's `reviewed-types.json` is restored afterwards) |
| tasks | | one `closure <upstream-file>` task per file with gap rows and one `delta <package>` task per package with pending upstream-sync files, in `tmp/pin-follow/<version>/tasks.tsv` |

Each step is recorded in `tmp/pin-follow/<version>/state.json`; a rerun resumes after the last passing step, and `--until <step>` stops after one. A failed step appends a FINDING line to the ready log; a finished follow appends a READY line and writes `automation/pin/records/<version>.json` (step times, latency from the commit time, frozen artifacts). The ready log is `--ready-log`, else `PIG_PIN_FOLLOW_READY_LOG`, else `tmp/pin-follow/<version>/ready.log`; set `PIG_PIN_FOLLOW_READY_LOG` in the cron entry to post to a shared log. The commit time is the modification time `git archive` gives the source tarball. The targets are the gap list 30 minutes and Porter output 2 hours after the upstream commit. `--run-porter` runs one headless `make porter-task` per task, serially in one tree; `automation/porter/run-porter-tasks.sh <tasks.tsv> <log-dir> <worktree>` runs a task list and commits each task's output (every created file included; a timed-out or non-building task is committed as `PARTIAL`); run the groups of different packages in separate worktrees to run them side by side, because the Porter edits the shared ledgers.

The follower never changes `.upstream/pin`, never merges, and the reviewers and merge train gate its output as any other.

## Moving the pin

```bash
make pin-bump PI_UPSTREAM_REF=<tag|commit>
```

One command does the whole move, and it stops only on content work (ledger rows to close) or on a failure that names itself. It is resumable: every step is recorded with its wall time, exit code and the number of changed files in `tmp/pin-bump/<commit[:8]>.json`, a rerun after a failure resumes at the step that failed, a rerun of a finished bump says so and does nothing, and the earlier pin (the ledgers are carried from it) comes from that record, not from the pin file, which has moved. When the pin file moved without a record, the earlier pin is the one `HEAD` holds; `PIN_FROM=<ref>` names it when neither exists. A clone without `refs/remotes/origin/main` fails in the first second (known-gaps-drift anchors the test baseline on public main): fetch it, or set `PUBLIC_MAIN_REF=<remote-tracking ref of public main>`.

| Step | What it does |
| --- | --- |
| retire | Decides what the port carried ahead of the pin and the target now holds, against the target, before the pin moves (`automation/pin/carried.py`, below). It stops on a conflict before editing anything. |
| move | `.upstream/pin` and every file derived from it (`make pin-sync`). |
| mirror, inventories, ledgers | `make upstream-mirror`; `make interface-proposals test-inventory-generate`; `make pin-ledgers PIN_FROM=<earlier>`. |
| vendor-pi-packs, vendor-sdk-ts-declarations, vendor-sdk-ts-pin-declarations, vendor-pi-dist, vendor-chord-plugins-node, vendor-chord-surfaces-client, model-catalogs, intl-tables | One step each, each recorded and resumable on its own: `make <step>`. The first packs the oracle's build of the pin (reproducible: the same sha512 twice) and writes the vendored-pack manifest; the second freezes the published release's declarations for the sdk-ts report (a no-op while the package version stays); the third regenerates `extensions/sdk-ts/pi-pin.d.ts` and the peer dependencies it imports from the oracle; the others are the vendored runtime, the chord copies, the model catalogs and the intl tables. |
| observation | The observation oracles (under the oracle Node, fetched when absent), `refresh-pi-test-sources.sh`, `make regenerate-alt-screen-oracle`. |
| gaps | `pin.py gaps --updates 2`: `make ledger-update` twice (the first binds, the second settles the pending rows that are not gaps), then `make ledger-check`. |
| generated | `go run ./test/parity/cmd/sdksurface` (`docs/extension-sdk-surface.md`); the outgoing pin's interface snapshots leave the index (`git rm --cached`; the gates track only the new pin and `coding.UpstreamReviewedVersion`, and the files stay on disk, ignored, so a rerun can still carry from them); `make generate`. |

**Provider data.** The first oracle build of a new commit has no frozen provider data, so Pi's own `hydrate-model-data` step (`catalog/generate.ts --data-only`) fetches the live model catalogs (`models.dev`, `openrouter.ai`, `ai-gateway.vercel.sh`) and the build freezes the result in `automation/pin/frozen/<commit>.provider-data.tgz` (with its `.sha256`); every later build of the commit unpacks that snapshot instead. That step therefore needs that network, and its output depends on the day it runs: commit the frozen files with the pin (the pin-follow run makes them ahead of the bump). The bump prints which data it used (the frozen snapshot's digest, or that it hydrated and the digest it froze) and keeps it in the state file (`provider_data`).

**Carried work.** Two things exist only until the pin reaches them. (1) The post-release backports, `automation/gen/pi-post-release-backports.mjs`: one `BEGIN backport <commit>` block per Pi commit, applied to the vendored runtime and to the oracle. The entries patch compiled output, and the oracle's `pi` bin runs the package's bundle (`dist/bundle`, which Pi's build makes of the compiled output), so the oracle build patches the installed compiled output and then has Pi's own bundler (`scripts/build-coding-agent-bundle.mjs`, with the esbuild of Pi's lock) make the bundle again from the patched output of the source build, which it then puts back as built. The build stops when the bundler does not first reproduce the installed bundle byte for byte from the unpatched output, so the rebuilt bundle differs from Pi's by the backports only. The stamp records the bundle's digest (`bundle_sha256`); `check-oracle` and the parity runner refuse an oracle whose `pi` runs another bundle, or one that carries backports in its compiled output only. Each entry is classified against the target's own installed package: *carried* (the target already holds the change: every after-text occurs once; the block is deleted), *pending* (the target is the build the entry was written for: it stays and must still apply) or *conflict* (neither: the bump stops with `backport <commit> neither applies to nor is carried by Pi <version>: <file>: entry text line N reads ..., the file's line M reads ...`, so the changed line is named without a diff; fix or drop the entry and rerun). A carried commit that also moves a dependency a Pi package pins exactly rides the same blocks as a `dependency(...)` entry (Pi f72f799a4: `@google/genai` 2.21.0 to 2.32.0 for pi-ai). The oracle installs the frozen closure with the lock entry of the carried version in place of the pinned one (version, archive and integrity as Pi's own `package-lock.json` holds them at the commit, so `npm ci` verifies the archive; the frozen file is not rewritten), stamps the digest of that lock as `closure_sha256`, and has Pi's bundler read the installed copy for the one run that makes its bundle; `check-oracle` prints that digest, the frozen one and each carried dependency. The entry is classified by the range the target's package pins (the pinned one: *pending*; the carried one: *carried*; another one: settled by GitHub's compare) and is deleted with the commit's blocks, and a build whose frozen closure no longer installs the version the entry replaces stops and says to delete it (`make pin-check` runs that check without a build). The oracle carries a commit's behaviour. What authors and inventories derive from the installed package (the published ranges of a `package.json`, the `.d.ts` declarations that `extensions/sdk-ts/pi-pin.d.ts` and the interface inventory are made of) stays the pin's until the re-pin, and each file a commit's blocks leave at the pin is named in them on a `// not carried: <file> (<what>): <reason>` line (`docs/parity/dependency-source-proof.md`, The oracle's carried dependency). So that a followed commit cannot leave the oracle behind unseen, `check-oracle` reads the sync ledgers of the commits past the pin (`test/parity/upstream-sync/v<pin>+*.toml`; `carried.oracle_ledger_problems`): a `ported` row of a file a block can patch (the compiled output of pi-ai, pi-coding-agent and pi-tui, the coding agent's docs and schemas) needs its block, a row of a package manifest or a lock needs `oracle = "carried: <backport id>"`, and either may say `oracle = "not carried: <reason>"` instead; a row that says neither fails `make parity-deps` and every parity run, naming the ledger and the file. A script with no block is a no-op that stays for the next release cycle: its digest is empty, so the oracle's key and stamp are those of a build without it. (2) The carried oracle: the tests of a Pi commit newer than the pin (`CARRIED_ORACLE_REF` in the Makefile), which run against that commit's build. GitHub's compare (`ahead` or `identical`) says whether the target contains it; then everything that exists only for that run is deleted: the Makefile block (`CARRIED_ORACLE_REF`, the two test lists, the targets `test-carried-oracles` and `test-carried-oracles-guard`), the CI step that runs the guard, the guard itself (`automation/pin/carried_guard.py` and its tests), the three skips of the oracle tests (`skipWithoutSuspendableWork` in `durable/interop`, `suspendableOraclePackages` in `durable/harness`, `namespaceOracleSkip` in `durable/codemode`: the pin's Pi has the work now, so those tests run in every test run), the reviewed decisions whose rationale starts "Carried ahead of the pin", the paragraph on the carried run below, and the commit's frozen files (kept when the target is that very commit: they are the new pin's). The tooling of a run at another Pi commit stays, because it serves any commit and is tested on its own: `pin.py override-tree` and `internal/pioracle` (`Packages`, `Project`, `OverrideTree`, `SkipAtPin`). The retirement is decided on the whole tree before a file is written: a piece that is not where the tool expects it stops the bump with `<file>: nothing to retire (<piece> is not there)` and no edit, and a tree without `CARRIED_ORACLE_REF` carries nothing (`carried oracle: none`). Carrying a later Pi commit after a retirement brings the Makefile block, the guard and the CI step back from the bump's commit, with the new `CARRIED_ORACLE_REF`, its test lists and a skip (`pioracle.SkipAtPin`) in each test the pin's Pi cannot answer; while one is carried, moving to a newer commit needs only `CARRIED_ORACLE_REF` and the frozen provider data and closure its first build writes. Without an answer from GitHub (no network, rate limit: set `GH_PUBLIC_TOKEN`) the step stops with one line; it never keeps or retires on a guess. Every decision and its evidence is stored in the state file (`decisions`) and printed in the summary: review it before committing.

The move step writes `.upstream/pin`, then regenerates everything derived from it (`make pin-sync`): `pigversion.go`, the `@earendil-works` versions in `extensions/sdk-ts` and `automation/images/ci-parity` (with their lock files when a version changed), the README badge and sentences, `docs/project/PROVENANCE.md` (the upstream pin and commit lines), `docs/site/docs/index.md`, the version fields of `known-gaps.toml`, `behavior-contracts.toml` and `async-contracts.toml`, and the credential-expiry probe. The later steps mirror the source, install the oracle and generate the unreviewed inventories. `make pin-check` (a prerequisite of `make port-map-drift`, so `make check` runs it) fails when a derived file differs from its derivation.

The `observation` step re-records the observation oracles with `automation/gen/regenerate-observation-oracles.sh`. Those fixtures are Node's own microtask and macrotask order for the Web Streams and `Readable` constructs Pi's providers read their sockets through, which the Go models (`ai/node_web_stream.go`, `ai/node_readable.go`) replay, so that PiG's consumers run in the same tick as Pi's. They are recorded under Node `v24.19.0` (`ai/testdata/node-microtasks/oracle-node-version`) and not under the qualified Node (`.node-version`, 24.22.x) because 24.22.x orders one construct differently (`values-buffered/bytes`) and lets separate socket writes reach the consumer in one macrotask: the goldens and the models are the 24.14.1 through 24.21.0 order, and the 24.22.x order is not recorded or tested (the live comparison skips under any other Node), so the product is compared with the older Node's ordering only. When the `node` on `PATH` is not the oracle Node the script runs `pin.py oracle-node`, which downloads nodejs.org's tarball for the platform (linux or darwin, x64 or arm64), checks its sha256 against the release's `SHASUMS256.txt`, unpacks it into the cache and checks `node --version`; a cached copy needs no request. The cache is `$PIG_ORACLE_NODE_CACHE`, else `$XDG_CACHE_HOME/pig/node`, else `~/.cache/pig/node`. With no network the script stops with one line naming the URL.

`make pin-ledgers` (run by `make pin-bump`, or by hand under `PI_UPSTREAM_REF=<ref>`; `PIN_FROM=<ref>` names the earlier pin, default the committed one) generates the new pin's three single-file ledgers into `test/parity/pin-ledgers/v<version>/` and the interface delta manifest and custom-factory draft: `async-contracts.toml` keeps the earlier pin's reviewed row for every source file that is byte-identical in the two mirrors and is pending for the rest (`asynccheck -generate -previous`), and `behavior-contracts.toml` and `known-gaps.toml` are copied with their version field set (a contract whose source changed fails its drift gate until the batch that ports it reviews it). It skips a file that already exists; `--force` regenerates.

The three single-file ledgers above are archived per pin under `test/parity/pin-ledgers/v<version>/` when a bump leaves a pin, and restored when a bump returns to it, so moving the pin back reproduces the earlier pin's ledgers. The working tree tracks interface snapshots only for the committed pin and `coding.UpstreamReviewedVersion`, the baseline used by the semantic delta and behavior-input gates. `pin.py sync` derives their `.gitignore` exceptions from those two settings. Other interface snapshots remain local during `pin-follow`. After carrying and reviewing a new pin's ledgers, remove the outgoing pin's interface snapshots with `git rm` only when that version is neither the new pin nor `coding.UpstreamReviewedVersion`. Retain the reviewed baseline's snapshots. `make pin-check` rejects tracked snapshots outside the active pin and reviewed baseline. Restore an earlier pin's reviewed interface snapshots from its Git commit before moving back to that pin. Keep the versioned `upstream-sync` records and archived single-file ledgers. `PI_UPSTREAM_REF` alone does not swap the three single-file ledgers: a gate that reads them reports the version mismatch until the pin is bumped.

A release leap or commit move then follows the upgrade workflow in `piglets/porter/skills/pig-porter/SKILL.md`: reviewed mappings, ported behavior, `make generate`.

## The vendored durable packages

`@earendil-works/pi-durable`, `chord` and the packages they run on (`pi-ai`, `pi-codemode`, `pi-schema`, `pi-telemetry`) are what `durable/core/host/cf`, `durable/interop` and `bench/k8s/image/pi-durable` install. npm publishes releases, not commits, so a commit pin's packages do not exist on the registry, and the release a `package.json` names can lack what the pin has (suspendable work, chord events). `third_party/pi-packs/` therefore holds the `npm pack` outputs of the pinned source build, which the three projects install through `file:` dependencies and overrides; their locks carry each pack's sha512, so `npm ci` refuses any other bytes and needs no registry for Pi's packages. `manifest.json` records the commit, and each pack's name, version, licence field and integrity; `LICENSE` is Pi's LICENSE at the pinned commit (see `THIRD_PARTY_NOTICES.md`).

- `make pin-bump` regenerates them (`make vendor-pi-packs`, after the oracle build): it packs the build, writes the manifest and `LICENSE`, points the three projects' `package.json` at the packs and refreshes their locks. `npm pack` of one build is reproducible (the same sha512 on two runs and on Node 22 and 24), and `pack()` in `automation/pin/oracle.py` normalises file modes, so the bytes do not depend on the machine.
- `make pin-check` (offline) runs `pin.py check-vendored`: the manifest is for the pin's commit, every pack has its recorded sha512, every lock entry of a Pi package in the three projects resolves to that file with that sha512 and never to a registry URL, no `package.json` of the tree outside the exemptions below names a Pi package by a version, and the pi-telemetry copy under `chord/nextnode/plugins/node/pi` equals the pack's shipped files. `make pin-check-vendored-rebuild` also packs the pinned build again and compares tar members and gzip bytes.
- `make durable-interop-deps` and `make durable-core-host-deps` are plain `npm ci`s of the locks; the Cloudflare host's `package.json` installs the vendored pinned build (a user who installs it from a checkout gets the pin's Pi packages, not 1.5.2 from npm).
- A run at another Pi commit (the oracle tests of Pi work the Go port carries ahead of the pin) needs that commit's packages and must not change what the pin's gates read. `PI_UPSTREAM_REF=<commit> python3 automation/pin/pin.py override-tree` builds a tree under the commit's entry of the build store (`durable-<digest>`, one per source build and interop lock) and prints its path: `packages` (a link to the packages of the commit's source build), `third_party/pi-packs` (the packs of that build, made as `make vendor-pi-packs` makes the pin's) and `durable/interop` (a copy of the repository's manifest and lock pointed at those packs and installed with `npm ci`). The tree is built in a scratch directory and gets its name by one rename, so a build that stops leaves no tree. The run hands the path to the tests as `PIG_PI_OVERRIDE_TREE`: `internal/pioracle` (`Packages`, `Project`) gives the oracle tests of `durable/harness`, `durable/codemode` and `durable/interop` that tree in such a run and the repository's own Pi (`.upstream/current`, `durable/interop`) in every other, and a test of carried work, which skips at the pin, fails there when the tree lacks the work. Nothing in the repository is written or linked, so `.upstream/current`, the oracle link and `durable/interop/node_modules` are the pin's whether the run ends, fails or is killed, and the next gate reads the pin's Pi without a `make upstream-mirror` in between. No packs of a carried commit are committed; its provider data and dependency closure are frozen in `automation/pin/frozen/` by its first oracle build, as any commit's are.

Still naming a Pi release on purpose, and not covered by the packs: the `extensions/sdk-ts` peer dependency (the published release an extension runs on outside PiG; the author type-checks against the pin's `pi-pin.d.ts`), the CI parity image (it builds the pinned commit from source, or installs the published release of a tag pin), `bench/k8s/image/pi-agent` (Pi's published install pair, a measuring tool of the competitor's side: a commit pin installs the frozen closure and the packs `install-oracle` built), the release locks under `bench/evals/locks`, the corpus locks of third-party extensions, the vendored `pi-dist` and chord sources (regenerated by their own `vendor-*` targets), and the generated provenance comments `// Upstream: @earendil-works/pi-ai 1.5.2` of the model catalogs.

## The sdk-ts declarations: the pin's bundle and the report against the release

`extensions/sdk-ts` keeps the peer dependency `@earendil-works/pi-coding-agent` at the published `UpstreamPackageVersion`, and an author type-checks against the pin, which is what PiG runs. `extensions/sdk-ts/pi-pin.d.ts` is generated from the oracle (the pinned source build in `node_modules`) by `scripts/pin-bundle.mjs`: one ambient module per specifier that the `exports` maps of `pi-coding-agent`, `pi-ai`, `pi-tui` and `pi-agent-core` expose, one per file of a package without a map, and one under a private `pi-pin:` specifier per further declaration file or model catalog JSON those reach. A block is its file's text with the `declare` modifiers and the source map comment removed and the specifiers of the four packages' files replaced by block names; imports of other packages stay as written. `index.d.ts` references the bundle, and the compiler looks an ambient module up before the installed package, so a project that imports the types package sees the pin's declarations in place of the release's without any `tsconfig` entry.

`make test-sdk-ts` gates the bundle. `scripts/pin-bundle.test.mjs` reads the bundle back as a build and requires `compare` (the checker comparison of `scripts/declarations.mjs`) to find no difference from the pinned build, requires a block for every exposed specifier, regenerates the bundle and requires the committed bytes. `scripts/author-view.test.mjs` compiles an author's project (the release's declarations from the snapshot, this package as packed, the release's other dependencies hoisted beside them) with `moduleResolution` `Node16` and `Bundler`, with and without `skipLibCheck`: an extension that uses the PiG-only declarations compiles, a member in neither build is refused, every exposed specifier is declared by the bundle, every member the pin adds to the release is in the author's view, and a model catalog has the type the compiler gives the pinned build's JSON file. `make pin-check` requires the bundle's header to name the pinned commit, without an installed oracle. `make vendor-sdk-ts-pin-declarations` (run by `make pin-bump` after `vendor-sdk-ts-declarations`) regenerates the bundle.

The differences between the pin and the release are a report, not a failure: `scripts/check-declaration-drift.test.mjs` compares the oracle with `testdata/published-<version>.declarations.json.gz`, the published packages' declaration files (checksum in the `.sha256` beside it; the test reads no network), and prints each exported declaration that differs as `<package>/<file>#<declaration> (<kind>) changed: member <name> (<kind>) added`, and each difference elsewhere in the declaration files as `not exported, differs`. The header of `pi-pin.d.ts` carries the same list of exported differences, so an author sees which members exist only in PiG and not in a runtime of the published release. The snapshot holds declaration files only: the model catalogs' JSON is the pin's in the bundle and is not compared. `make vendor-sdk-ts-declarations` (run by `make pin-bump`) writes the snapshot from `npm pack` of the locked release, verified against `package-lock.json`'s integrity, and does nothing while the snapshot is of the peer version.

The bundle's imports of other packages (`typebox`, `@earendil-works/pi-mcp`, the provider SDKs) resolve from the types package's own directory, so `package.json` declares each as a required peer dependency at the range the importing Pi package declares. `make vendor-sdk-ts-pin-declarations` writes that block with the bundle, and `package-lock.json`'s copy of it through `npm install --package-lock-only`; `scripts/pin-bundle.test.mjs` fails when the bundle imports a package that is no peer, when a peer is declared that the bundle does not import, and when a range is not Pi's. `extensions/sdk-ts/.npmrc` sets `legacy-peer-deps`, so those peers stay out of the lock's tree, which remains the published install of Pi that `freeze-closure --from-published-lock` reads; the same test requires the lock to hold every required peer of the tree's own packages. `scripts/author-view.test.mjs` compiles the author's project, `typecheck.ts` included, in three layouts built by hand: hoisted as npm installs it, isolated as pnpm does (the types package beside its declared peers only), and a link to the source folder with `preserveSymlinks`. In each, a type that comes through another package (`McpServerConfig`'s `url`, from `@earendil-works/pi-mcp`) must refuse a number. The dev tree's own `node_modules` is the oracle, not an install of this package, so nothing is compiled there.
