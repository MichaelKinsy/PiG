## Real gaps found and fixed (tests first)

- **`isProtocolJSON` 512-deep guard** (`protocol/messages.go`). Pi's `isJsonValue` has no depth limit (`chord/src/json.ts:78-120`), so a request whose call nests deeper than 64 fails in `encodeCbor` with `Unable to encode client protocol message: CBOR nesting depth exceeds configured limit of 64` at every depth (Pi 1.0.4, depths 64 to 5000). The Go guard returned `Invalid client protocol message` from depth 513 on. Red: `TestEncodeMessageDeepCallFailsInCborLikePi` (depths 513, 600 and 5000). The guard is removed. The wire cannot carry such a value (CBOR decode is capped at depth 512), so only in-process callers saw the difference.

## CI group 4: `TestServerWireDifferential/go_server`, "hello then hello"

Triage `ci-042-triage.md` group 4 reported that the Go server replied with a hello before `hello_error` while Node sent only the error. Root cause: the harness sleeps 40 ms between writes and assumes every server completes its first handshake inside that window. On a loaded runner the Node server does not; the second hello then arrives while Node is still handshaking, `failProtocol` runs first, and `finishHandshake` sees `state.stage !== "handshaking"` after `attachClient` and sends no hello (`server.ts:239-245,264-285`). The Go server already behaves the same way in that ordering. The server is not wrong, the oracle comparison was timing dependent.

- Reproduced (red): with the Node server's `serverServices.attachClient` delayed by 150 ms and the old harness, three cases differ (`hello then hello`, `hello then garbage`, `hello then zero length frame`), each with the CI symptom (Go sends `hello` first, Node only the error). The delay was a temporary edit to `node-server.mjs` and is not committed.
- Fix (`interop/server_wire_test.go`): a case whose first write is a complete hello now waits for the server's reply before the next write (`awaitFirstReply`). With the same slow Node, the differential passes (712 of 712).
- Guard for the ordering the CI run did not reach: `routing/TestSecondHelloDuringHandshakeSendsOnlyTheError` holds `AttachClient` open, sends the second hello, releases, and asserts a single `hello_error` (`invalid_request`, "hello may only be sent as the first message"), a closed connection and one attachment release.

## Review additions (rev-gap-behavior-remote)

The review's own mutations found behaviour the registered tests did not pin. Tests were added, each mutation-proven (`go test -overlay`), and registered on the same records:

- `session-router.ts`: `TestSessionRouterAttachmentLifecycle` pins same-Session re-attach (`:160-195`), the switch release without a published detach, `removeSession` release and Harness close (`:72-89`), disconnect without publish (`:91-101`) and close releasing attachments (`:108-140`). Seven mutations that survived the whole routing package now fail.
- `server.ts`: `TestServerHoldsSubscriptionUpdatesUntilTheSnapshotResponse` (`:338-344`, `:375-382`) and `TestServerClosesTheConnectionWhenAHeldUpdateFailsAfterTheResponse` (`:383-401`); `TestServerProtocolProcessesAHelloAndRequestCoalescedInOneByteChunk` is now named because it is the only test that fails when handshake-pending messages are dropped.
- `unix.ts` (client): `TestProbeUnixServerOmitsOnlyTheEndpointsPiOmits` now covers the version `hello_error`, the close without a cause and a non-version `hello_error` (`:263-276`). Its comment had claimed the first two before.
- `TestSecondHelloDuringHandshakeSendsOnlyTheError` no longer sleeps for 200 ms. It reads the `hello_error` and the close while `AttachClient` is still held, then asserts that the server reports no error.
- `TestClientSubscriptionHoldsHydratedUpdatesUntilStart` no longer sleeps. It checks the queue right after the synchronous dispatch, and `Dispose` joins delivery before the order is checked.

## Method notes

- Every expected value in `messages_schema_test.go` was run through Pi's own `parseClientMessage`/`parseServerMessage` first (all 102 agree). Expected error messages and wire bytes in the CBOR, framing and codec tests come from the Pi sources, and the encode/decode outputs that were not obvious (key order, 17 MiB frame length, depth messages) were taken from Pi 1.0.4 itself.
- A mutation counts only if it compiles, fails a test named in the record, and the baseline passes. Mutations whose failure is a test timeout or a process abort are recorded as `test timeout`/`test abort`.
