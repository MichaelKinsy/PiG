# gap-behavior-durable-env: behavioural evidence for the `durable` and `env` PORT_MAP rows

Slice `gap-behavior-durable-env` (Pi 1.0.4, base `202dc09b1`). The 14-package accounting showed 205 ported rows without behavioural evidence; 66 of them are in `packages/durable` (61 rows) and `packages/env` (5 rows). Each row below is closed by records in `test/parity/unit-evidence/gap-behavior-durable-env.json`: the named Go tests assert the upstream behaviour (almost all are ports of upstream `packages/{durable,env}/test` cases or of the upstream `test/examples` scripts), and each recorded mutation compiles, fails those tests and leaves the baseline green. PORT_MAP.md and coverage.md are regenerated by the integrator.

## How the rows were closed

1. For every row, mutation candidates were generated mechanically in the Go file(s) PORT_MAP maps to the upstream file: a comparison flipped (`==`/`!=`, `<`/`<=`), a constant changed by one, a boolean inverted, an `if !x` negated, a message literal extended. A candidate counted only if the mutated file compiled (`go test -overlay`, no `-cover`) and a test of the touched package or of its dependents (`durable/harness`, `durable/session`, `durable/storage/...`, `durable/tools`, `durable/env/node`, `durable/examples`, `env`) failed. A mutation that survived is not evidence; it is in the gaps list below.
2. Each kept mutation was re-run in isolation (`go test -run '^(<tests>)$'`): the baseline passes, the mutated build fails at least one of the named tests. A kill that appeared only inside a full-package run (ten cases in three repeated runs, seven of them `TestExample25Compaction`, which also failed at baseline once under heavy machine load; the others are `TestExample23SubagentBackground`, `TestNodeExecutionEnvConformance` and `TestOwnedConversationsFromTools`) was discarded. `TestExample25Compaction` is not cited as evidence anywhere.
3. The named tests were run `-race -count=3` as one set per package: all pass.
4. Where a row maps to several Go files (for example `env/node.ts`, `edit-diff.ts`), each file got its own mutations.

Upstream references are `file:line` of the upstream definition that matches the mutated Go function (`function name`, method or class declaration) or of a message literal in the mutated line; when the Go symbol has no same-named upstream definition the reference is the whole file `file:1-N`. The tests' upstream counterparts are the `packages/{durable,env}/test/*.ts` file named in the Go test's `Ports` or `upstream:` comment, or the `it`/`test` title with the same words (cited with its line).

## Real gaps found and closed, tests first

The generated mutations that survived the existing tests are the missing evidence. Each is closed by a new test that pins the upstream behaviour:

- `durable/errors.go` (`errors.ts:4-28`): within `./durable` nothing asserted `ConversationBusy`'s message (the harness test `TestGeneration` asserts it contains `is busy`) or `StorageRejected`'s cause chain (`ReadAfterWrite`'s message is asserted by the ported `TestSessionTransactionTables`; the new test also pins it where it is defined). New `TestDurableErrorMessagesMatchPi` and `TestStorageRejectedKeepsItsMessageAndCause` (`durable/errors_test.go`). Mutations that survived the `./durable` tests before: `Conversation %d is busy` -> `is not busy` (killed only by the harness `TestGeneration`); `Unwrap` returning nil.
- `durable/tools/index.go` (`tools/index.ts:21-25`): no test looked at `CodingTools` itself (the tests install the tools one by one). New `TestCodingToolsAreReadWriteEditAndBashInOrder` (`durable/tools/index_test.go`): name `coding-tools`, tools `read`, `write`, `edit`, `bash` in that order. Survived before: dropping `edit`, renaming the extension, swapping the order.
- `durable/harness/types.go` and `scheduler.go` (`harness/types.ts:467-476`): the tests compared `TaskInspectionKind` constants with themselves, so a changed literal passed. New `TestTaskInspectionLiteralsMatchPi` (`durable/harness/task_inspection_literals_test.go`) pins the five kinds and the three blocked reasons to Pi's literal values.
- `durable/storage/sqlite/database.go` (`database.ts`) holds only types; its evidence is the compile-time contract (see the row note).

No production code needed a fix: every surviving mutation was a missing assertion, not a behaviour difference. No numbered divergence was added. The review below found three production differences in `env` that the lane's mutations did not reach.

## Review (rev-gap-behavior-durable-env)

Semantic mutations (beyond the lane's comparison flips) in the rows with the weakest evidence found these survivors; each is now closed by a test that failed first:

- `env/connection.go` (`connection.ts:255-305`, `#start`): the hello was sent after the read loop and the exit reaper had started, and a buffered exit was preferred over the hello's failure. Pi sends the hello in the tick that spawns the daemon, and a corrupt frame rejects it before the killed daemon's `exit` fires. Under CPU load a corrupt frame during the hello was reported as `pi-env exited with code null before it was ready` or `pi-env connection lost` (45 of 60 runs). Fixed: the hello is pending before any goroutine starts, and the exit reaper tears down with the exit failure while the hello is outstanding, so the first teardown decides. Regression: `TestConnectionRejectsAFrameLengthOutsideItsBounds`.
- `env/connection.go` (`connection.ts:338`): pre-sync noise was trimmed with Go's `strings.TrimSpace`; Pi uses `String.prototype.trim` (removes U+FEFF, keeps U+0085). Fixed with `jsstring.Trim`. Regression: `TestConnectionReportsShellNoiseBeforeTheSyncLineThroughOnLog` (JavaScript whitespace case). The MAX_FRAME bound, the onLog call and the 1 MiB noise cut had no assertion: `TestConnectionRejectsAFrameLengthOutsideItsBounds`, `TestConnectionFindsASyncLineSplitAcrossTheNoiseCut`.
- `env/watch.go` (`watch.ts:107-108`): an `error` event without a message produced an empty message; Pi's `String(event.message)` is `undefined`. Fixed with `templateString`. Regression: `TestRemoteWatcherReportsTheDaemonsWatchErrors`. The `ready`/`change` mode handling and the permission_denied mapping had no assertion: `TestRemoteWatcherTakesItsModeFromTheDaemonsEvents`.
- `durable/tools/path_utils.go` (`path-utils.ts:20`): the case-insensitive `/ (AM|PM)\./gi` survived; a lowercase `am` case was added to `TestReadFindsTheMacOSVariantOfAMissingName`.
- `durable/tools/file-mutation-queue.ts`: the cited tests kill only error-path flips and the plain serialization; the canonical-parent key is pinned by the serialization tests now added to the evidence.

Survivors kept as notes, not gaps: `durable/storage/sqlite/node/node.go` rollback on a panicking callback (Go-only path; Pi has no panic), `env/watch.go` resetting the mode to native on a later `ready` (reachable only after a reconnect), and `durable/tools/path_utils.go` dropping the duplicate NFD variant (equivalent: the NFD-with-apostrophe variant covers it).

## Row notes

- `storage/sqlite/database.ts`: type-only (`SqliteExecutor`, `SqliteDatabase`). Compilation is the contract: a required method added to the Go interface breaks every adapter and test double (`controlledSettlementDatabase`, `NodeSqliteDatabase`), so `TestPortableSQLiteFacadeSettlement` (settlement, rollback and queueing through the facade), `TestSqliteStorageConformance` and `TestDurableSQLiteMigrations` do not build. This is the only record whose failure is a build failure.
- `testing/assertions.ts`, `testing/runner.ts`, `testing/types.ts`: vitest adapters; the Go counterpart is `durable/durabletest`, exercised by the storage and environment conformance suites. The mutations are in `durabletest.go`/`env_conformance.go` and fail the conformance tests that call them. `testing/storage-benchmark.ts` is evidenced by `TestStorageBenchmarkExpectations`; `testing/storage-conformance.ts` and `testing/env-conformance.ts` by the memory, JSONL, SQLite and Node-environment conformance tests.
- `durable/interop` (cross-runtime comparison with Node Pi Durable) is not used as evidence: it needs `make durable-interop-deps` and its tests fail on a host without the pinned Node packages.
- `harness/*.ts` rows are mostly evidenced by `durable/harness` tests (ports of `harness-*.test.ts`); rows without a dedicated Go test file use the ported `test/examples` scripts under `durable/examples` (named in the reference).
