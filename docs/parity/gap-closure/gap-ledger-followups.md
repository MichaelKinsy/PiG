## 3. Extension-context production use

Closed without a redesign of the Host dispatch (lead ruling: only an observable difference justifies it). Measured with a type-checked scan of non-test code (calls resolved to the method object): `Context.Abort`, `Compact`, `GetContextUsage`, `GetSystemPrompt`, `HasPendingMessages`, `IsIdle`, `ScopedModels`, `Shutdown`, `Signal`, `CommandContext.Fork`, `GetSystemPromptOptions`, `NavigateTree`, `NewSession`, `Reload`, `SwitchSession`, `WaitForIdle`, `UIContext.OnTerminalInput` and `SetWidget` have no production caller, because production extensions run out of process and `UIBridge` answers their host calls from `HostCallbacks`. Probe of whether any extension-visible behaviour differs from Pi's runner on those paths:

- Stale context (`runner.ts:679-690`, `assertActive` on every member): the Host rejects every extension-to-host call once invalidated (`host_calls.go:293`), so each host-call-backed member (all the ones above) returns the stale message. The Node runtime bundles Pi's own runner and is covered by `TestNodeContextMembersThrowOnceTheRuntimeIsStale`. Equivalent.
- Unbound defaults (`runner.ts:368-388`): `isIdle` true, `hasPendingMessages` false, `getContextUsage` none, `getSystemPrompt` empty, `abort`/`shutdown`/`compact` no-ops match in the bridge. `newSession`, `fork`, `navigateTree`, `switchSession` and `reload` differ when unbound (Pi: `{cancelled:false}` and a resolved no-op; bridge: an `unsupported` error), as does `getSystemPromptOptions` (Pi: `{cwd}`; bridge: empty). The Session binds every one of these in every mode before any extension code runs (`cmd/pig/session_extension_actions.go`, `Session.ExtensionCommandActions`), so no extension can observe it. Not reachable; no change.
- **One observable difference found, and closed (lead ruling: option 1).** Pi throws the stale message from `ctx.cwd`, `mode`, `hasUI` and `model` after a session replacement or reload (`runner.ts:571-600`). The Host sends `NotifyInvalidate` to each extension for this, but only the Node runtime handled it; the Go, Python and Rust SDKs kept answering from cached state (the red probe, now `TestLocalContextMembersPanicWithTheStaleMessageAfterInvalidate`). Each SDK now records the first invalidate message and raises it from those members: Go panics with it (`Cwd`, `Mode`, `HasUI`, `Model`, `ModelProvider`, `ModelQualified`; no signature change), Rust panics, Python raises `RuntimeError`; the handler dispatcher reports it as the handler's error. A replacement (withSession) context is not stale. The Rust `handler_panic` response now carries the panic text, which the stale message needs to reach the caller. Tests: `TestStaleContextLocalMembersRaiseTheStaleMessageInEverySDK` (conformance: Go, Node, Rust, Python; isolated, packed and fused; the active run reports a working directory, a value no SDK's fallback returns), `TestFirstInvalidateMessageWins` / `test_first_invalidate_message_wins`, `TestReplacementContextIsNotStaleAfterInvalidate`, and the Rust and Python unit tests, each red before the change. The matrix row is in `docs/extension-api-parity.md`.
