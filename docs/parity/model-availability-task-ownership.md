# Model availability task ownership

Pi 0.87.1 `packages/coding-agent/src/core/model-runtime.ts:286-299,323-343` rejects availability `Promise.all` on the first failure. Other promises continue until they settle or their signal is cancelled. Success requires every branch. The shared snapshot and visible error use the existing full/provider generation checks.

Pi's provider-refresh catch handlers add failures to the result map as they settle (`model-runtime.ts:722-731`). The outer refresh still waits for all selected providers because those handlers catch their individual failures.

## Go lifetime

One `modelTaskOwner` belongs to the Services-owned registry. `ModelRuntime.startBackground` and all availability fan-outs use that owner. The registry's auth-check and available-model fan-outs share it, so a nested failure cannot remain hidden behind another provider.

Each fan-out has a coordinator that publishes its first rejection and then drains every child result and joins every child. The caller stops waiting on rejection or cancellation. The coordinator remains admitted until it drains. A late sibling does not republish snapshot or error state.

`Services.Close()` stops admission, cancels the Services lifetime and waits for all admitted coordinators and background jobs. `ModelRuntime.Close()` uses the same owner for standalone `CreateModelRuntime` callers. Storage supplied by the caller remains caller-owned. A Session Runtime created with supplied Services does not close them. Call Close outside model callbacks and after active Sessions finish.

The CLI closes Services before extension transports and profiles at process exit. RPC closes Services only when it creates them. RPC background catalog work uses the same owner and keeps its original caller cancellation and timeout.

## Cancellation context

A live parent signal has one shared cancellation binding, not one retained child per operation. Request values are supplied separately for each call. Cancellation causes and deadlines remain visible. A completed operation does not cancel a retained `Done` observer. Parent cancellation removes its binding; Services closure cancels and clears remaining bindings.

This is a native lifetime mechanism for the existing Promise behavior. It does not create another model registry or another snapshot.

## Registration refresh

Pi `registerNativeProvider`, `registerProvider` and `unregisterProvider` (`model-runtime.ts:744-797`) return synchronously. Each one first republishes the snapshot through `updateModelSnapshot` (`model-runtime.ts:277-284`). `registerProvider` also adds provisional configured auth when the provider has a stored credential or configured request auth, and it keeps a real check result (`model-runtime.ts:768-787`). Each call then starts `void this.refresh({ allowNetwork: false })`.

That refresh is a microtask continuation on the single JavaScript thread. It cannot pass its first await (`ModelConfig.load`, `model-runtime.ts:702`) before the registering caller yields. Its later stages keep event-loop FIFO order, and it never runs concurrently with provider callbacks or host code. In Pi's request path the request's own auth callbacks run before the refresh's callbacks: after two awaited stream calls the scenario-23 counter is 2, and the refresh's callbacks land afterward.

The Go mapping has four parts:

1. **Synchronous part.** The committing registry calls the Services-bound projection after it releases its locks and before it notifies change listeners. The projection performs no I/O and calls no provider callback. A projection mutex keeps the newest committed catalog last. `RegisterNativeProvider` from the extension host performs no authentication and no catalog refresh of its own.
2. **Deferred refresh.** The registry records that a refresh is pending. Nothing runs and no goroutine starts. Registrations that queue before a pass starts share one pass: Pi's earlier passes are superseded by the newest through its availability generations and provider supersession, so the newest pass reaches the same state (their extra provider-callback calls are the only difference). A registration that queues while a pass runs is never dropped: the next yield starts its own pass, which runs concurrently with the running one and supersedes it, as Pi's separate `void this.refresh` calls do.
3. **Yield.** The pass starts on the Services task owner inside the first awaited model-runtime call: `Refresh`, `ExtensionRefresh`, the catalog refresh coordinator, `GetAvailable`, `CheckAuth`, `Login` and `Logout`. It starts before the caller's own operation, as Pi's earlier-queued continuation runs first. Only a caller whose operation covers every provider (an unscoped `Refresh`, `GetAvailable`, the catalog coordinator) waits for the pass. Pi launches the registration refresh unawaited, and a provider-scoped refresh, availability or auth call selects only its own providers (`models.ts:398-449`), so a scoped caller (`Providers` set, `GetAvailable(id)`, `CheckAuth`, `Login`, `Logout`) starts the pass and does not wait for another provider's callbacks. A registered provider whose auth check blocks therefore cannot hold an unrelated provider's scoped call until its deadline. A scoped `Refresh` or `ExtensionRefresh`, `Login` and `Logout` refresh their own providers, so they cover those providers' queued registrations instead of starting a pass beside them: a pass started beside them would begin the same provider's refresh after theirs and supersede it (`models.ts` `beginProviderRefresh`), where Pi's earlier-queued pass begins first. A covering caller whose refresh is aborted, or whose login or logout never reaches local synchronization, returns the covered providers to the queue and starts it, because Pi's registration refresh has no signal and still runs. A provider request (`Stream`, `StreamSimple`, request auth) is not a yield. A caller that finds nothing queued returns at once, even while a pass runs, so a provider callback that calls back into the runtime cannot deadlock the pass. The pass never yields to itself.
4. **Extension host registrations.** A registration that arrives through an extension host returns to its extension when the host callback returns; that return is the registering caller's turn ending in Pi. After startup, `cmd/pig` binds the host callbacks so each one starts the queued pass on the Services task group and does not wait for it. A native Provider that an extension registers after startup (a command or event handler, or a crash-restart re-registration) therefore becomes available to the synchronous readers (RPC `get_available_models`, `/model`, the settings selector) without another model-runtime call. Provider callbacks of extension providers run over the extension's connection and never inside a provider request. An interactive `/reload` holds the queued refresh (`HoldRegistrationRefresh`) while `host.Reload` loads every extension, and releasing the last hold starts it, as Pi flushes the reloaded factories' registrations after every factory has finished (`bindCore`). An awaited yield ignores a hold.

The pass has no signal in Pi. Cancelling the yielding caller stops only its wait. `Services.Close()` cancels and drains the pass. A pass failure is recorded for `GetError` and is never returned to the registering or yielding caller. Listeners hear about state the pass changed on goroutines the listener owns, so `Services.Close()` never waits for listener code.

A full refresh reloads `models.json`, recomposes every native provider, and a provider-scoped refresh recomposes the selected ones, whether or not `models.json` changed and even when its own signal is already aborted: `ModelConfig.load` takes no signal, and the signal reaches only the catalog refresh that follows (`model-runtime.ts:270-275,700-712`). An aborted refresh publishes the reloaded configuration and reports `aborted`. Each recomposition supersedes that provider's in-flight refresh, so a pass in flight cannot publish after a newer full refresh.

Pi assigns `availabilityRefreshSeq` when `queueAvailabilityRefresh` starts (`model-runtime.ts:317-330`), after the refresh's awaited catalog phase. The pass reuses the existing generation checks.

Startup: Pi `createAgentSessionServices` flushes the extension provider registrations and then awaits `modelRuntime.refresh({ allowNetwork: false })` (`agent-session-services.ts:158-182`) before `main.ts` resolves the startup model or answers `--list-models`. `cmd/pig/main.go` makes the same awaited `ModelRuntime.Refresh` call after it loads the final extension set. Until that call, a host registration only queues its pass, as Pi queues the registrations of the extensions it is still loading, so no Provider callback runs before every extension factory has finished. That call yields to the queued pass, so a native Provider registered at startup is authenticated before startup model resolution, `--list-models` and the first RPC command.

Divergence [D84](DIVERGENCES.md#d84-direct-go-provider-registration-refreshes-availability-on-the-next-awaited-call) (owner-approved 2026-09-29): a Go caller that registers directly on the registry or the Model Runtime, outside an extension host, and never makes an awaited model-runtime call sees only the synchronous projection. Pi's unawaited refresh would land on the event loop's next turn. Go has no implicit yield, and a background goroutine would run provider callbacks during the caller's own request sequence, which is not Pi's order: scenario 23 prints Pi's `0,2` only because no callback runs inside the request sequence. Extension-host registrations match Pi.
