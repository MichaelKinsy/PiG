# Chord v2 plugins: the build in Go, the evaluation in a Node subprocess

Status: owner decision 2026-11-01 for `chord/nextnode/plugins` (Pi `b556cfe5`, `packages/chord/src/next-node/plugins`).
Replaces the `Builder` and `Evaluator` seams of the first port, whose only implementations were test fakes.

## 1. Split

| Pi file | Go form |
|---|---|
| `discover.ts`, `install.ts`, `watcher.ts`, `plugins.ts` | Go, as ported (`plugins_*.go`). |
| `build.ts` | Go, 1:1 on esbuild's Go API (`github.com/evanw/esbuild/pkg/api`, Pi's pin `0.28.2`): every option `buildFacet` passes, `ImportRules` as an `api.Plugin`, `freeGlobals` over the inline source map (VLQ decoder with Node `SourceMap.findEntry` semantics), `describe`. No `Builder` interface: `BuildFacet` is the build. |
| `evaluate.ts`, `stack.ts`, `runtime.ts` | Pi's own TypeScript, vendored verbatim and run by Node (type stripping, no transpile) in a subprocess. Go has no `vm`, and AGENTS.md forbids an embedded JavaScript runtime. |
| (none) | `node/host.mjs`, the thin driver of that subprocess, and `plugins_node*.go`, its Go client (`PluginRuntime`, `NodeHost`). No Pi counterpart: Pi's workers (`next-node/workers/main.ts`) fork the same shape over Node IPC. |

The in-process `PluginRuntime`/`Evaluator` seams, `Plugins.Load/Reload` on a Go `host.Host` and `HostPackages map[string]any` are deleted: a facet is JavaScript, so it can only be loaded into a JavaScript host. That host is Pi's own chord host (`next/host`), running in the subprocess and linked to the Go host.

## 2. Process model

One Node process per `NodeHost` (Pi: one worker per host). It runs, from one extracted tree (section 7):

- `node/host.mjs`: parses its one argument (the socket address), connects, makes `createHost`, `createPluginRuntime` and the two channels below, `connect`s the link to its parent as Pi's forked worker does (`next-node/workers/main.ts`), and serves the control requests.
- Pi's `next/host` (the chord host), `next-node/plugins/runtime.ts` (per-host loaded facets, complete-set load and reload, the `adopt` rule after an aborted commit), `evaluate.ts` (`vm.Script` under `/chord-plugins/<plugin>/<file>?<digest>`, `require` for host packages, `pluginFile`, `chord.external` packages) and `stack.ts` (`mapStack`, source maps kept while a facet lives). Nothing of these is translated.

The host's plain-value options are the app's (`RuntimeLoad`): `heartbeat`, `closeTimeout`, `readyTimeout` and `compression` (`createHost({ compression: nodeCompression })`, Pi's `next-node/compression.ts` vendored; the Go host the link is attached to compresses its own parts when it is created with `host.HostOptions.Compression: nextnode.NodeCompression`, a compressor being a host's, not a link's). `telemetry`, `principalKey` and `revokedBy` are the app's Go callbacks the Node host calls (`RuntimeLoad.Telemetry`, `PrincipalKey`, `RevokedBy`; section 10.1 and 10.6): the telemetry as ordered data events replayed into the adapter, the other two as synchronous calls. `GoPackages` are the app's Go functions and values offered to the plugins as host packages (10.4).

Host packages (Pi: `HostPackages`, this process's module instances) are modules imported in that process. `@earendil-works/chord/next` is always Pi's vendored `next/index.ts`. Any other specifier of `RuntimeLoad.Modules` names a file the app ships (`specifier -> absolute path`); the driver `import()`s it once and the plugins share that one instance. A Go app offers host packages of its own as `RuntimeLoad.GoPackages` (10.4): the driver answers the specifier with a module whose exports are asynchronous functions that call the Go functions, and JSON values; a plugin `require`s it as it requires a file package. The `core` facets (the app's own) are files too (`CoreFacet{Name, Module}`, default export a facet). The driver answers `@earendil-works/chord/next` and `@earendil-works/chord/context` for every module it imports (`module.registerHooks`), so an app's modules import Pi's chord by its package name and share the host's instances.

## 3. Wire

One local socket (a unix socket in a private 0700 directory; a named pipe on Windows), accepted once. Frames are what Pi's IPC link uses (`next/link/ipc.ts`, `link.IpcLink`): a 4-byte big-endian length, then one kind byte and the payload. Kind `0`: one chord link message (`link.BinaryCodec` bytes), carried by `link.IpcLink` on the Go side and Pi's `ipcLink` on the Node side, so the two hosts speak the pinned link wire byte for byte. Kind `1`: a control message, one JSON object (Pi's worker `envelope` shape).

The Node host is the child of the Go side, as Pi's forked worker is of its server. `host.mjs` makes its host at `load` and `connect`s the link as its parent link with `{ principal: peer, trusted: true }` (`RuntimeLoad.Peer`: who the Go side is, as the Node host stamps it, `workers/main.ts:114`) when the Go side first uses the other end: the `attach` control request (10.9). The Go end of that link is `NodeHost.Link()`, a wrapper of an `IpcLink` over the channel made when the process connected, before the first frame is read: whatever the Node host sends before the app attaches it (its `hello`) waits in the link. The app attaches it to a Go host as Pi's app does, and nothing in this package touches a Go host:

- `Host.Route(kind, RouteOptions{Authorize, Resolve})` for an address-bound kind: `Resolve` returns `host.ResolvedLink{Link: node.Link(), Principal: <who the Node host is>, Trusted: true}` (Pi: `workers.ts:98`, and `plugins.test.ts`'s end to end: `server.route(Worker, { authorize, resolve: async () => ({ link, principal: { kind: "worker" } }) })`). A hold of a remote type whose `hostAddress` is that kind then goes over the link to the Node host, which serves what the plugins' facets serve. The app calls `Load` inside `Resolve` when it wants the process started on demand, as `workers.ts` forks inside `resolve`.
- `Host.Accept(node.Link(), LinkOptions{Principal, Trusted: true})` for a Node host nothing is held from (a child of the host).

`RuntimeLoad` has no Go host: a NodeHost needs none to load, so one Go host owns any number of NodeHosts (one `Route` per kind, one `Accept` per child), and a Go host that has a parent of its own can load plugins (the worker host of `next-node/workers`: it `Connect`s to its server, and routes its plugins' kind to a NodeHost; give it no address of its own, which its kind's route would not reach). The first port made the Node host the *parent* of the Go host. That had no room for either: a Go host has one parent, and a hold relayed up to a Node host that accepted the relaying host as its child fails with `hold: an origin on a child link` (a child relays nothing), which only the Node host's `onError` saw: the hold waited until its ready timeout.

The heartbeat is the host's and belongs to its parent link: a Node host closes a link silent for 30 s (`RuntimeLoad.Heartbeat`), its handshake included, and the process exits with the link. The link is attached lazily (10.9), so the clock starts at the first use of `NodeHost.Link()` by the Go host, at any time after `Load` returns; a host nothing attaches has no link, no clock and stays alive until `Close`. Closing the link, from either end, ends the channel, so the process exits (Pi: a worker whose link closed is stopped).

Control (JSON, request ids chosen by Go, one reply per request, replies in any order):

| request | reply |
|---|---|
| `load {kind, core, scripts, modules, address, principal, peer, heartbeat, closeTimeout, readyTimeout, compression}` (once) | `{failed: [{plugin, error}]}`: runtime.ts `load`'s report. |
| `reload {scripts}` | `{plugins, failed, objects}`: the host's `ReloadReport`; or an error. |
| `attach` | none: `host.connect` of the parent link (first use of `NodeHost.Link()` by the Go host, once). |
| `abort {target}` | none: aborts the context of request `target` (Go's context cancel). |
| `close` | none: `host.close`, which ends the link and with it the channel, then the process exits. `NodeHost.Close` waits for the exit. |

Node to Go, unrequested: `started` (connected), `activity {counts}` (the host's keep-alive counts `host.activity`, once at load and at each change: `NodeOptions.OnActivity`, `NodeHost.Activity`; a Go host that only routes to the NodeHost counts none of its objects' work, so a supervisor that stops idle workers reads them here), `error {error}` (the host's `onError`: every field of the `HostError` of its kind, so `NodeHostError` carries them typed), `fatal {error}` (an uncaught exception or rejection; the process exits).

`scripts` are `PluginScript`s as plain data (`{plugin, built}`: the `BuiltFacet` the Go build made, `source` and `digest` included), exactly what Pi ships to a worker. The digest rule of `runtime.ts` (same digest: same facet object) therefore holds across reloads of one process.

## 4. Lifecycle

- **Start** (`Load`): discover Node (section 6), extract the tree, listen, spawn, wait for `started` (`ReadyTimeout`, 30 s, as `chord/host`'s loader), send `load`, return the report. A failed start (aborted context, `ReadyTimeout`, a process that ended) kills the process, waits until it is gone and returns the cause with the stderr tail; the socket's directory is removed on every path.
- **Reload**: `Plugins.Reload` applies the build to the kind's current set and sends `reload` in that same section, so requests reach Node in the order the sets were decided; Node's `runtime.reload` queues per host in arrival order.
- **Cancel**: a cancelled Go context sends `abort`; the Node side aborts that request's `Context.abortSignal`. After a commit `runtime.ts` adopts what the host committed, as upstream.
- **Crash**: process exit or a closed socket fails every pending request with `*NodeExit` (exit code or signal, the `fatal` the process sent, stderr tail: the exit is built once the channel was read to its end, bounded by the stop grace, 5 s, so a `fatal` read after the process was waited for is in it). A request sent after the channel ended and before the process exited returns that exit once it is known (bounded by twice the stop grace, 10 s), not that the connection is closed. The crash closes the link (the Go host's route or child link drops; its holds go `loading`), and the `NodeHost` stays dead: nothing restarts it (Pi: "never restarted by itself"). `NodeHost.Exited()` closes.
- **Close**: `close` request, then the process gets `NodeOptions.StopGrace` (5 s: `GRACE` of `workers.ts`) to answer and exit and is killed after it. A process that answers `closing` is running its host's close (Pi's: the calls drained and the natives closed, each up to `closeTimeout`, then the app's store, which `host.mjs` closes after the host): it is not killed before `closeTimeout` (RuntimeLoad.CloseTimeout, 30 s by default) plus the grace, so the store's close runs. `Close` after exit is a no-op and returns the exit if it was a crash.
- **Output**: the child's stdout and stderr go to `NodeOptions.OnOutput`, else to this process's, as workers do; the last 8 KiB of stderr is kept for errors.

## 5. Errors

A failure inside Node is data on the wire: `{name, message, stack, chord?, cause?}`; `cause` is the error's `cause`, itself a wire error (a cause that is no Error is an error of its string, a cause already on the chain ends it). `stack` is `mapStack(error)` computed in Node while the script's map lives, so a plugin's import-time throw or a failed `setup` names `notes/helper.ts:3:8`, not `/chord-plugins/...`. `code` and `details` are a `ChordError`'s (`aborted` carries `details.committed`). Go returns `*NodeError` (its `Error()` is `message`; `Stack` is the mapped stack; `Cause` the cause's `*NodeError`; `Unwrap` gives the `*data.ChordError` when it is one and the cause, so `errors.As` finds a ChordError anywhere in the chain). Only plugin errors are plugin failures: a Go panic anywhere (the client, the decoder) propagates, it is never turned into a `PluginFailure`.

## 6. Node

Pi's `packages/chord` `engines.node` is `>=22.19.0`, the first release that strips types by default. Discovery (10.12, decided: (c)) runs `--version` on each candidate, parsed as semver, and takes the first that is `>=22.19.0`, in this order: (1) `PIG_NODE`, an executable, which when set is the only candidate (a value that is unusable or too old is the error), (2) `node` on `PATH`, (3) the install locations of version managers and installers (nvm, fnm, Volta, asdf, mise, `/usr/local/bin`, `/opt/homebrew/bin`, `/usr/bin`; on Windows `%NVM_SYMLINK%`, nvm's and fnm's versions, Volta, `%ProgramFiles%\nodejs`, `%LOCALAPPDATA%\Programs\nodejs`), the newest installed versions first. An error names the requirement, and the newest version found when every candidate was too old, or where it looked. The process runs `node --disable-warning=ExperimentalWarning <NodeOptions.ExecArgv...> host.mjs <address>`. A missing Node is an environment failure of `Load`, not of the build: `Build`, `Discover`, the watcher and `Plugins.Scripts` need none.

## 7. Packaging

`node/` is embedded (`go:embed all:node`) and extracted once per content hash under the user cache directory (`os.UserCacheDir()/pig/chord-plugins-node-<hash>`), published by an atomic rename; concurrent processes share it. A directory is trusted only when its `.complete` marker (written last, holding the hash) names this content and every file has its embedded size; a partial or older one is repaired in place, file by file (each a rename of a complete file), the marker last.

- `node/host.mjs`: the driver, written here.
- `node/pi/chord/src/**`: the import closure of `next/index.ts`, `next-node/plugins/{evaluate,stack,runtime}.ts`, `next-node/compression.ts` and `context/index.ts` at the pinned Pi commit, copied byte for byte, at Pi's own relative layout (so `../../next/host/index.ts` resolves).
- `node/pi/schema/`: `@earendil-works/pi-schema`, the package of Pi's tree (`packages/schema`, version checked against the one Pi's chord depends on) that chord imports by name: its `package.json`, `LICENSES/` and the `src` closure of its entry, copied byte for byte. Node refuses to strip the types of a file under `node_modules`, so `host.mjs` answers the name with `schema/src/index.ts` as it answers `@earendil-works/chord/next` (a package vendored as TypeScript cannot be found by Node's own lookup). Pi's chord has no other runtime dependency but pi-telemetry (the script fails if it gains one).
- `node/pi/node_modules/@earendil-works/pi-telemetry`: Pi's telemetry contracts at Pi's pin (from the `extensions/sdk-ts` lock; its `dist` modules are JavaScript, so Node's lookup finds them).
- `node/manifest.json`: the Pi commit, the pin (`.upstream/pin`) it was made against, the sha256 of every vendored file, and, when the commit is not the pin's, `catchup` naming it. A Go test fails when a file differs from the manifest, when the pin moved since, and when the commit differs from the pin without being the named catch-up (the pin is `b556cfe5`, the commit vendored: no catch-up is named; a script run with `PI_COMMIT` other than the pin's records one).

`automation/gen/vendor-chord-plugins-node.sh` (`make vendor-chord-plugins-node`, run by `make pin-bump` next to `vendor-pi-dist`) regenerates `node/pi` from the mirror of the pin (`PI_TREE`/`PI_COMMIT` override the Pi tree and its commit for a catch-up); it checks pi-schema and pi-telemetry against the versions Pi's chord depends on (and that those are its only dependencies), and writes nothing else.

## 8. Designed out, and what differs

- **The store.** The Node host has a store of its own, Pi's `createHost({ store })`: `RuntimeLoad.Store`/`PluginsLoad.Store` (`StoreOptions{Path}`) make the driver (`node/store.mjs`) open `openStore(sqliteBackend(await openNodeSqliteDatabase(Path)))` with Pi's vendored `next/store` and `sqlite/node.ts` (`node:sqlite`), as Pi's examples 20 and 21 open theirs, and pass it to the host; `close` closes the host and then the store, as Pi's apps do, and a `storage_failed` of the store reaches `NodeOptions.OnError` once and closes the host (`TestStoreAFailedStoreReachesOnErrorOnceAndClosesTheHost`). A persisted document and a table survive closing the NodeHost and loading another on the same file (`TestStoreAPluginsPersistedDocumentsAndTableSurviveClosingTheNodeHost`). Why not the Go host's store served over the link: a store belongs to one open host (Pi's rule, `host.ts`: "One open host per store"), and the Go host and the Node host are two hosts, so each has its own store, as any two Pi hosts do (a forked worker has its own); `store.Store` in Go is an in-process engine (commit queue, outbox, claims, the id allocator) that cannot be a second host's backend. A host loaded without a Store keeps Pi's `persist needs a store` (`TestStoreAFacetWithAPersistedDocumentFailsToActivateWhenTheHostIsLoadedWithoutAStore`). Two Node hosts on one file are two stores: Pi checks the rule in memory, so nothing refuses the second, whose writes the file's constraint refuses as in Pi (`TestStoreTwoNodeHostsOnOneFileAreTwoStoresAsInPi`).
- **`vm`-level API of `evaluate.ts` on the Go side** (`EvaluateFacet`, `PluginFile`, `ScriptFilename`, `mapStack` as Go functions): they exist only in the subprocess; Go sees their effects (reports, mapped stacks).
- **V8's compilation cache flag** (`runtime.ts`): runs unchanged inside the subprocess.
- **Other runtimes** (Bun, a runtime-slot executable) for this subprocess: Node is the only runtime (AGENTS.md: no embedded JavaScript).

Every remaining difference a Pi user or plugin can observe, with whether and at what cost it can be closed, is numbered below.

## 10. Closing the observable differences (owner decision 2026-11-01: full support, no divergences)

The differences from Pi are numbered. Every one closes by the designs below except #12 (the location Pi prints cannot be produced without inventing it: numbered divergence D222, 10.10) and the keyed members of a bridged Go core facet (10.4: Pi's `KeyedSlot` is owned by an object's own documents); only #12 is a numbered divergence. All rules of AGENTS.md hold: one subprocess, Pi's TypeScript vendored verbatim, no embedded JavaScript runtime, no `plugin.Open`. Where the process boundary makes Pi's behavior strictly more isolated than Pi's (the app survives what ends Pi's process), the difference is additive and stated as such.

Two mechanisms carry most of the work and are specified once.

### 10.1 Control calls in both directions

Today the control channel carries Go to Node requests (`load`, `reload`, `abort`, `close`) and Node to Go events. Section 10 adds:

- **`call` (Node to Go, asynchronous)**: `{event: "call", id, name, args}` answered by `{op: "answer", id, ok, result | error}`. `name` names a Go function the app registered (`NodeOptions.Functions`, `map[string]func(ctx, JSON) (JSON, error)`). The Go side runs each call in its own goroutine with a context that ends when the process ends. Used by host packages (10.5) and by telemetry (10.7).
- **`sync` (Node to Go, synchronous)**: Pi's `principalKey`, `revokedBy` and a telemetry propagation `inject`/`extract` are synchronous functions of the host. A request/answer pair on a second connection of the same socket address (a worker thread of the Node process owns it; the host thread blocks on a `SharedArrayBuffer` with `Atomics.wait` until the worker stores the answer). It needs no extra file descriptor, so it works on Windows. A Go `sync` handler is a pure function that never calls back into the Node host (a handler that did would deadlock; the Go side enforces it by giving the handler a context whose `NodeHost` calls fail with `ErrSyncCallback`). `principalKey` answers are memoized per canonical principal JSON in a bounded map only if the measured per-call cost (benchmark in the test file) exceeds 20 µs; `revokedBy` is never memoized (it reads the app's state).
- **Reference RPC (both directions)**: one protocol that lets one side hold, read, watch and call an object of the other side's host (10.3, 10.4): `get {type, params}` returns a handle; `value {handle, member}`, `watch {handle, member}` (then `frame` events, in order, until `unwatch`/`release`), `call {handle, method, args}` and `release {handle}`. The serving side runs it on its own host (`Host.get` in Node, `host.Host.Get` in Go) with the request's context, so cancellation, `ReadyTimeout`, errors (`unavailable`, `aborted`, a `ChordError` as data) and release are the hosts' own. The proxies' requests to the Go host travel as events `get`, `value`, `watch` and `bridgeCall`, answered by `{op: "bridgeAnswer", id, ok, result | error}`: `call` and `answer` are the callbacks' (above), with ids of their own, and both share the one channel.

### 10.2 Contracts as data

A type crosses the boundary as `ContractData`: the normal form of the contract that the fingerprint hashes (kind, name, version, params schema, members with their schemas and kinds, variants, methods with arguments and result). Go makes it from a `contracts.Contract` (`ContractData(c)`), Node rebuilds the Pi contract from it (`contractOf(data)`) with TypeBox-compatible plain JSON schemas, and the rebuilt contract must have the same fingerprint as the original. The receiving host binds with Pi's own check (kind, version, fingerprint), so a type that differs from what the other side serves is refused as Pi refuses it. A test per side proves the round trip for every fixture contract (`Index`, `Notes`, `Item`) and for each contract kind and member kind.

### 10.3 #1: the app's Go host holds local types its plugins serve

`NodeHost.Get(contract *contracts.Contract, params, ctx, host.GetOptions) (*NodeReference, error)` is the Go form of `server.get(Index)`. It sends `get` with `ContractData(contract)`; the Node host runs `host.get(contractOf(data), params, ctx)`. `NodeReference` has the shape of `host.Reference` for the members a local type has (`Member(name)` with `Value`, `Watch` (a `chord.WatchHandle[delta.JsonValue]` fed by ordered `frame` events), `Call`, `State`, `Release`), so Go code reads, watches and calls a plugin's local type typed by the Go contract it declares. Release is exact: a released `NodeReference` releases the Node hold; a process end fails the reference as `loading`, as a lost link does.

### 10.4 #2 and #4: Go objects offered to plugins

- **Go core facets in the plugins' closure (#2).** `RuntimeLoad.Bridged []BridgedFacet{Name, Host *host.Host, Contracts []*contracts.Contract}` names Go core facets whose *local* types plugins may use. For each, the Node host loads a proxy facet named `Name` that serves the same local contracts (`contractOf(data)`) with a factory that forwards `watch`/`call` over the reference RPC to the Go host's own object of that type (`Host.Get`). The proxy is an ordinary Pi facet in the Node host's `load` and `reload` sets, so Pi's closure rule and the runtime's `adopt` rule see Go core facets exactly as they see Pi's core facets: a plugin's request for a type a Go core facet serves binds to the proxy, and a Go core facet that failed to load on the Go host is passed as a failed core proxy, so the closure rule keeps its dependents old as it does for any failed plugin. In the other direction a plugin's local types the Go core facets need are `NodeHost.Get` holds; a plugin that failed at a reload is reported by the Node host, and `Plugins.Reload` returns the report so the Go host's `Reload(..., ReloadOptions{Failed})` gets those names and its own closure rule applies. A test per direction: a plugin needing a Go core type binds and reads it; a Go core facet needing a plugin's type keeps its old code when that plugin's new code fails; a failed Go core facet keeps its dependent plugin old.
- **Keyed members.** A keyed member of a bridged Go core facet's type is refused: Pi's host accepts a keyed member's source only from a `KeyedSlot` made by the object's own `Documents` (`#`-private state, a lazy load only through a persisted definition), and the vendored Pi is not edited. `NodeReference` has keyed pins (`pin`/`unpin`); only the proxy direction is open.
- **Host packages (#4).** `Pi: HostPackages` is a map of module instances the app made. A Go app offers `GoPackage{Specifier, Exports map[string]GoExport}`: each export is a Go function (`func(ctx, JSON) (JSON, error)`) or a JSON value. The driver writes a module for the specifier whose exports are asynchronous functions that `call` the Go function (10.1) and values that are the JSON value, and plugins `require` it as they require a Pi host package. What cannot cross is identity and live state (a JavaScript object shared by reference between plugin and app, a function called synchronously and returning a non-JSON value): a plugin that needs one is written against the package's asynchronous JSON functions. This is the whole boundary; it is stated at the use site.

### 10.5 #3: persisted documents and tables

The Node host gets Pi's store: Pi's `next/store` (already in the vendored closure) and `sqlite/node.ts` with `sqlite/database.ts` (vendored verbatim; `node:sqlite`, Pi's own backend). `RuntimeLoad.Store *StoreOptions{Path string}` makes the driver `openStore(sqliteBackend(await openNodeSqliteDatabase(Path)))` and pass it to `createHost({ store })`; `close` closes the host and then the store, as Pi's app does. Pi's rule is one open host per store, and a Go host and a Node host are two hosts: so the Go app's store and the Node host's store are two files, which is Pi's shape for any worker host (each host has its own store). The Go store is not served over the link: `store.Store` is an in-process engine (Export, Outbox, commit queue), and a store has one open host. Durability and the schema are Pi's own (WAL, `synchronous = NORMAL`, Pi's migrations), so a persisted document survives a restart of the Node host (test: write through a plugin's document, close, load a new NodeHost on the same path, read it). A host with no `Store` option keeps Pi's `persist needs a store` error.

### 10.6 #7: `telemetry`, `principalKey`, `revokedBy` as Go callbacks

`RuntimeLoad.Telemetry telemetry.TelemetryContext`, `PrincipalKey *data.PrincipalKeyFunction` and `RevokedBy host.RevokedBy[delta.JsonValue]` are `NodeOptions`-level callbacks of the app. The Node host builds a `TelemetryContext` whose spans and metrics are data events to Go (`span` start with name, attributes, parent as an id or a carrier; `end`; `attributes`; `event`; `metric`), in order on the channel; the Go side replays them into the app's adapter (`Extract(carrier)` for a parent that came from a carrier). `inject` returns a carrier made from the proxy span's id, which the Go side resolves, so no synchronous call is needed; `extract` keeps the raw carrier. `principalKey` and `revokedBy` are `sync` calls (10.1). `NodeHost.Revoke(r)` forwards `host.revoke(r)` to the Node host, as `Host.Revoke` does on the Go host.

### 10.7 #8: crash and exit semantics

Pi's plugin runs in the app's process: an uncaught exception, `process.exit(n)` or an infinite loop is the app's. Here they end or stall only the Node host. **Strictly additive isolation (stays, not a divergence):** the app survives a plugin's crash, exit or stall; the `NodeHost` is dead afterwards and nothing restarts it (Pi's workers are never restarted by themselves; restart policy is the app's, `workers.ts`'s component). What the app observes is made as close to Pi as the boundary allows:

- **Uncaught exception.** The host prints on the process's stderr (`NodeOptions.OnOutput`, else the app's stderr) what Node prints for an uncaught error: the error as `util.inspect` shows it (stack, own properties, `[cause]`), a blank line and `Node.js <version>`, with the plugins' positions mapped through their source maps (`mapStack`), and only then reports `fatal` and exits with code 1. The excerpt of the throwing source line that Node prints above the error is not printed. A thrown value that is no Error prints as Node prints it, with the `--trace-uncaught` hint for a primitive.
- **Unhandled rejection** is Node's default (`--unhandled-rejections=throw`): raised as an uncaught exception, so printed and fatal as one (a reason that is no Error is wrapped as `UnhandledPromiseRejection`, code `ERR_UNHANDLED_REJECTION`).
- **`process.exit(n)`.** `NodeExit.Code` is `n` (1 after an uncaught exception, -1 when a signal ended the process), `NodeExit.Signal` is Node's name of the signal (`SIGKILL`; empty on Windows, which has no signals), `NodeExit.Err` wraps the `*exec.ExitError`. `Exited()` closes; the link closes.
- **Infinite loop.** A stalled host answers nothing, so the heartbeat of the Go host the link is attached to closes the link; the stalled process cannot read its closed channel, so it is killed after `NodeOptions.StopGrace` (5 s, Pi's workers' `GRACE`). `Exited()` closes and `NodeExit` says why: `Signal` `SIGKILL`, `Code` -1 and `Reason` (its link closed and it did not exit within the grace).

### 10.8 #9: start latency and ordered frames

**Measured** (`BenchmarkNodeStart`, `go test -run '^$' -bench BenchmarkNodeStart -benchtime 15x`, Intel Xeon 8468, 6 cpus, Node 24.22.1, milliseconds per start to `started` / to the `load` report; `node --version` discovery, 5.5 to 7 ms, is inside `started`):

| tree | V8 compile cache | to `started` | to `load` |
|---|---|---|---|
| cold (extracted for each start) | none | 653 | 662 |
| cold | `enableCompileCache` (first start writes the cache) | 713 | 721 |
| warm (extracted once) | none | 617 | 625 |
| warm | `enableCompileCache` | 313 | 321 |
| warm, a spare process taken by `Load` | `enableCompileCache` | | 8 |

The `load` request costs about 8 ms; extraction about 25 ms; the cost is Node starting and importing Pi's closure (type stripping and compiling about a hundred files). Before `enableCompileCache` the warm start was 629 / 638. The numbers justify both levers: the compile cache halves a start from a warm tree (its first start pays about 50 ms to write it), and a spare process takes the rest off the `Load` (8 ms).

- **Compile cache.** `host.mjs` calls `module.enableCompileCache(<tree>/v8)` before its imports; the cache lives and dies with the extracted tree (one per content hash) and an unwritable directory is Node's no-op. Node writes the modules a process compiled when the process ends, which for a cold cache is a file per module written one after another and, on Windows under load, outlasted the stop grace after a link closed (the Go side killed a process that had run its exit handlers), so `host.mjs` calls `module.flushCompileCache()` once the process is up (after `started` is out) and after each `load` and `reload` reply, and the exit has nothing left to write (`TestNodeTheCompileCacheIsWrittenBeforeTheProcessExits`).
- **Spare process.** `PluginRuntime.Warm(ctx)` starts one process up to `started` (Pi's modules imported) and waits; `Load` takes it (waiting for one still starting, which is no longer than starting its own, and leaving it for the next when its ctx ends first); a dead spare is not taken. At most one spare exists. `NodeOptions.KeepWarm` starts the next spare in the background each time a `Load` has its process; that start is an owned task of the runtime (cancelled and joined by `Close`, its failure reported to `NodeOptions.OnError` as kind `warm_failed`). All options of a process are the runtime's (`ExecArgv`, callbacks), so a spare always equals what its `Load` would start; there is no per-`Load` process option to differ. `PluginRuntime.Close(ctx)` closes the spare and joins the background starts; it closes no host a `Load` returned; `Load` and `Warm` after it are errors. `Plugins.Warm` and `Plugins.Close` (which closes the runtime) are the component's hooks.
- **Ordered frames.** The frames a reload caused and its reply travel one socket in order, and the reader hands each link frame to the link, and the link to the Go host's channel, before it reads the next frame (`framedPort.read`, `Channel.receive`), so every frame the process wrote before the reply is handled by the Go host's channel when the reply is decoded, except a message that waits for an asynchronous inflate (a Go host with no compressor, a Node host that deflates). What is left is the Go host's own queue: the deliveries it scheduled for its watchers' listeners. A host that takes a link implementing `host.DeliveryAwaiter` (`Accept`, `Connect`, a route's `Resolve`) hands it its wait (`Channel.Idle`, then the sections queued and the deliveries entered, the wait of its own `Reload`). `NodeHost.Link()` implements it, and `Load` and every reload (`PluginRuntime.Reload`, `Plugins.Reload`, rollout steps) run that wait after the report is decoded, so when they return the frames the request caused are in the Go host's replicas and its watch listeners entered, as `await reload()` followed by Pi's `transported()` and `delivered()` is. The context ends only that wait. A link wrapped by the app before it reaches the host hides `Taken` and is not waited for (forward it). The end-to-end test reads the frame list right after the rollout.

### 10.9 #11: lazy attach

The Node host does not `connect` its parent link at `load`. `NodeHost.Link()` returns a link whose first use by the Go host (`OnMessage` or `Send`) sends an `attach` control request before the use, on the same channel; the host `connect`s then, and its heartbeat starts then. A NodeHost nothing attaches has no heartbeat clock, so no 30 s window exists. `Load` returns without the link being attached; `Close` of an unattached host works; a link attached at any later time carries the host. `Close` and `OnClose` of the link attach nothing. ### 10.12 #10: Node discovery (decided: (c))

Node.js >= 22.19.0 must be installed because evaluating Pi's TypeScript needs a JavaScript runtime, and AGENTS.md forbids an embedded one. Options were: (a) `node` on `PATH` with version discovery and an error that names the requirement; (b) a Package or Piglet that ships Node and gives `NodeOptions.Executable` its path; (c) discovery beyond `PATH` with the same version check. Decided (owner, 2026-11-01): **(c)**. (b) is deferred to PiG Standard after 0.7.0 and is not built.

`discoverNode` (`plugins_node_discover.go`) takes the first candidate whose `--version` is at least `22.19.0`, in this order:

1. `PIG_NODE`, an executable path or a name on `PATH`. When it is set it is the only candidate: a value that is not an executable, does not run, prints no version or is older than the minimum is the error, and nothing else is tried.
2. The Piglet runtime slot: none. Stock's runtime slot (`PIG_TS_RUNTIMES_DIR`, `docs/site/docs/typescript-runtimes.md`) holds Bun and executable runtimes that host TypeScript extensions and forbids the name `node`, so it does not provide a Node. No second mechanism is added.
3. `node` on `PATH`.
4. Version managers and installers, each checked in this order. Unix: `$NVM_BIN`; the newest versions of `$NVM_DIR/versions/node` or `~/.nvm/versions/node`; the newest of fnm's `node-versions` (`$FNM_DIR`, `$XDG_DATA_HOME/fnm`, `~/Library/Application Support/fnm` on macOS, else `~/.local/share/fnm`); Volta (`$VOLTA_HOME/bin`, `~/.volta/bin`); asdf shims (`$ASDF_DATA_DIR`, `~/.asdf`); mise shims (`$MISE_DATA_DIR`, `$XDG_DATA_HOME/mise`, `~/.local/share/mise`); `/usr/local/bin`; `/opt/homebrew/bin`; `/usr/bin`. Windows: `%NVM_SYMLINK%`; the versions of `%NVM_HOME%` or `%APPDATA%\nvm`; fnm's `node-versions`; Volta (`%VOLTA_HOME%\bin`, `%LOCALAPPDATA%\Volta\bin`); `%ProgramFiles%\nodejs`; `%LOCALAPPDATA%\Programs\nodejs`. A directory of versions contributes at most its three newest installs, compared as semantic versions.

A candidate that runs but is too old does not end the search. When none satisfies, the error is the requirement and `found <newest version seen>` (the text of option (a)); when none was found, it also says `node was not found on PATH or in <the places searched>` and names `PIG_NODE`. Stock PiG finds an existing Node and selects, ships and installs none (an inert capability, `docs/additive-features.md` D221).
