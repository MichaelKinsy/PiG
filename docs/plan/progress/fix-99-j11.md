# fix-99-j11: SDK handlers never run on the reply-reading loop

Base: staging `porter/pi-0.99.1`. Pi source: `.upstream/v0.99.1`. Found by the #104 review (`1cf1a6f3d`, "Not fixed").

## Scope and upstream tests

Pi has no test for this: every Pi handler runs in one process and awaits host calls (`packages/coding-agent/src/core/extensions/types.ts`: `ctx.ui.*`, `exec`, `executeTool` return promises; `runner.ts` awaits each handler). The width handler (`on_width_change`) is a PiG-only trigger (D19). No upstream test changed in this scope, so no test is ported; the red tests below are PiG's own.

## Green

| Item | Change |
|---|---|
| Python | `_handle_notify` no longer calls width handlers. `_dispatch_width_change` (`pig_sdk/__init__.py`) snapshots the handlers subscribed at arrival, queues the delivery and starts one worker thread (`pig-width-change`, tracked in `_request_threads` so `_stop_runtime` drains it); `_run_width_deliveries` runs deliveries one at a time in arrival order, isolates a raising handler (stderr traceback, silent after shutdown) and exits when the queue is empty. |
| Rust | `WidthDeliveries` (`extension.rs`) does the same on a `pig-width-change` thread counted by `RequestThreads`; `stop_requests` calls `stop()` first; a panic is caught per handler. |
| Go | `notifyWidthChange` queues a `widthDelivery`; `runWidthDeliveries` runs on `requestWG.Go`, so `stopRequests` waits for it; `stopWidthDeliveries` drops queued widths; a panic is recovered per handler (`extension.go`). Go had two separate defects: the handler ran on the message loop (no request served while it waited) and the read loop stalled on the 16-slot `incoming` channel while the handler held the loop. |
| Node | No change. Handlers are async; `ctx.ui.*` returns a promise, and `serve()` keeps resolving `call_result` frames while a handler awaits. Confirmed by `TestConformance_WidthHandlerHostCall/subprocess-node{,-packed}`. |
| Docs | `on_width_change` / `on_width_change` / `OnWidthChange` docs no longer say handlers must not block; `docs/extension-api-parity.md` row with the async contract; CHANGELOG entry. |

Request, command, tool and event handlers already run on a thread or goroutine per request in all three SDKs (characterization tests kept). The other notifies handled on the reader or loop (`events.release`, `tool_render_release`, `autocomplete.release`, `provider_release`, `model_stream_event`, `execute_tool_update`, `ui.custom.input`, `state_update`, theme/height) only update state or enqueue; none calls user code.

Ordering contract chosen: deliveries are FIFO and unbounded (an `int` each); a handler observes its delivery's width or a newer one through `ctx.width` because the reader stores the newest width on arrival. Pi has no width handler (D19 additive), so no Pi ordering applies.

### Existing tests adapted (not upstream ports, PiG tests)

- `extensions/sdk/width_change_test.go`, `extensions/sdk-py/tests/test_sdk.py`: each call to the notify path is followed by a wait for the queued deliveries (`requestWG.Wait()`, joining the `pig-width-change` thread). Inputs and expectations are unchanged.
- `extensions/sdk/mcp_servers_test.go` `TestRegisterMcpServerReplyOutranksAnOlderStateUpdate`: it held the message loop with a blocked width handler. Width handlers no longer run there, so it holds the loop by locking `toolRenderMu` and sending a `tool_render_release` notify. Mutation `at := 2*notifySeq - 1` in `mcp_servers.go` still fails it. `TestRegisterMcpServerFromTheMessageLoopReturns` is renamed `...FromAWidthHandlerReturns` (same assertions).

Tests added after the fix (not red-proven against the old code): Go `TestWidthHandlersRunInOrderWhileOneBlocks`, `TestWidthHandlerPanicDoesNotStopTheExtension` (mutation: recover removed, the process panics).
