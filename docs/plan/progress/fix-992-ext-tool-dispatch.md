# fix-992-ext-tool-dispatch progress

Scope: audit-992-codemode-mcp CM1 (subprocess tool `prepareArguments` runs after the host validated) and CM2 (a parallel batch of subprocess tool calls starts in goroutine order). Oracle: Pi 0.99.2 source (`.upstream/current`, identical to v0.99.1 for the cited ranges): `packages/agent/src/agent-loop.ts:619-647, 707-716, 820-837`. CM3 (argument member order) belongs to `fix-992-argument-order` and is not asserted here.

## Findings (root cause)

- CM1: Pi's `prepareToolCall` calls `tool.prepareArguments` and then `validateToolArguments` on the result (`agent-loop.ts:707-716`). A PiG subprocess tool had no host-side `PrepareArguments`: the host validated the raw arguments (`agent/tool_execution.go` prepareToolCall, already ordered prepare-then-validate for tools that implement `ArgumentPreparer`) and the SDK runtimes prepared inside `tool_call`, after validation. The conformance row called `Definition.PrepareArguments`/`Execute` by hand, so it could not fail.
- CM2: `executeToolCallsParallel` (`agent-loop.ts:619-647, 820-837`) invokes every call through `Promise.all(map)` in source order and each reaches `tool.execute` synchronously. PiG ran one goroutine per call and a subprocess tool wrote its `tool_call` request from that goroutine, so the frames left in scheduler order (7 of 10 reversed with N=2). The Go, Rust and Python SDKs then ran each request on its own goroutine/thread, so arrival order did not fix start order either. Node serves frames in order on one thread (`runtime.mjs` serve loop calls `handleRequest` synchronously, whose `tool_call` branch reaches `execute` before its first await).

### Follow-up commit: what a Go and Rust test can pin

My red tests asserted that the first statements of the handlers run in call order for every SDK. That holds for Node (one thread) and for Python (the GIL keeps a thread that handed its place on running; 30 runs under 4 burners on 4 pinned cores x 24 rounds x 16 calls, no inversion). It does not hold for Go and Rust: measured on 4 pinned cores with 4 CPU burners, the Go SDK test inverted about once per 200 batches of 16 (a thread preempted between the hand-off and its handler's first statement). A spinning hand-off did not change this; the delay is the OS preempting the thread, not the wake-up. No Go or Rust construct closes the window (a handler is arbitrary blocking code with no synchronous prefix). So, with a QUESTION posted to the lead ( proceeding on "language mechanic, not a divergence"): the SDK guarantees invocation order; the Go SDK strict test now runs on one processor (`GOMAXPROCS(1)`, where the scheduler's choice is deterministic: without the gate the goroutine started last runs first); the gate has deterministic unit tests in Go and Rust (`TestToolStartOrderHoldsALaterRequestUntilTheEarlierOnesBegan`, `ToolStartOrder` tests, the release path); the Rust wire test now checks the failure path; and the conformance row asserts first-statement order for Node (isolated, packed) and Python, and, for Go, Rust and fused Go, that each call starts exactly once with numbers from its own round and results stay in source order. This edits my own red tests in the green phase; they were not upstream ports, and an assertion that can fail under scheduler load for no PiG defect is a flake, which the rules forbid.
