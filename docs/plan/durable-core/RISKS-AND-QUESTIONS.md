# Durable core: risks and open questions

Status: 2026-10-06. Companion to [ADR-0001](ADR-0001-core-architecture.md), [CONTRACT.md](CONTRACT.md), [ABI.md](ABI.md) and [BAKEOFF.md](BAKEOFF.md).

## 1. Questions for the owner

| id | question | why it matters | needed by |
|---|---|---|---|
| Q1 | When can we use a Cloudflare account (Workers Paid, SQLite-backed DO), and may we publish numbers measured there? | Miniflare runs workerd locally, but production differs in ways the decision depends on: Wasm compile and code caching at isolate start, how many objects share an isolate, real eviction timing, alarm retries, and the `rowsRead`/`rowsWritten` billing counters. Until then every number is "local workerd on smc1". | before the bake-off decision is published; S0 can start without it |
| Q2 | Will you open the upstream conversation about sidecar tables: a reserved prefix (`pig_`, or a neutral one such as `ext_`) that pi-durable migrations will never use, and a stated rule that pi-durable ignores tables it does not own? | pi-durable 1.0.4 checks only `durable_schema.version` and tolerates unknown tables today (research notes 1), but that is behaviour, not contract. Without the agreement, a future pi-durable migration could collide or start rejecting foreign tables, and stores the core touched would stop opening in Pi. The fallback is a no-sidecar mode (ADR D6 path 3), which costs cold time. | before the sidecar ships to users |
| Q3 | Which upstream line does the DO product track: the pinned 1.0.4 until the next PiG leap, or each pi-durable release? | The unreleased changelog reportedly adds task `startedAt`/`endedAt` and message `durationMs`, and a context-range fix that moves the B2 bar. Row identity is per version (CONTRACT section 1). | before the production core's first release |
| Q4 | Product placement: is the Cloudflare host (JS shim, Worker bundle, DO class) part of Stock PiG, a Package, or PiG Standard? | AGENTS.md requires a classification before an additive capability is implemented. The core itself is Stock (it is the Durable implementation); the `pig_` sidecar is an additive, user-visible artefact that needs a record in `docs/additive-features.md`; the DO host looks like a separately distributed Package. | before S0 merges to a release branch |
| Q5 | Is a TypeScript core acceptable for the DO product if the L6 control wins outright, or is one Go codebase a hard requirement? | BAKEOFF decision rule 4 escalates that case to you. Knowing the answer up front changes how much effort goes into L6. | before L6 starts |
| Q6 | May the bake-off record a real-provider cassette (OpenAI Responses and Anthropic Messages, a few turns each) with an owner key? | W4f and CONTRACT example 16 need recorded streams; without them the wire plane and example 16 stay untested. | optional; before W4f |
| Q7 | Benchmark publication: durable-bench is published by tardigrade's author. Do we publish comparisons, contribute our targets upstream to durable-bench, or keep results internal? | Public claims need the same harness, both scripted-model variants, and smc1 or production numbers; AGENTS.md public-writing rules apply. | before any public statement |

## 3. Risks

| id | risk | likelihood / impact | mitigation |
|---|---|---|---|
| R1 | Semantic breadth. The slice is ~1,400 lines; pi-durable's storage, session and harness are ~12,700. The production core can stall between the two. | high / high | The contract corpus is the only gate; the existing `durable/` Go port stays the reference and fallback until the core-backed Harness passes all of it; production work expands family by family in the CONTRACT section 3 order. |
| R2 | Moving bar. Once upstream stops re-reading, pi-durable approaches its 50-turn numbers at every size. | certain / medium | Design to that floor (B2 is stronger than the announced fix); judge on cold, memory and size, where the design advantage does not depend on upstream's read pattern. |
| R3 | Benchmark artefact. The in-core scripted model and durable-bench's unbounded active range flatter the core. | high / high for credibility | W2c is reported separately and never compared with baselines; the host-side stubs (W1, W2) and W4a/W4b are primary. |
| R4 | Byte fidelity. Key order, number format, escapes or Chord op choice differ in a corner the corpus does not reach. | medium / high (silent store divergence) | Differential fuzzing against `JSON.stringify`, `JSON.parse` and chord 1.0.4 (CONTRACT section 5.6); the handoff matrix; mutation scenario X1. |
| R5 | Scheduler order. Pi's commit order under concurrency comes from Promise microtask order; reproducing it in a synchronous scheduler is subtle. | medium / high (outside the slice) | Effect tapes make both sides deterministic; V11 establishes Pi's own determinism; parallel rounds and sub-agents enter the corpus before the production core claims them. |
| R6 | Memory per object in shared isolates. A 3.5 MB Go floor per instance and non-shrinking linear memory limit objects per 128 MB isolate. | medium / medium | H-mem (one instance per isolate), L2 (TinyGo), L3 (host-held bytes), instance recycling (ADR D10). |
| R7 | Shared failure domain. One instance per isolate means a trap reopens every object on it. | low / medium | Traps are bugs caught by fuzzing; reopen is a cold open, not data loss; the bake-off measures the trade. |
| R8 | Extensions in a DO. Pi extensions are arbitrary async JS; the transaction channel holds the Session line across host awaits, and a misbehaving extension can stall a Session, exactly as in Pi. | medium / medium | Same semantics as Pi (§4, §7.5); ABI section 8 queues other events; hosts may add timeouts only as numbered divergences. |
| R9 | Wire plane size and scope. Porting provider body building and stream parsing into the core grows the module and the contract. | medium / medium | Context plane is the default; wire plane only after H-wire passes; build tags per provider family. |
| R10 | Interrupted turns in a DO. Deploys, runtime updates, the 15-minute I/O window and storage access during shutdown kill turns mid-flight. | certain / medium | Recovery is Pi's (CONTRACT section 3.8), proven by the crash matrix; the liveness alarm resumes without a user request (ADR D7). |
| R11 | Sidecar staleness bug returns the wrong context silently. | low / high | Two-step validation (ADR D6), `core_id` content identity, acceptance A4, and a debug mode that rebuilds from rows and compares on every cold open. |
| R12 | TinyGo correctness. Its `encoding/json` mis-decodes `json.RawMessage` (wasm-spike); other reflection-dependent PiG code may fail similarly. | medium / low | The core avoids reflection and `encoding/json` (ADR D15); L2 stops early on non-trivial source changes. |
| R13 | Two toolchains for L4 (Go plus Rust or Zig) and two linear memories. | medium / medium | L4 must beat L1/L3 by 1.3x on cold to continue; the kernel ABI is six calls. |
| R14 | Measurement noise on smc1 (shared, load 15-60). | high / medium | CPU gate, interleaved rounds, two sessions, at least 100 aggregated turns, bootstrap intervals (BAKEOFF section 7). |
| R15 | Policy friction. Sidecar tables and the DO host are user-visible additions; a Pig-owned format must stay unversioned. | medium / low | `core_id` is content identity, not a version; additive-feature record and product classification (Q4) before release; any observable difference from Pi is a numbered divergence first. |
| R16 | Upstream schema change (a pi-durable migration to schema version 2). | low / high | Refuse newer schemas as pi-durable does; re-capture the corpus on the pin bump; the sidecar is a cache and is discarded. |
| R17 | pi-ai functions inside the core. Stored bytes depend on pi-ai code the core must reproduce in Go: `validateToolArguments()` (TypeBox `Value.Convert`, `coerceWithJsonSchema` key reassignment, error text), `getCurrentTools()`, `estimateMessageTokens()` and `calculateContextTokens()` (compaction), and `uuidv7()` on native hosts. | medium / high (silent store divergence on tool calls and compaction) | Use PiG's existing parity ports of those functions; differential tests against pi-ai 1.0.4 (CONTRACT section 5.6); tool-call scenarios with coercible and invalid arguments in the corpus. |
