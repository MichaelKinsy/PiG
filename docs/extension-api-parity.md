# Pig extension API parity matrix

Pig's subprocess extension API must account for every upstream Pi extension interface. A row is complete only when Pig has a protocol/API mapping, SDK coverage, and a conformance test. If exact parity is impossible or intentionally rejected, record a numbered divergence in `docs/parity/DIVERGENCES.md`.

This matrix tracks behavior. For the SDK surface, symbol by symbol for each runtime, see the generated matrix in `docs/extension-sdk-surface.md`.

Source for upstream inventory: upstream Pi `docs/extensions.md` and `examples/extensions/`.

The unported declarations of upstream 0.99.2's extension API are named by `test/parity/known-gaps.toml` (scope `upstream-parity`), and `test/upstream-parity` fails when one is fixed or a new one appears.

## Parity boundary (read this first)

Pig is a Go-native port of upstream pi. Upstream pi has exactly **one**
SDK (TypeScript) and loads extensions **in-process**. Pig deliberately
rejects in-process production extensions (no embedded JS runtime, no WASM,
no dynamic Go plugins). Two downstream-only constructs exist so that we
can still expose the upstream extension API faithfully:

- **Multi-language SDKs** (`extensions/sdk`, `extensions/sdk-rs`,
  `extensions/sdk-py`): see `docs/additive-features.md` D19. These are
  language bridges into the **same current wire contract** in
  `coding/extension/host/subprocess/protocol.go`. The wire has no independent
  version or compatibility negotiation. They are not separate APIs. Every SDK
  row in this matrix must keep its
  semantics aligned with the in-process Go reference exercised by
  `test/extension-conformance/conformance_test.go`.
- **TypeScript declarations** (`extensions/sdk-ts`): re-export the exact pinned
  Pi extension types and add declarations for PiG-only capabilities. Node
  extensions still run through PiG's compatibility modules. This package does
  not define another runtime API.
- **Runtime cells / packed runners**: see `docs/parity/DIVERGENCES.md` D20. These
  are an internal optimization on the host side. They do **not** change
  the extension API: each contained extension still gets its own socket
  and runs the same wire register handshake. Treat packed cells
  as transparent for parity purposes; a row is only "complete" if it
  preserves identical semantics in both isolated and packed modes.

The wire handler declarations require a positive `handler_id` so multiple
registrations for one event preserve exact identity and order. It identifies a
handler within one extension registration; it is not a multi-register handshake. The host rejects missing, zero, or duplicate identities.

When a row is impossible or intentionally non-parity, record a numbered
entry in `docs/parity/DIVERGENCES.md` and link it from the Status column.

### Async contract requirement

Every upstream Promise-returning extension method, callback, handler, factory,
provider refresh/login function, and UI operation must preserve whether the host
awaits it, completion ordering, rejection/error propagation, cancellation,
concurrency, and event-loop ownership. Go `error` and result returns represent an
awaited Promise only when the host waits for the callback to return. A detached
goroutine is valid only for an intentionally unawaited upstream operation and
must have explicit lifetime ownership, cancellation, error reporting, and
shutdown draining. Conformance for an async row must include premature-return,
cancellation, and error-path assertions; TUI-facing rows must also prove that UI
mutation re-enters the main loop. See `docs/extension-authoring.md` for
TypeScript-to-Go examples.

### Retained Context host-call lifetime

Normal completion retires a request parent before its response is published, without invalidating a retained Context's original connection. Active requests retain parent cancellation; cancelled origins and retired connections never become unparented live calls. Writer ordering serializes parent selection and normal completion. Pending calls resolve or cancel rather than retaining an absent parent. `TestConformance_TerminalInput` retains the original Context across current, empty/reset and replacement UI values in every SDK and isolated/packed/fused realization. The request-lifetime unit tests cover cancellation, racing publication, worker-start failure and disconnect, and scenario48 compares the actual Host/SDK caller with Pi. See `docs/parity/retained-context-lifetime.md`. Host guards, Provider child leases and Markdown callback body completion remain separate.

### Subprocess liveness contract

The current subprocess wire carries `ping`, `pong`, and `request_state` without
version negotiation. Each SDK dispatcher answers `ping` directly. A request
reports `started`, then `progress` or `blocked` when applicable, and
`completed` before its response. Host calls carry `parent_request_id`.
Interactive UI calls automatically report `blocked:user`; other awaited host
calls report `blocked:host_call` and then `progress`.
The blocking-reason vocabulary is `user`, `host_call`, and `external_io`.

The host sends heartbeat only while the connection owns outstanding work or
live provider state. A frame the host has queued or is writing is outstanding
work, and every byte the extension reads renews the pong deadline, so a slow
reader stays connected and a peer that stops reading fails visibly. Missing
`pong` closes the logical connection and returns `extension_unresponsive` with
extension, request, and operation context. The host never drops an outbound
frame and sets no socket write deadline. Loading has no deadline either: like
upstream's awaited factory, a load ends when the extension registers, its
process exits, its connection closes, or the caller cancels. A packed runner
reports a member whose factory fails by closing that member's socket.
Tools, commands, events, and shortcuts have no host completion or inactivity
lease. Their caller-owned context controls cancellation. Renderers use a
generation-scoped inactivity lease off the TUI loop and retain the last
completed frame. A failed logical packed member does not quarantine siblings;
shared process death quarantines the packed cell. Parent cancellation cancels
its blocked host/UI calls and removes response correlation before a late
response can arrive.

Ordering and cancellation coverage lives in
`coding/extension/host/subprocess/liveness_test.go`. `TestLivenessConformanceSDKsMatch`
compares normalized Go, Node/TypeScript, Rust, and Python production recordings for
heartbeat while blocked, awaited and interactive calls, no-result calls,
parent cancellation, completed ordering, and late-response disposal. Node work scheduled by a handler after its response has settled carries no parent request; it belongs to the live extension connection instead. `TestNodeUICallScheduledByAFinishedHandlerRuns` gates that transition in isolated and packed Node cells, and `34-late-overlay` exercises the delayed terminal overlay against Pi. A Node host call the handler started before its response stays outstanding after the response and settles only through its own result, as Pi's in-process `showExtensionCustom` does (`interactive-mode.ts:2858-2940`); `TestNodeCommandReturnDoesNotCancelItsHostCalls` and `TestHostCallReadBeforeItsParentsResponseSurvivesTheResponse` gate it. A request cancellation or a closed connection rejects the Node calls still pending, and a rejection the extension dropped does not end the process, while any other unhandled rejection keeps Node's default: `TestNodeCancelledCommandDoesNotCrashOnDroppedHostCall`, `TestNodeReloadDoesNotCrashOnDroppedHostCall`, `TestNodeExtensionUnhandledRejectionStillCrashes` and `TestNodeExtensionUnhandledRejectionListenerKeepsProcess`. Active-request cancellation remains covered by the liveness suite. This is the D56
subprocess-host behavior; upstream has no subprocess transport.

## Owner-approved known gaps for 0.3.x

On 2026-09-28, owner Michael Kinsy approves recording the remaining SDK Provider surface and foreign registered-config identity (D78), partial-message observation across the process boundary (D82, RPC33), and foreign event-bus payload identity (D83). These are visible differences, not parity completion or closure waivers. Same-process object behavior must remain Pi-exact. [The integration record](findings/0.3.0-known-gaps.md) separates current source from later owner checkpoints and names the remaining native defects.

Foreign configuration readers receive snapshot data, not transparent author-held aliases; implemented callable capabilities do not confer container identity. On 2026-09-29 the owner narrowed D83 (Q2 = A) and retired D77 (Q1 = B): every Node realm shares one bus and foreign listeners receive the original payload by reference; D83 keeps only the named cross-realm scheduling, cycle, brand-check and native-realm boundaries. A remote partial message does not acquire later producer revisions. None of these decisions changes callback waiting, cancellation, error propagation, listener order, terminal results, persistence or resource ownership. The strict RPC33 scenario remains enabled, unchanged in strength and durability, and records its raw failure.

RPC shutdown async contract: upstream 0.99.1 `rpc-mode.ts:726-742,802-805` removes signal handlers and Session stdout subscriptions before awaiting `AgentSessionRuntime.dispose`. The runtime emits and awaits `session_shutdown` before synchronous Session disposal (`agent-session-runtime.ts:404-411`, `agent-session.ts:1350-1371`). Pending dialogs are not resolved by stdin EOF. A pending Node shutdown Promise may let the event loop drain; PiG reports that transport observation without synthesizing a response. The aborted run's hooks still deliver `turn_end` and `agent_settled` through the stale runner, while a missing persisted assistant entry emits `extension_error` (`agent-session.ts:805-853,1037-1043`, `runner.ts:1020-1109`). The direct Pi comparison tests pin the complete immediate-tail event sequence and stdout records. Node reports post-disposal suspension beyond immediately fulfilled continuations, so a delayed `turn_end` does not postpone process exit (`output-guard.ts:95-108`, `TestRPCInputEndDoesNotJoinDelayedTurnEnd`). General host-call suspension during that tail and keepalive aggregation across separate runtime cells are not closed by those tests.

RPC stdin-end command contract: Pi reads stdin's end one event-loop iteration after the line that started an extension command, and `shutdown()` then exits within microtasks and one tick (`rpc-mode.ts:726-742,802-805`, `output-guard.ts:105-108`; the stdout write callback runs inside the current macrotask). A command answers only if it settles inside that window: microtasks, ticks and the check phase of the line's own iteration. A nested `setImmediate`, file I/O, a child process, a timer and a dialog do not answer; a command that settles while a `session_shutdown` handler that awaits a timer or I/O keeps Pi alive does. The Node runtime arms each command's window at invocation. When the window closes unresponded it reports `request_state` `suspended` only after `runtime_input_end`, because a client that closes stdin later than the line (on the handler's last notification, say) finds every continuation that ran in between answered. At `runtime_input_end` the runtime re-evaluates each closed window: a command that started or finished a host call since its window closed ran meanwhile and gets a fresh window, which a pending short host call keeps open and which reports suspended only if the command still waits when it closes; a command that did nothing since is reported suspended (`TestNodeRuntimeReportsCommandSuspensionAfterInputEnd`). Only a host call that settles synchronously or through microtasks in Pi keeps the window open. Before it starts shutdown, the host waits until every command that Pi would have answered before it read stdin's end has written its response (`rpcCommandJoin.windowIdle`, fed by `Host.SetCommandWindowHandler`): a Node command counts as unanswered only once its runtime reported it suspended, and a running command of a runtime with no microtask continuation counts as unanswered at once. A command's response therefore precedes the `session_shutdown` handler's output and survives a client that closes stdin on the handler's notification (`TestRPCInputEndResponsePrecedesShutdownNotificationComparedWithPi`, `TestRPCInputEndAfterCommandNotificationAnswersComparedWithPi`, `TestRPCShutdownInputEndSettlesBeforeShutdownStarts`). The host records input end at EOF, holds a suspended command's response unless a quit `session_shutdown` handler is itself suspended, and joins each command until it answers or is suspended. The host applies a suspension only after every earlier call of the connection applied, so after input end a command's or quit handler's response waits until the suspension that preceded it is applied; before input end the response does not wait, because a suspension cannot hold it then (`TestResponseAfterInputEndWaitsForItsSuspension`, `TestResponseBeforeInputEndDoesNotWaitForAnotherRequestsCall`, `TestRPCInputEndAfterQueuedReplacementHoldsCommandResponse`). A runtime with no microtask continuation (Go, Rust and Python SDKs, fused and packed placements) has its still-running commands counted suspended at the checkpoint, without an SDK message (`TestConformance_SuspendedCommandFlush`). `setTimeout(0)` and a single `fs.stat` are racy in Pi and have no row. A command's response frame precedes the drain notification of its own connection; the notification is how a still-pending quit handler reports that Node's loop emptied. The Node process reports the drain on every connection it hosts. At the first report the host takes its own list of the process's open connections and acts after each of them reported or closed, so a response on any packed sibling connection is ordered before the exit, and a connection the host closed earlier, or a report of a generation the host no longer accepts, cannot leave the wait open (`TestRuntimeDrainWaitsForEveryConnectionTheHostHolds`, `TestRPCInputEndAfterSecondExtensionCommandNewSessionAnswersComparedWithPi`). The connection's read loop marks the command answered as it routes the response, before it reads the next frame, and the join stops counting an answered command as suspended unless its delivery holds the response. The drain exit therefore waits until such a response is written, as Pi's loop stays alive until it writes it (`TestRPCInputEndAfterCommandNewSessionAnswersComparedWithPi`, `TestCommandFlightAnsweredIsNotSuspendedUntilHeld`). Pi runs every extension in one event loop, which stays alive for a child process, a timer, I/O, a session change or any other host call and does not stay alive for a dialog that stdin can no longer answer, or for a Promise nothing settles. Each Node process therefore reports its own loop after input end: a process with a pending quit handler reports `runtime_drained` when its loop drained (Pi's exit when the loop empties), and a process without one reports `runtime_commands_drained` when its loop drained with an unanswered command. Neither report carries arguments, and each goes out on every connection the process hosts. A pending host call other than a dialog keeps the loop, and so the process, from reporting. A report covers only the commands the process had started when it sent it: the runtime reports a command's `started` state as it reads the command, and the host marks the commands whose `started` state it read on that connection before the report. A command the process reads after a report can keep its loop alive, and the process reports again if its loop drains with that command unanswered (`TestDrainReportCoversOnlyRequestsTheRuntimeStarted`, the `never settles, then newSession` and `never settles twice` rows of `TestRPCInputEndQuarantinedNodeCommandComparedWithPi`). `runtime_commands_drained` only records that the process cannot answer those commands: without a pending quit handler Pi exits at the stdout flush, which the shutdown path applies itself, so the report does not end the host. `runtime_drained` is the loop-drain checkpoint, taken when the host handles the report and before the wait. From it, a Node command counts suspended once its own process reported that nothing keeps its loop alive with the command started, and not before: the host awaits the command of another isolated process, such as a Node `/ns2` that waits for the host to build the replacement Session, until that process answers or reports, and stops awaiting a command that waits on a dialog or on a Promise nothing settles, as Pi's loop would. The host counts a Go, Rust, Python, fused or packed command from the host calls it applies for the command, in arrival order: a user dialog counts apart from every other call that keeps Pi's loop alive, and a command counts suspended while its only outstanding calls are dialogs, whether the dialog came before the checkpoint or after it, and however many other calls the command started and finished meanwhile. So a Go command awaiting `ctx.Exec` is awaited, as Pi's `/exec` is. An answered command counts only when its response is held. `runtime_quit_yield` is Pi's exit at the flush, so it applies the flush checkpoint and does not take the loop-drain checkpoint (`TestRPCInputEndQuarantinedNodeCommandComparedWithPi`, `TestDrainSpansIsolatedNodeProcesses`, `TestDrainCheckpointCountsDialogWaitsFromHostCalls`, `TestHostCallsAreCountedPerRequestFromTheirFrames`, `TestCommandsDrainedProcessCountsItsUnansweredCommands`, `TestQuitYieldKeepsTheFlushCheckpoint`, `TestRPCInputEndDrainExitCountsGoSDKCommandAwaitingDialogSuspended`, `TestRPCInputEndDrainExitKeepsGoSDKCommandAwaitingExecComparedWithPi`, `TestDrainAwaitsIsolatedNodeCommandThatWaitsForSessionChange`). A Node runtime cannot observe a command of another runtime process; the host's checkpoint and each process's own report do. A connection that closes while a report waits for it, and a report of a generation the host no longer accepts, complete after the calls the connection sent earlier applied (`TestStaleRuntimeDrainWaitsForEarlierCallInitiation`), and Shutdown joins the task that finishes a drain after a close (`TestShutdownJoinsDrainTasks`).

RPC settle-tail contract: Pi emits `agent_settled` in the microtasks that follow a published `agent_end` (`agent-session.ts:1044-1058,1752-1777`), so its stdin reader, which runs between macrotasks, reads no line between them (`rpc-mode.ts:355-360,808-810`). Pig reads stdin on its own goroutine, so `rpcSettleGate` holds each stdin batch, and stdin end, from a published `agent_end` until `agent_settled` is written, except while a compaction, an auto-retry delay, a new run (`agent_start`), an extension dialog or a waiting settle-tail handler is pending, which Pi serves stdin during (`TestRPCCommandAfterAgentEndAnswersAfterAgentSettledComparedWithPi`, `TestRPCCommandAfterAgentEndWithoutExtensionsAnswersAfterAgentSettled`, `TestRPCSettleGate*`). The Node runtime arms a window for each `agent_before_settle` and `agent_settled` handler in RPC mode and reports `request_state` `suspended` when the window closes unresponded, as for a command; `Host.SetSettleTailHandler` delivers the count of such handlers, and the gate stays open while it is above zero. A command sent during a handler that awaits a timer or I/O is therefore answered before `agent_settled`, and stdin's end during a handler that never settles starts shutdown (`TestRPCCommandDuringSuspendedSettleTailAnswersComparedWithPi`, `TestRPCInputEndDuringSuspendedSettleTailShutsDownComparedWithPi`, `TestSettleTailCountsHandlersPiServesStdinDuring`). A runtime with no microtask continuation (Go, Rust and Python SDKs) reports no window: its running tail handler holds stdin until it answers (divergence D86), and after input end it counts as waiting, as `FlushCommands` counts its commands, so stdin's end does not wait for it (`TestRPCInputEndDuringGoSDKSettleTailHandlerShutsDown`).

Interactive session-replacement async contract: upstream 0.99.1 `agent-session-runtime.ts:133-164` awaits `session_before_switch` and `session_before_fork` before it touches the session, with its event loop still running. Interactive `/new`, `/resume`, `/fork` and `/clone` emit them through `awaitExtensionUI`, as `session_start` does: the handlers run off the owner loop, and the owner loop keeps serving their `ctx.ui` calls. While a handler waits, input reaches only the extension's dialog, custom UI or terminal-input listeners; other type-ahead waits for the command. The handler's result is read as Pi's `cancel` field from typed and JSON results, and a cancel ends the command without output. Handler failures are reported by the runner and do not cancel. Loop shutdown ends the wait with an error. `extensions-runtime/65-session-before-dialogs` covers the Node-to-host path.

## UI prompt events

Upstream's runner wraps the bound UI surface (interactive and RPC modes, not
print) so every `ctx.ui.select`, `confirm`, `input`, `editor`, and `custom`
call reports the outermost blocking prompt (runner.ts `withUIPrompt`). A
nested or overlapping prompt raises the depth without an event, and the end
event repeats the outermost prompt's kind and title. `custom` carries no
title, and an empty title is omitted from the payload.

Async contract: the prompt does not wait for remote asynchronous handler completion. Upstream queues each event with `queueMicrotask(() => void this.emit(event))`; handler errors go to the extension error listeners. Pig admits queued emissions in FIFO handler-body order. A Go in-process handler returns at its only observable suspension boundary; a handler that starts asynchronous work returns before that work finishes. A subprocess handler acknowledges when the SDK reports `blocked` or `completed`, or returns its response; a socket write or `started` state is not handler admission. Go, Rust, and Python report awaited host calls as suspension boundaries. Node reports the return from invoking the handler, before awaiting its Promise. A suspended start handler therefore does not block the matching end emission. Each runtime retains registration order within one emission. Invalidation (reload, session replacement) drops pending events and cancels active handler contexts.
In-process extensions reach the scope through the runner's wrapped UI surface.
`TestPromptHandlerBodyFIFOAcrossSDKs`, `TestPackedPromptHandlerBodyFIFO`, and `TestReviewPromptHandlerBodyFIFOThroughFusedSDK` record handler entry before any host call and check the unsorted sequence association. `TestPromptEndRunsWhileSDKStartWaitsForHost` and `TestNodePromptEndRunsWhileStartPromisePending` prove that admission does not await suspended completion.
Subprocess, packed, and fused extensions reach the terminal through the
subprocess UI bridge, which opens the scope when the dialog call arrives and
before it waits for terminal focus, because the extension already waits on the
user from that point. Interactive mode rebinds the bridge to the new runner on
reload.

Focused subprocess UI classifies wire traffic by semantics: input is an
ordered non-idempotent event, a rendered line set is a replaceable snapshot,
and open/result/cancel/error/close is a lifecycle barrier. Input and barriers
are never coalesced. Timer-driven render requests are coalesced to one pending
request and limited to the upstream TUI's 16 ms render interval. Input-driven
frames remain immediate. A snapshot is suppressed only when both its text and terminal width match the previous snapshot. Each published snapshot carries its terminal width (not the resolved overlay render width) and monotone sequence. The bridge rejects stale-width or out-of-order arrivals, and the UI cache checks terminal width again at paint time. The overlay key is the realization-local
generation and reload ownership includes the connection identity, preventing an
old runner from updating or closing its replacement.

Interactive dialog calls are awaited by the extension handler. The host installs
and mutates dialog components on the owning TUI loop while the subprocess call
waits off-loop. Selection/submission returns `ok=true`, Escape returns
`ok=false`, and host/transport failures use a protocol error rather than an
ambiguous empty success. Headless contexts return `ok=false` without opening a
surface. Go and Rust SDK methods return host errors explicitly; Python and Node
raise/reject them.

Interactive select/input key handling stays on the owner loop. upstream 0.99.1 `extension-selector.ts:96-113` resolves expansion, navigation, confirmation and cancellation in order; empty choices do not complete the request. `extension-input.ts:80-89` uses selection confirmation rather than the inner Input's independent submission action. The host's existing expansion callback runs before dialog completion. A positive `timeout` follows Pi's CountdownTimer (`countdown-timer.ts`, `extension-selector.ts:56-63`, `extension-input.ts:60-67`): the title shows the remaining seconds, each second runs on the owner loop, and the second that reaches zero cancels the dialog in the same turn, so the extension's awaited call resolves as a cancellation and no frame shows a zero countdown. An answer or cancellation disposes the countdown. `TestExtensionDialogTimeoutCountsDownAndCancels` and `TestExtensionDialogAnsweredBeforeTimeoutStopsCountdown` drive the owner loop, `TestExtensionDialogCountdownMatchesPi` compares the countdown frames with Pi's components, and `interactive-rendering/09-countdown-timer` compares the Node-to-host path with exact escaped output.

Autocomplete async contract: Pi `interactive-mode.ts:789-804,2567-2570` calls every factory synchronously while rebuilding, not per query. Node uses the restricted synchronous socket pump; native SDK handlers wait on their worker. The pump services sibling sockets in a packed Node cell without dispatching arbitrary asynchronous handlers reentrantly. Suggestions run off the TUI loop, serialize after prior queries, and carry cancellation. A forced suggestion Promise does not hold typing; only the synchronous trigger and completion callbacks hold input until their owner-loop effect applies. Callback errors propagate; rejected editor queries reach the uncaught-crash owner, while cancelled queries produce no error. Startup phases keep ordinary editor input live after managed-tool setup. Idle submissions queue until the initial prompts complete and the main consumer starts; the one-shot consumer resumes after the current terminal read's synchronous sequences, before the next read. Default and remote editors share that submit handler, including ECMAScript whitespace trimming. Loop exit clears the pending callback and queued prompts, and cancellation prevents another queued prompt from being admitted. Go's byte cursor becomes UTF-16 at the shared extension boundary. `SlashCommand.AwaitArgumentCompletions` represents Pi's Promise-returning callback separately from the existing immediate-return Go callback; each command binds one form. It returns a real first answer rather than a cache-miss stand-in. Reload and connection loss cancel owned work, remove factories and release captured providers. See `docs/findings/fix-rigidity-b.md` for red, mutation and resource evidence.

Native providers use the same serial worker and owner-publication boundary as extension providers. Synchronous native callbacks run on the owner loop; filesystem and awaited command callbacks run on the worker. ### Terminal string transport

Pi `stdin-buffer.ts:251` emits one UTF-16 unit for ordinary input. `tui.ts:1053-1068` passes each chunk unchanged through ordered listeners and applies their rewritten strings. The host and Go SDK share `extensions/sdk/json`, which uses the native `internal/jsstring` WTF-8 convention and writes unmatched units as standard JSON surrogate escapes. This shared codec covers terminal input, owner snapshots, editor/custom input, text getters/setters, completion and render-line carriers. The wire stays valid UTF-8 JSON; it carries no alternate string field or discriminator.

Rust terminal and focused-component callback data and terminal verdicts use `JsString(Vec<u16>)`. Raw request and custom-input notification arguments and typed call results avoid a `serde_json::Value` conversion before decoding those fields. `get_editor_text` returns `JsString`; setters accept `Into<JsString>`. Serialize lossless Rust values directly with `serde_json::to_string` or `to_vec`, not through `Value`. Python's existing JSON encoder and decoder preserve surrogate escapes. Node uses its native JSON implementation.

The existing awaited, ordered verdict contract is unchanged. No task, timeout, coalescing, or TUI-loop work is added. Codec buffers belong to the current bounded frame. `TestTerminalInputNodeSurrogateQualification` drives actual StdinBuffer events and Editor snapshots through Node. `TestConformance_TerminalInput` checks input, rewrites and callback-time editor text through every SDK, isolated/packed modes and fused Go. `56-terminal-surrogate-transport` compares the complete unit trace with pinned Pi. Pure Go, Python and Rust codec tests cover literal escapes, ordinary Unicode, unmatched halves and pairs.

## Performance and resource contract

The Node socket worker assembles each four-byte header and bounded frame body with linear copying. It parses only complete JSON frames, answers heartbeat on the worker, and retains the existing unread-byte backpressure and socket-error boundary. Assembly adds no task or callback boundary. `TestNodeProviderSocketFrameCopyIsLinear` drives the real worker with fragmented Unicode payloads and a heartbeat; `TestNodeFrameBufferPreservesEveryFragmentBoundary` covers all split positions, empty bodies, the exact size limit, oversized headers, and consumer failure. `TestNodeProviderSocketRejectsBadFrameBeforeNextEnvelope` checks the actual worker's parser/size errors and failure ordering before a following envelope.

Extension parity includes latency/resource behavior at the TUI and lifecycle
boundaries; green payload conformance alone is insufficient. The foundation P6
matrix covers the concrete in-process reference, D31 fused path,
packed subprocess cells, and isolated subprocesses.

- `Render` and input-loop callbacks must not perform blocking extension IPC,
  filesystem/network work, or unbounded transcript traversal.
- Session history stays unloaded until first use. A persisted session is read
  locally by the isolated runtime, then reconciled with the host cursor. Missing
  history and later appends cross the socket in ordered pages no larger than 4 MB.
- Renderer/widget/overlay caching must preserve width, expansion, invalidation,
  ordering, disconnect, timeout, fallback/error, and exact terminal bytes.
- Registration, host-call, event, tool/update, cancellation, reload, quarantine,
  fission, and shutdown paths require representative latency/allocation and
  goroutine/fd/process/memory-lifetime evidence.
- Packed/fused optimization must remain observationally identical to isolated realizations of the current subprocess wire. The host currently serializes extension dialogs and custom overlays without blocking the TUI loop. Floating-overlay serialization is a known parity bug, not the upstream contract; see [overlay release gap](findings/fix-overlay-shim.md). Waiting calls are cancellation-aware. A faster fused realization cannot create a second SDK or skip protocol/conformance semantics.
- The broad `coding/extension.API` interface is not accepted merely because it
  mirrors this document: it needs a production reference implementation/caller
  or deletion under P0/P2. The concrete `*sdk.Extension` author surface remains
  the current production Go factory API.

Current focused-component rendering is cache-backed on the host. The TUI render
loop performs no extension IPC or JSON work. Go/Rust/Python component workers
serialize input and render callbacks away from each SDK dispatcher. Node uses a
bounded 16 ms scheduler and socket backpressure. Isolated, packed, and fused
lifecycle tests cover the current contract.

## High-risk parity areas

These areas need design before they can be marked complete.

### Custom TUI components

Upstream Pi passes in-process TUI components. Pig subprocesses cannot pass Go component objects across process boundaries. Pig needs a declarative component protocol, a restricted built-in component registry, or a numbered divergence.

### Tool and message renderers

Message renderers are production-bound. In-process Go renderers return TUI
components. Subprocess Go/Rust/Python/Node renderers return lines through an
owned background request; the TUI component reads only a generation-checked
cache and retains a visible default fallback on startup, timeout, disconnect,
or invalid output. Width, expanded-state, and output-padding changes replace stale generations. Upstream message renderer callbacks are synchronous. The subprocess bridge awaits their result on the owned request worker; a padding change uses the existing single-flight generation loop and never waits on the TUI loop. It retains the last completed frame until a current result arrives, rejects stale results, and preserves the existing cancellation/error/shutdown ownership.
`BenchmarkRenderProxyCached` measures about 17 ns/op and one 16-byte defensive
slice-copy allocation on the recorded M4 Pro; no socket or JSON work runs in
`Render`. Tool-call renderers remain a separate surface.

### Provider registration and custom streaming

Initially registered custom stream producers and raw native Provider objects retain distinct payloads in the one current wire contract. Producer callbacks use `provider_stream_simple`; native object methods use `provider_stream`. Both share the event decoder and option encoding, retaining explicit numeric presence and raw thinking fields. Metadata lookup and active Session refresh use catalog's shared auth-free composition path. Runtime registration, queue/bind behavior and D78 closure remain separately tracked.

### Extension CLI flags

Upstream Pi extensions register flags during load. Pig subprocess extensions require registration inspection before CLI parsing to expose flags in time.

### upstream 0.99.1 extension API fidelity

Factory-time MCP registry calls and virtual-model unregistration: upstream 0.99.1 `loader.ts:456-478` validates a registration and checks name ownership when `registerMcpServer` is called and throws to the factory. `getMcpServers()` returns the live registry. `loader.ts:228-232` makes a pre-bind `unregisterVirtualModel` filter the runtime-wide pending queue. The Node runtime does the first two through two calls the host answers before the register frame: `mcpServers.check` (validation and ownership, no commit) and `getMcpServers`; the register frame still commits what the factory registered. The Go, Rust and Python SDKs have no factory-time Pi object: `RegisterMcpServer` is an `Extension` method that queues before `Run`, the host validates the queue when the extension registers, and `GetMcpServers` exists on the Context only. They open no connection before `Run`, and a fused Piglet Binary receives its pipe in `RunWithConn`, so a native factory cannot catch a registration error and keep loading. All four SDKs send `unregister_virtual_models` in the register frame, and the host applies it to the runtime-wide queue before the extension's own virtual models and after the frame's MCP servers passed: a server the host rejects is Pi's throw from `registerMcpServer` inside the factory, which discards every queued change (`loader.ts:512-527`). Tests: `TestNodeFactoryMcpRegistrationThrowsInsideTheFactory`, `TestNodeGetMcpServersInsideTheFactoryListsTheLiveRegistry`, the `Unregister...BeforeBind...` rows of each SDK, and `TestRegisterExtensionAPIRejectedMcpServerLeavesAnotherExtensionsQueuedVirtualModel`.

Router state identity, `ctx.tools` and nested-call updates: `agent-session.ts:788` stores a router's state unless `route.state === request.state`, which is object identity. Node replies `stateUnchanged` when it observes identity, and the host trusts only that reply for a Node extension, so a fresh object stays a new state as in Pi. The host compares the JSON values for the other SDKs, which cannot express identity, and answers the session with the request's own bytes, so the encoder's escapes, spacing and key order never read as a change. The session compares the bytes it receives with the bytes it sent, so a Node router's fresh object whose `JSON.stringify` bytes equal the stored state's bytes is stored by Pi and skipped here. `runner.ts:958-961` reads the callable tools when the getter is read: every SDK calls `getCallableTools`, and the state snapshot no longer carries them. `nested-tool-calls.ts:219-248` and `agent-loop.ts:820-849`: `execute_tool_update` is a request the host waits on. An exception, panic or throw from `onUpdate` is the answer. The host skips that update's `tool_execution_update` event, sends the later updates, and rejects the call with the first error after the tool returned, with no `afterToolCall`, no `tool_execution_end` and no recorded result. `ExecuteTool` actions, `NestedToolCallRunner.Execute` and `agent.RunToolCall` return that error. Tests: the `...RouterReturningItsRequestState...` rows of each SDK, `TestNodeVirtualModelRouterReturningAFreshEqualStateIsStored`, `...CtxToolsIsLive...` and `...OnUpdate...Rejects...` rows of each SDK, `TestRunToolCall_RejectsWithTheFirstUpdateSinkErrorAndSkipsAfterToolCall`, `TestNestedToolCallRunnerUpdateCallbackFailureRejectsTheCallBeforeItsEndAndAfterHook` and the real-binary `TestExtensionToolContextIsWiredInEveryMode`.

Host calls that outlive their request's response: Pi's host calls run in the extension's own process and belong to no request. `loader.ts` `createExtensionRuntime` has no request scope, and `interactive-mode.ts:2858-2940` settles a custom UI call only through its own completion, so a handler that starts a call without awaiting it and returns leaves the call running, and only the call's own `AbortSignal` ends it. The Node runtime follows this since #103. The Go, Rust and Python SDKs now follow it too: a response no longer cancels the pending calls of its request, so a goroutine or thread the handler started still receives the host's result. The Go wait hands over from the request's context, which ends with the handler, to the runtime's context once the request completed, and all three SDKs detach the completed request's pending calls from it so a later cancel frame for that request does not reach them. A cancel frame for a request that has not completed still cancels its calls, and a call started after completion is unscoped, as before. Tests: `TestExtensionAPIHostCallStartedByAHandlerOutlivesItsResponseGo`, `TestRustSDKHostCallStartedByAHandlerOutlivesItsResponse`, `TestPythonSDKHostCallStartedByAHandlerOutlivesItsResponse`, `TestCompletingContextLeavesUnsettledParentCallRunning` and `TestNodeCommandReturnDoesNotCancelItsHostCalls`.

## Completion rule

A row moves to `complete` only when:

```text
1. upstream behavior has been read and summarized in a test comment or doc row;
2. Pig protocol and SDK expose an equivalent;
3. at least one conformance test exercises the production path;
4. packed and isolated subprocess modes preserve the same semantics when relevant;

```

## Provider response and tool-prompt evidence

Pi, then pinned at 0.87.1, was probed with `extensions-runtime/50-after-provider-response` and `51-tool-prompt-contributions`. Both scenarios failed on the unmodified host and pass three exact-output pairs after the fix. The response mutation disconnects `StreamOptions.OnResponse` in the Session stream function and makes `TestAfterProviderResponseSession` fail before its first delta. The snippet mutation drops `ToolDef.PromptSnippet` in the subprocess registration bridge and makes the Go and Node cases of `TestProviderResponseAndToolPromptsAcrossSDKs` fail with `(none)` in the provider's tools section. The production conformance row covers all four SDKs, packed Node, and fused Go. `TestPackedProviderResponseAndToolPrompts` covers packed Go, Rust and Python.

On Linux amd64 with Go 1.27.1 and an Intel Xeon 6746E, `BenchmarkProviderResponseObserver` measured 680 ns/op, 408 B/op and 6 allocations for four headers. `BenchmarkToolPromptContributions` measured 12 µs/11 KB for 8 tools, 158 µs/129 KB for 128 tools, and 1.31 ms/1.11 MB for 1,024 tools. CPU and allocation profiles identify prompt string construction, metadata maps and garbage collection as the costs. These are construction costs, not per-frame costs: interactive prompt reads use the cached string. Response observers create no detached task, use request cancellation, and complete before stream consumption. Rejection closes the response body and Bedrock event stream. Existing extension request ownership drains subprocess handlers; reload resolves the current runner on the next callback. Run `go test ./ai -run '^$' -bench BenchmarkProviderResponseObserver -benchmem` and `go test ./internal/codingagent/prompts -run '^$' -bench BenchmarkToolPromptContributions -benchmem` to repeat the measurements.

## SDK coverage matrix

`docs/extension-sdk-surface.md` is the authoritative per-runtime matrix. It is
generated by `go run ./test/parity/cmd/sdksurface` from Pi's extension declarations
and each runtime's source, and it records every surface symbol by symbol for
the Node runtime, Go, Rust, and Python. Each missing cell is listed with its
reason in `test/parity/sdk-surface-exceptions.toml`. `go test ./test/parity/cmd/sdksurface`
fails on an unlisted gap, and `make sdk-surface-drift` fails when the generated
file is stale.

The wire protocol carries each surface for every SDK that realizes it. The
conformance suite compares the in-process Go reference with the Go,
Node/TypeScript, Rust, and Python subprocess runtimes. Future additions must
land in all applicable SDKs or record the gap in
`test/parity/sdk-surface-exceptions.toml` in the same change.
