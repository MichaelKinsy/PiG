# bench/evals: reproducible benchmarks for PiG

Every number we publish about PiG, its stripped Piglets and its optimisations comes from a command here, with a recorded seed, against exactly pinned arms. `make bench-<name>` writes `raw.json`, `summary.csv` and `report.md` under `tmp/bench/<name>/`.

| command | what it measures | spends money |
|---|---|---|
| `make bench-overhead` | startup, first request, first frame, harness CPU and added latency per turn, peak RSS, binary size; print, PTY, RPC, 10 extensions, 1,000-turn session with compaction | no |
| `make bench-reliability` | HTTP 429/500, mid-stream and pre-response disconnects, kill mid-tool-call and resume, SIGTERM mid-stream; pass or fail per fault per arm | no |
| `make bench-soak` | scripted RPC turns for `BENCH_SOAK_HOURS` (default 24) on PiG and Pi at once; processes, threads, descriptors, RSS and PSS sampled each interval; a run whose second half is too short to judge is `undecided`, never flat | no |
| `make bench-longhistory` | sessions of ~1M tokens, and ~3M tokens across 3 compactions: open, `/resume`, RSS, keystroke and frame time, resize redraw, append cost | no |
| `make bench-durable` | the durable-bench workload (50/250/1000/3500 turns) on PiG Durable and pi-durable | no |
| `make bench-harbor` | writes and validates Harbor job configs; checks Harbor's Pi converter against PiG; **runs no job** | no |
| `harbor-analyze` | paired analysis of finished Harbor jobs: SWE-bench Pro, Terminal-Bench 2.1 | the jobs it reads did |

Only task-completion benchmarks (SWE-bench Pro, Terminal-Bench) may use a live API key, and only after an explicit decision to spend it. Every other bench runs with **no live key and no vendor login**: each arm points at a local mock endpoint with a dummy key, in an isolated `HOME` with no credentials. A CLI that refuses to run headless without a real login is excluded from that bench and the report states the exact error. A socket audit (below) fails the bench if any harness connects outside the loopback.

## Arms and the lock file

`arms.lock` pins every arm: exact version, source, and checksums. `arms.toml` says how to run each one. The lock is JSON, regenerated by one command, and its SHA-256 is printed in every report.

| arm | version | source |
|---|---|---|
| `pig-0.5` | 0.5.0 line | built from this checkout (`go build`, stripped, like `make install`); the commit is in the report |
| `pig-core`, `pig-min` | 0.5.0 line | stripped Piglet Binaries built from this checkout (`piglets/`) |
| `pig-0.4.1` | 0.4.1 | GitHub release asset, SHA-256 from the release's `SHA256SUMS` |
| `pi-1.1.0` | 1.1.0 | npm registry, `npm ci --ignore-scripts` from `locks/pi-1.1.0.package-lock.json` |
| `claude` | Claude Code 2.1.296 | npm registry, platform binary package, locked |
| `codex` | Codex CLI 0.162.1 | npm registry, platform binary package, locked |
| `copilot` | Copilot CLI 1.0.95 | npm registry, platform binary package, locked |

Each bench installs the arms it needs into a throwaway directory (`npm ci --ignore-scripts` with the npm cache inside it, or the release archive), checks the package-lock hash, the primary tarball's SRI integrity, the installed version and the `--version` output, runs with `HOME`, config and cache directories inside it, and deletes it. A mismatch stops the bench. Nothing is committed but the lock and the package-lock files; third-party binaries are never redistributed. `PIGBENCH_BIN_<ARM>` overrides one arm's binary for development; the report marks it **not pinned**.

```sh
make bench-lock-verify                              # lock against its committed package-lock files; BENCH_ONLINE=1 re-downloads tarballs
make bench-lock-bump ARM=codex VERSION=0.163.0      # one command: new integrity, tarball sha256, package-lock, executable hash
make bench-arms                                     # install every arm, verify, delete
```

Licences, as the report records them: Pi (MIT), PiG (MIT), Codex CLI (Apache-2.0); Claude Code is proprietary (Anthropic's legal agreements apply) and Copilot CLI is under the GitHub Copilot CLI License (redistribution only unmodified). We run the registry tarballs unmodified and do not commit or redistribute them.

## The ten extensions in every realization

`rpc-ext10` and `print-ext10` load ten identical extensions (`fixtures/extensions/bench-ext-NN.ts`: a tool, a command and four event handlers). `fixtures/extensions-go/` is the Go SDK port of the same ten, so one scenario measures the same extensions in each way PiG can run them:

| realization | source | how PiG runs it |
|---|---|---|
| Node, packed cell (the default for TypeScript factories) | `extensions/bench-ext-NN.ts` | one Node process hosts all ten |
| Bun, Node-compatible slot | the same files, `PIG_TS_RUNTIME=bun` | one Bun process |
| Go, isolated | `extensions-go/standalone/bench-ext-NN` (exact `package main` modules) | ten Go processes |
| Go, packed cell | `extensions-go/factory/bench-ext-NN` (`func Extension() *sdk.Extension`) | one generated Go runner |
| Go, fused | `extensions-go/pig-ext10.yaml` (`pig piglet build --format binary`, set `PIG_SOURCE_ROOT` to a PiG checkout) | compiled into the PiG executable: no extension process, no IPC |

PiG has no setting that isolates a TypeScript or Go *factory*: factories pack, and only an exact standalone is isolated. All three Go sets share one body (`extensions-go/benchext`). `TestBenchExt10GoPortsRegisterWhatTheTypeScriptOriginalsRegister` (`coding/cli`) checks, through `pig install --validate-only`, that each Go set registers what the TypeScript set registers; Buffon ([github.com/MichaelKinsy/buffon](https://github.com/MichaelKinsy/buffon), arms `pig-ts-node`, `pig-ts-bun`, `pig-go-*`) also compares the tool results of every arm before it times anything.

## Rust arm and metric endpoints

The overhead bench reports the endpoints of the Go-versus-Rust protocol: `--version` exec-to-exit (`version` wall), spawn to the first answered RPC command (`rpc` `ready_ms`), first frame and first accepted input in a PTY (`first_frame_ms`, `first_input_accepted_ms`: a key is typed every 40 ms from the first frame and the first echo counts), RSS and PSS at ready (`ready_rss_mib`, `ready_pss_mib`: PSS from `smaps_rollup` summed over the cgroup), and peak (`peak_rss_mib`, cgroup `memory.peak`). A report lists the ratio of medians against Pi with a 95% bootstrap interval for every metric, the ones PiG loses included. `--aa pig-0.5 pi-1.1.0` runs a second copy of an arm (`-b`, same binary, own home) and reports the A/A noise floor with a declared equivalence margin of +-5%. Interleaved runs: `make bench-overhead BENCH_ARMS="pig-0.5 pig-0.4.1 pi-1.1.0 rpi codex" BENCH_OVERHEAD_ARGS="--scenarios version rpc pty --runs 20 --aa pig-0.5 pi-1.1.0"`. Not done yet: tuned Rust and PGO Go builds (2x2), hyperfine, and the `pty` scenario on Windows (`WINDOWS.md`). pi_agent_rust is not an arm until its licence is decided; it also ignored typed keys on a pseudo-terminal in this harness. A build of a competitor uses its own release flags, never PiG's.

## Several machines, one report

`make bench-aggregate DIRS="<dir> <dir> ..."` (or `python3 -m pigbench aggregate <dir>...`) reads the `raw.json` of overhead and startup runs from different machines and writes one report: a machines table, a summary of PiG 0.5 against Pi on each architecture (`linux-x64`, `linux-arm64`, `darwin-arm64`, `windows-x64`, taken from each run's environment block) as ratios of medians with 95% bootstrap intervals, absolute medians side by side, per-architecture tables, and the scenarios or arms missing on an architecture. A startup run's samples form the scenario `version (hyperfine)`, apart from the overhead bench's `version`, because the two measure with different meters. Runs of one machine (same architecture, OS, CPU model, logical CPUs and memory) share a column; a second machine of the same architecture gets its own column (`linux-x64 #2`). Ratios are formed only within one machine; absolute numbers of different hardware are shown and never ranked. Other run kinds are refused. The runs must share one commit and one `arms.lock` hash, or the command refuses unless `--allow-mixed` is given, which the report then states. On Windows the meter is a Job Object and release assets are zip archives; the bench has no ConPTY driver, so the PTY scenarios do not run there (`WINDOWS.md`).

## Method in brief

* **Mock endpoint** (`pigbench/mock.py`): OpenAI Chat Completions, OpenAI Responses and Anthropic Messages, scripted by a policy (a read tool call, then text; a request with no tools is a compaction and gets text). It stamps every request's arrival and reply end, and injects HTTP errors and dropped streams. The model's tool call is built from whatever read or shell tool the request declares, so Pi, PiG, Claude Code, Codex and Copilot each receive a call to a tool they have.
* **Meter** (`pigbench/cgroup.py`): each harness tree runs in its own cgroup v2, read for CPU (`cpu.stat`) and `memory.peak`, with the tree's resident set sampled every 25 ms. Modes: a delegated cgroup directly, a transient `systemd-run --user --scope`, or, with neither (macOS), `wait4` rusage plus `/proc` or `ps` samples. The mode is in the report. `cgroup.kill` ends a tree without matching names.
* **Arms are interleaved**: every repetition rotates the arm order. Warm-up repetitions are dropped. A cell is the median with a 95% percentile-bootstrap interval, seeded.
* **Egress** (`pigbench/egress.py`): inside an isolated network namespace egress is impossible by construction and the report says so. Otherwise each harness tree's sockets are read from `/proc` every 25 ms and any connected non-loopback socket fails the run and the bench. A connection shorter than 25 ms can be missed; for a strict run use `docker run --network none` or `unshare --net`. Finding this way: Codex 0.162 contacts chatgpt.com and github.com at startup even with a custom provider unless its plugin and remote-catalog features are off, so the bench turns them off in its config and says so.
* **Statistics** (`pigbench/stats.py`): paired task-level bootstrap and sign-flip, exact McNemar, TOST with a declared margin for parity claims, ratio of totals plus geometric mean for cost and time, Holm across arms, A/A noise floor. Resampling is by task, never trial. Blog figures use the qualitative labels in the report (`much lower`, `about the same`, ...), only where the intervals do not overlap; overlapping intervals are labeled `inconclusive`, never `about the same`, because a parity claim needs TOST with a declared margin.

## Long history: what Pi 1.1.0 does (upstream v1.1.0)

* The session file keeps every entry. It is appended per entry (`coding-agent/src/core/session-manager.ts:1187`) and read whole on open and resume (`:627`).
* The TUI renders only the model context, not the file: `buildContextEntries` (`session-manager.ts:476-510`) returns the latest compaction plus the entries from `firstKeptEntryId` on; `renderInitialMessages` (`modes/interactive/interactive-mode.ts:4208`) draws it on startup and, via `renderCurrentSessionState` (`:2212-2218`), on `/resume`. After a compaction `compaction_end` (`:3686-3711`) clears the chat container and re-renders the context entries, so earlier messages leave the transcript. A 3M-token session with 3 compactions therefore shows Pi only the last summary, its kept entries and what followed; open, resume and append still read the whole file, so those phases run at the full 3M.
* The default `tuiMode` is `fullscreen` (`core/settings-manager.ts:1372`): an alternate screen, so there is no terminal scrollback while the session runs, and a width or height change redraws only the visible rows (`tui/src/tui-alt-screen.ts:1701-1702`). But `ScrollView.render` renders the entire child every frame (`tui/src/components/scroll-view.ts:215-217`), so per-width caches are invalidated on a width change and the whole transcript is laid out again: that is the cost the bench measures. In `regular` mode a width change is `fullRender(true)` (`tui/src/tui-main-screen.ts:337-341`) and a height change likewise (`:344-350`): ESC[2J ESC[H **ESC[3J** (the scrollback is cleared) followed by every line of the transcript. Earlier messages stay in terminal scrollback only until such a redraw.
* The bench runs both modes. It records whether each resize cleared the scrollback and how many bytes it wrote, for every arm.

The synthetic sessions (`pigbench/longhistory.py`) are generated from the seed (the digest is in the report): per turn a question, a `read` call, a 2.5-5.5 KB result and an answer, until the case's token budget (characters / 4), with a compaction entry that keeps the last 20k tokens when the case has one. `1m` is one 1M-token segment with no compaction; `3m` is three 1M-token segments, each followed by a compaction, then a 60k-token tail.

On Kubernetes, `pigbench/k8s.py` runs the same measurement as `bench/k8s`' built-in `longhistory` profile: `pigbench k8s generate` builds a case's session (the same history for a seed as this bench; its fingerprint is this bench's digest with `TMPDIR` at `/tmp`, wherever the pod writes it), and `pigbench k8s sample` measures one agent on a copy of it in fresh processes and prints one k8sbench result line. See [Running PiG benchmarks on Kubernetes](../../docs/site/docs/benchmarking.md). `pigbench k8s overhead-seed` and `overhead-sample` do the same for this bench's overhead scenarios (`version`, `print`, `print-tools`, `rpc`, `pty`; the built-in profiles `overhead-pi`, `overhead-codex` and `overhead-rpi`; `--arm <id>` measures an `arms.toml` arm with its harness settings): one sample is each scenario in a fresh process, and the line's `open` and `turn[]` are `print-tools`' first request and per-turn gaps.

## Durable

`workloads/durable-bench.json` states the workload of durable-bench (github.com/clavia-labs/durable-bench: no licence found, so the method is re-implemented and no code is copied), as durable-report (`bench/durable/report`) measured and reproduced it: a scripted model that calls `lookup` for the number of tools planned in the user message; histories of 50/250/1000/3500 turns planning `[1, 1, 0]` tools in turn; ten measured turns of eight tool calls on a fresh copy of the seeded store; cold = open plus the first measured turn; warm = the nine following turns of every sample, **pooled** (the median of the pooled turns, not a median of per-sample medians); and the CPU-idle gate (busy fraction at most 8% over one second before each sample, reading recorded). The seeded histories must reproduce the four published fingerprints (`b017b487524e44a4`, `dcea9f30b0917245`, `ac520308146f2a8f`, `0a8c8e4b0d9a0794`), and the transcripts after the measured turns must agree between the runtimes, or the run fails.

Reporting follows durable-report's rules: rounds are the outer loop and sizes the inner one (rotated), the two runtimes alternate in order every round, the report gives p50, p95 and max of the pooled warm turns with a bootstrap interval, marks a cell with fewer than 100 warm turns as below the rule (`--rounds 12` gives 108), and gives a verdict on the same-session ratio: loss above 1.03, win at 1.3x or better, slightly better below 0.97, otherwise a tie. The runners are `bench/durableperf` (PiG, Go) and `durable/interop/bench.mjs` (pi-durable on Node); each sample is a fresh process, pinned with `taskset -c` when `--cpus` is given. Not measured here: the empty-target floor and retained heap, which belong to the Miniflare runner (`bench/durable/report/runner`) and to k8sbench's `durable-core` profile; use those for the Durable Object path and for a pod. A bench tool that returns `content` where Pi main expects `output` (pi-mono eba84973) gets empty tool results; the pinned pi-durable predates that rename, and the fingerprint checks catch a drift. Only PiG and pi-durable are arms here: the CLIs have no Durable layer.

## Harbor (prepared, not run)

`pigharbor/agents.py` holds `PigAgent`, a subclass of Harbor's `Pi` adapter (`harbor/agents/installed/pi.py`, Harbor 0.24.0), and `CopilotByokAgent`, a subclass of `CopilotCli` (`copilot_cli.py`). Harbor 0.24.0 also ships adapters for Claude Code (`claude_code.py`) and Codex (`codex.py`); they run pinned through `kwargs.version`. Harbor's Pi adapter runs `pi --print --mode json --session-dir <logs>/pi/sessions --provider P --model M <instruction>` and converts the session JSONL's `usage` fields (`input`, `output`, `cacheRead`, `cacheWrite`, `reasoning`, `totalTokens`, `cost`) into its trajectory and accounting. For a custom endpoint (every planned job goes through the metering gateway) the adapter writes `models.json` with a `harbor-endpoint` provider whose `apiKey` references a variable, into the directory `PI_CODING_AGENT_DIR` names. `make bench-harbor` runs PiG 0.5.0, PiG 0.4.1 and Pi 1.1.0 with exactly those flags and that configuration against the mock, checks that every request carries the referenced key, and feeds their logs to Harbor's own converter. PiG reads `PIG_CODING_AGENT_DIR`, not `PI_CODING_AGENT_DIR` (PiG divergence D2), so on its own it fails with `Unknown provider "harbor-endpoint"`; `PigAgent` therefore sets `PIG_USE_PI_DIRS=1`, D2's switch to Pi's directories, on every command and puts a pinned PiG on `PATH` as `pi`. With that, PiG matches Pi on events, usage keys, trajectory steps and metric keys, and PiG itself needs no change. Harbor's Copilot adapter forwards only a GitHub token (`copilot_cli.py`, `run`), so `CopilotByokAgent` adds the BYOK variables from the host environment to every command; the key is not written to disk.

`harbor-plan` writes one job per pairing and dataset (`tmp/bench/harbor/jobs/*.json`), validated with Harbor's `JobConfig`: PiG 0.5.0, PiG 0.4.1, Pi 1.1.0 and Copilot against Claude Code on one Claude snapshot, and the same arms against Codex on one GPT snapshot; SWE-bench Pro public split at k=3 and Terminal-Bench 2.1 at k=5; plus a Pi-vs-Pi A/A job per dataset (same configuration, labels `pi-a` and `pi-b`). Every agent may reach only the metering gateway (`extra_allowed_hosts`); `pigbench/gateway.py` is that gateway, one base URL per arm, which swaps in the real key from the host environment and logs tokens, latency and failures per request. Every agent config carries a placeholder key (`GATEWAY_PLACEHOLDER_KEY` in `pigbench/harbor.py`) under its provider's key variable: Harbor's Pi adapter rejects a custom endpoint without one, and without it Harbor would resolve the key from the host environment and pass the real key into the task container. Keep the real key in the gateway's environment only. Confirm before the first run: the Harbor registry names of the datasets (`DATASETS` in `pigbench/harbor.py`), that the SWE-bench Pro task images are history-pruned, and that the tasks' `network_mode` is `allowlist` or `no-network`.

arXiv 2610.00917's released Pi adapter (`github.com/liyix/finding-the-right-fit`, Apache-2.0) is an ALE-CLI deployer, `integrations/ale_agents/study_pi/` (Pi 0.84.4 plus a `cua-extension.mjs`), not a Harbor adapter, so it cannot be reused here; Harbor's own `pi` adapter is the base. `harbor-analyze` reads finished job directories and reports, per arm, the infrastructure-error rate, the paired differences with Holm, TOST parity at the declared margin, cost and time as ratios of totals, and the A/A floor. A parity claim means parity on the test-passing rate, not on patch quality.

Running a job: `HARBOR_PYTHON=<python with harbor==0.24.0> make bench-harbor`, then `harbor run -c <config>` with the gateway up, after an explicit decision to spend. Nothing in this directory starts one.

## Tests

`make bench-test` runs stub harnesses whose timing is known by construction (a first request after exactly 0.4 s, a tool that takes 50 ms), checks the cgroup CPU and memory readings against known loads, asserts the egress audit fires on a connection to a non-routable address, checks the statistics against textbook values, detects a tampered lock, and includes negative controls for the reliability judge.

macOS: the rusage meter and the `ps` parser are covered by unit tests on Linux only; the PTY and cgroup paths have not been run on macOS.

## Build variants (the 2x2)

`pig-0.5` is built from this checkout with `-pgo=off` (a stray `default.pgo` cannot change a measurement). `pig-0.5-pgo` is the same checkout built with the locked profile `locks/pig-0.5.pgo` (a merged CPU profile of 20 `pigeval profile` round trips, 21 KB; `make pgo` writes `tmp/pgo/default.pgo`, which is copied here and its sha256 relocked). The lock records the profile's sha256 and `lock verify` rejects a mismatch. Result of the first comparison (provisional: 12 runs per arm, version/print/rpc, with an A/A copy of the default build as the noise floor, on a shared host at load average 341 with the arm's code not yet committed; raw output not committed): the profile-guided build is indistinguishable from the default build on every metric, and its binary is 20 KB larger (68,198,560 vs 68,178,080 bytes). A profile taken from short start-up round trips does not change inlining enough to move any number; a larger scripted session profile is the next experiment, and this arm is a measurement arm, not a shipped build.

### Any build as an arm: `variants`

`python3 -m pigbench variants --arm <id>=<path>[,flag...] ... --scenarios version print rpc --runs 12 --out DIR` runs the overhead scenarios on executables you built yourself: a profile-guided or `GOAMD64=v3` build, a stripped Piglet Binary, a Go-fused extension Piglet, or one binary under another `GOGC`. Every arm runs beside an A/A copy of itself (`<id>-b`: same executable and settings, its own home), arms rotate each repetition, and `variants.md` lists each variant's median, its copy's median and the difference between the two, which is the noise floor of that cell. `variants.json` records each executable's SHA-256, size and environment. Arms are unpinned and the harness says so.

Flags after the path: `noext` (the build cannot load extensions, so the extension scenarios skip it), `own` (the build carries its own extensions, so `print-ext10` and `rpc-ext10` install no TypeScript fixtures and still check that the first request declares the ten tools), and `K=V` (an environment variable for that arm; the harness drops inherited `PIG_` variables, so put a `PIG_` setting here). `--env K=V` applies to every arm. A bench run on a shared host still goes through `lane-run --bench`.

The Rust half (the competitor's tuned release flags versus its published release) is not built: competitors run as their release builds, and a source rebuild of rpi with `-C target-cpu=native`, fat LTO and one codegen unit needs the cargo toolchain and a declared flag set in `arms.lock`.
