# Host protocol: what the hosts send and expect beyond ABI.md

Status: ratified, 2026-10-07, by the integrator (dcore-int) for the production core; written by dcore-host and dcore-cfhost. ABI.md fixes the event, effect and notice kinds, the binary layouts and the `api` table (section 8.1). It leaves the JSON payload bodies of most events to the core. This file is the bodies the hosts in this repository (`host/cf/src`, `sqlhost`) send and the core reads. A hosts-versus-core disagreement is a bug in whichever side departs from this file. A change to a body is a seam change: the integrator edits this file and merges it forward. `abi_id` does not cover these bodies.

Code of record: `host/cf/src/protocol.ts` (shapes), `host/cf/src/effects.ts` (effects), `host/cf/src/facade/` (events and transactions).

## Events

| event | body | notes |
|---|---|---|
| `open` | `{mode: "harness" or "session", settings, models, registry, sidecar, delta, hasEnv, storageProfile?}` | `settings` is `HarnessSettings` over its defaults, `extensions` as names. `models` is the catalogue entries the host lets the core name (default: every model the `models` object lists). `registry` is the snapshot below. `mode: "session"` opens the tables-and-documents Session of `createSession`: no built-in documents, no scheduler |
| `registry` | `{registry}` | a registry publication after open (extension reload) |
| `seal` | none | ABI event 19, sent synchronously by `Harness.close()` before anything else: the core runs what Pi's close listeners run at `session.close()` (scheduler `#seal`) while admitted work continues; the terminal `close` follows |
| `resume` | none | ABI event 17, sent once by the first call that asks for progress (`resume()`, `submit`, `compact`, `abort`, the waits): scheduling stays paused until the host says `resume` |
| `submit` | `{id, conversationId, type: "input" (content, and entry: the `{kind, data?}` it is placed as instead of `pi.user`) or "write" (entry), requestId, whenBusy?, invocation?}` | `id` is a number the host allocates; the core answers with an `api_result` notice for `id`: `{ok: {id: submissionId}}` once the admitting commit is applied (after that commit's `published` notice), or `{error: {name, message}}` (`ConversationBusy` for whenBusy `reject`). The core runs the admission when the Session line is free, so the answer may follow later steps. The host always sends a `requestId` (a minted UUID when the caller gave none); a known `requestId` returns its submission without a commit |
| `abort` | `{requestId, conversationId?, background?}` or `{requestId, taskId, keepRestart?}` (`keepRestart`: a task marked with abortReason `restart` keeps its mark and waits on, as for an owner's own cleanup; otherwise a request replaces the mark) or `{requestId, submissionId, conversationId?}` (`requestId` here is the numeric api_result key) | the core answers with an `api_result` notice carrying `requestId`: `"marked" or "terminal"` for a task, `"aborted", "already_placed", "settled" or "not_found"` for a submission, `null` for a conversation |
| `inspect` | `{query: "harness", requestId}` | `HarnessInspection`: scheduling state, live tasks with their scheduler state, unsettled submissions. Answer: `api_result` with `requestId` |
| `tx` | `u32 txId` then `{op, ...}` | section 8. `begin` carries `{invocation?, conversationId?}` |

### Registry snapshot (`open.registry`, `registry.registry`)

`{extensions: [{name, tools, sections, hooks, wraps, tasks}]}` in installation order. Every `handler` is an index into the host's append-only function table: an index never changes meaning, so an effect issued under an older snapshot still resolves after a reload.

- tool: `{name, description, parameters, replay, handler, executionMode?, outputLimits?, prepare?}`
- section: `{key, tag, handler}`
- hook: `{task, handlers: {hookName: handler}}`
- wrap: `{tool, handler}` or `{section, handler}`
- task: `{name, version, phases: [names], abort: bool, handler}`

## Transactions (ABI section 8)

Operations carry the `Tx` method name and a JSON object of its arguments. An absent record is `null` on the wire and `undefined` in the host.

`conversation{id}`, `entry{id | kind,id}`, `task{id}`, `scanConversations`, `scanEntries`, `latestHeadMarker`, `scanTasks`, `submissionByRequest`, `createRootConversation`, `createConversation{ownership}`, `forkConversation{parentConversationId, at, ownership}`, `appendEntry{conversationId, kind?, value}`, `createTask{task, version, state?, input, options}` (the host computes `initial(input)` for a task whose definition it holds; `state` is absent for the built-in tasks `generation`, `tool` and `compaction`, whose first checkpoint the core builds), `createSubmission`, `settleSubmission`, `placeSubmission`, `doc{address, def, version, seed?, initial?, migrated?}` (answer `{value, deltasSinceBase?}`), `doc.write{address, def, ops, baseRevision, checkpoint?}` (Chord `Op[]` from `@earendil-works/chord/delta`, sent for every changed draft before `end`), `retireDoc{address, def}`, `end{state?}`, `abort{error}`.

Document operations carry `def`, the data fields of the definition: `{kind, version, scope, history?, fork?, family?}`. The definition's functions run in the host. When `doc` needs a value only they compute, the core answers `{need: "initial"}` (an absent document: the host sends `initial`, the value of `initial(seed)`) or `{need: "migrate", value, from}` (a stored version older than `def.version`: the host sends `migrated`, the value of `migrate(value, from)`), and the host repeats the operation with the value added. `deltasSinceBase` is present when the document was stored; the host then evaluates `checkpointWhen(value, ops, {deltasSinceBase})` on its prepared draft and sends `checkpoint: true` with `doc.write` when it holds. The api reads `snapshot{doc, def}`, `snapshotAsOf{doc, def, at}` and `watch.open` carry `def` the same way; a read-only access has no transaction to answer `{need}` in, so when `def.migrates` is true and the stored version is older the core rejects `NeedMigrate` with the message `{"value":…,"from":N}` and the host repeats the request with `migrated` (without `migrates` the kernel's own `requires migration` error stands). The api `unloadDocuments{}` drops the core's loaded documents (session.ts unloadDocuments), so a later read loads, and migrates, again.

`end` also carries `elapsed`: the microtask passes the host spent holding the line, from `ready` (the line was granted) to `end` (or a failure), counted by one self-requeuing microtask and capped at 512. A host callback transaction is a job of Pi's duration on the line (scheduler.ts #gated, harness.ts commitWith); the passes its callbacks already took are part of that duration, so the core holds the line for the job's duration minus `elapsed` (never below zero) after `end`. The job's duration is Pi's change callback as the Transaction operations charged it (hopcost), the settle, the Storage commit and the return through `#enqueue`. The core answers `end` and publishes the commit 3 passes before the job's end, the passes the facade needs from the `tx_result` to its caller (`end()`'s reaction and `runCommit`'s return), and frees the line one hop before the end. A host that omits `elapsed` is counted as 0.

The core runs the built-in conversation-creation hook inside `createRootConversation`, `createConversation` and `forkConversation`, and the host runs `HarnessOptions.conversationCreated` itself, in the same transaction, right after the operation answers: the hook is the last step of creation, so its transaction operations continue the creating transaction and a throw fails it.

## Effects: fields beyond ABI.md section 6

- `tool` adds `handler` (registry index). Without it the host takes the first installed tool of that name.
- `section` adds `handler`. Without it the host asks the `agent` api and indexes `sections`.
- `hook` names: `beforeRequest {messages}`, `afterResponse {message}`, `onYield {answer}`, `afterTools {assistant, results}`, `beforeTool {call}`, `afterTool {call, result}`, `beforeCompact {compaction}`, `prepareArguments {arguments}`, each with `handler`. Host-answered hooks take no handler: `resolveAgent {state}` returns the resolved agent (wraps are host code), `conversationCreated`.
- Resolved agent JSON: `{model?, thinkingLevel, extensions: [names], tools: [{name, description, parameters, replay, handler, ...}], sections: [{key, tag, handler}], hooks: [{task, handlers: {hookName: handler}}], instructions?, cwd?}`. `hooks` are the selected extensions' hook tables in extension order; the core runs only those (agent.ts agentHooks). The core caches it per registry publication and stored `pi.agent` state.
- `env` adds `taskId`: the host keeps the built environment under it and gives it to the task's `section` and `tool` effects.
- `model_http` payload: `u32 headLength`, the head JSON, then the body recipe of section 10.2. The host answers with `model_bytes` phase 0 `{status, statusText, headers}`, chunks, end, or a transport error.
- `callback` names: document `initial`, `migrate` and `checkpointWhen` of extension definitions, and a conversation's `init` (names to be fixed with the document family owner).

## Hook results and section input (both hosts)

`hook_done` result by hook: `beforeRequest` `{messages}` or `null`; `onYield` `{continue: UserInput}` or `null`; `beforeTool` `{arguments}` or `{block}` or `null`; `afterTool` a tool result object `{output, isError?, details?, diagnostics?, usage?, control?}` or `null`; `beforeCompact` `{decline: true}` or `{summary}` or `null`; `prepareArguments` the repaired arguments; `afterResponse` and `afterTools` `null`. A hook that throws completes with outcome 1 `{name, message}`. A handler of the wrong kind for the hook name, an unknown hook name, or an undecodable payload is a protocol failure: the host discards the handle. The TS host still reports this case as a thrown outcome; that is a host bug owned by dcore-cfhost.

`section` input is `{shown: {key: text}}`. The host adds the conversation, the agent it resolved, the task's environment and a document reader. The `section` index selects `agent.sections[index]`; an index out of range is a protocol failure. The result is the rendered text or `null`. `tool` results use the same object as `afterTool`.

## Events the host sends for effects

- `model_event`: a JSON array of pi-ai events, batched until the next macrotask or 64 events; the first event whose partial has content (text_start) and a terminal event flush the batch at once, because Pi arms its partial flush timer in the microtask that yields that event. pi-ai mutates one partial message in place, so only the last event of a batch carries its `partial`; an earlier event carries `partial: null`, unless the content was still empty when it arrived (the partial throttle skips empty partials, CONTRACT section 3.9). The core must not read `partial` of a non-final event except to test for empty content.
- `tool_progress` with `skipped` non-zero (ABI 5.1 event 6; ratified by the lead 2026-10-07): the field holds `skipped.bytes`; the payload is `u32 metaLength`, `{bytes, newlines, endsWithNewline}`, then the chunk. `skipped` zero: the payload is the chunk.
- `tool_done` outcome 2 means the tool returned a value that is not strict JSON (a function, a cycle): the payload is `{name, message}` and the call faults, as pi-durable's settle commit rejects such a result. `tool_done` outcome 1 and `hook_done` outcome 1 carry `{name, message, stack?}`.

## Notices

`published` body: `{seq, submissions: [{id, conversationId, requestId?, status}], entries: [ids], tasks: [{id, kind, status}], documents?, watchId?, frame?}`; `seq` is the commit's sequence. A submission appears with its `id` when admitted and again on every status change. The host reads the settled record itself from `submissions`.

## Host-served reads (CONTRACT section 3.10)

`getTask` and `submission` read `tasks.record` and `submissions.record` from Pi's tables on the host connection. They need no core state.

## Watches and attached states

`api` op `watch.open {watchId, target}` with `target` = `{kind: "doc", address}` (the wire address of `snapshot`), `{kind: "view", conversationId}` or `{kind: "graph"}`. The host chooses `watchId`, unique for the life of the handle, and registers it before it sends the request. The answer is `{ok: {value}}`: the committed value at the acquisition boundary. `value: null` means the document or view is absent and the core opened no watch (the host answers `undefined`, as pi-durable's `watchDoc` does). Every later commit that changes the target is published in a `published` notice `{watchId, frame: {value, ops}}`, in commit order, with no overlap with the first value and no gap. `ops` is the Chord `Op[]` that takes the previous value to `value`. A `null` value retires the target and the core opens no further frames for that `watchId`. `watch.close {watchId}` releases it; the host sends it when a watch is stopped, cancelled, retired or its state is disposed, and not at handle close. A notice may carry frames in the same step as the `watch.open` answer; the host holds them until it has built the watch. The `view` target serves `Conversation.watch`, `viewState` and `watchEvents` (ABI section 8.1): its value is harness/view.ts `ConversationView` `{conversation, entries, docs}` (`docs` holds the mounted `pi.agent`, `pi.live`, `pi.inbox`, `pi.provider` and `pi.usage` documents that exist), and a view frame is `{ops}` without `value`: the host applies the ops to the value it holds (entry ops are `["p",["entries"],...]`, document ops are prefixed with `["docs", kind]`, a new incarnation or definition version replaces `["docs", kind]` whole). The `graph` target is the same: its value is `{tasks: {"<id>": TaskGraphNode}}` and a graph frame is `{ops}` without `value` (`["s",["tasks",id],node]`, `["d",["tasks",id]]`, `["s",["tasks",id,"conversations"],ids]`, `["s"|"d",["tasks",id,"blocked"],...]`). The view target's `watch.open` is a read on the Session line (view.ts attach is `readOnLine`): it answers when Pi's attach would resume, and with `completing: true` in the target the answer also carries `completing`, the IDs of the conversation's `pi.generation` tasks in status `completing`, read on that same line job (events.ts watchEvents). An observer joining a view the host already holds sends `view.attach {conversationId, completing?}`, a line job of its own that builds nothing and answers `{completing?}` the same way. A view opened with `changes: true` also gets `changes: {entries, tasks, submissions, nestedResults?}` in every frame: the records the commit wrote for that conversation (an empty-ops frame is sent when only those changed). `nestedResults` is present when the commit wrote `pi.tool.nested-call` documents of the conversation's tasks: `[{key, value}]`, `key` the nested call's key and `value` the document `{taskId, result?}` (a call's creation carries no result yet; the host reads a nested call's result by its `taskId`), read at the commit because the caller's documents may retire in the next one (events.ts `nestedResults`).

## Invocation-bound operations and the registry snapshot call

- `submit` and `abort` events carry `invocation` (the task ID of the calling invocation) when the call comes through an invocation-bound handle (`harness.ts` `boundConversation`: `api.conversation()` of a tool or task, and the submissions it returns). The core rejects such an operation at line-job start, with the invocation's abort reason, when the invocation was aborted or ended while the operation waited for the line: Pi's `throwIfAborted` at `session.ts:411` on `withAbortSignal(binding.signal, ...)` (`harness.ts:381`, `:391`). Unbound calls send no `invocation`.
- Hook `registrySnapshot` (no payload; answer: the registry snapshot JSON of `open.registry`): the host calls the user's `RegistryReader.snapshot()` once, synchronously when the effect starts, and answers its snapshot. The core emits it where Pi's `#decide` calls `registry.snapshot()` inside the step line job (`scheduler.ts:955`): the reader may run user code, even `close()`, and the `seal` event (ABI event 19) that `Harness.close()` sends synchronously reaches the core before the answer, because the host's effect handler answers a microtask after the reader returns. `seal` precedes the terminal `close`, which still waits for caller transactions. A core that does not know `seal` rejects it and nothing else changes.

## Storage gate

`open.storageGate` lists the Pi `Storage` methods the Storage the caller gave the host overrides (a subclass of `MemoryStorage`, or a proxy around it); the field is absent when none is. The core gates `commit`. Before it applies a commit it sends the host-answered hook `storageCommit {writes}` (`writes` is Pi's `StorageWrite[]`, in staging order) and applies the commit only when the hook completes. A hook that throws `StorageRejected` fails the commit and changes nothing; any other error fails it and poisons the Session (`session.ts #runCommit`). The line job that issued the hook holds the line and runs again from the start, at the same Harness time, when the answer arrives; a host transaction keeps the line and answers its `end` with a `tx_result` `{gated: true}` and later `{result}` or `{rejected}`. Other jobs and microtasks run while the line waits. A crash the host simulates is a hook that never completes: nothing of the commit reaches the store.

`api` op `opened` answers when the scheduler's open commit finished (`{ok: null}` or `{error}`); the host asks for it only when `storageGate` is set, and closes the Harness when it fails (`harness.ts Harness.open`).

A task runtime's context read is the `api` op `context` with `taskId`. The core keeps Pi's per-conversation range cache (`scheduler.ts #contexts`: head marker and tail of the last range, an idle period of `settings.contextRetentionMs`, ten minutes by default, one timer for the earliest expiry, dropped at seal) and issues Pi's read pattern to a Storage that overrides it: on the line the hooks `storageRead {method, args}` for `scanEntries` (one row) or `entry`, then `findLatestHeadMarker`; off the line `storageScanRange {query}`, which the host answers after scanning the range in pages of 256 (`context.ts scanRange`) when the cache has no range for the head marker or the tail grew, and not at all otherwise. The view itself comes from the core's transcript store.

## Context reads

The core reads the little a request preparation needs of a context (`pig_context_summary`, `pig_context_messages`, `pig_context_release`, ABI.md section 4.2) from the host, which derives it with the range algorithm that also derives the messages of a `model_context` range (`host/cf/src/contextstore.ts` `ContextReader`, `contextreads.ts` `answerContextRead`; `sqlhost/context.go` in the Go host). The estimate is a port of pi-ai's `estimate.ts` at the contract's reference commit (`durable/contract/PIN` main; `tokens.ts`, as `history/tokens.go`), because the installed pi-ai is older and counts 4 characters per token instead of 3.5.

## Close

`close` runs behind the Session line (`session.ts` close): the jobs and host transactions admitted before it, and the commit in flight, settle first. The core answers it with an `api_result` for request 0 when the Session is closed, in the same step when the line is idle. The host sends `close` after the effect handlers of the sealed invocations have completed (`harness.ts` close: `scheduler.join()`, then `session.close()`), waits for that answer, and then discards the handle. A transaction begins as a job on the line, so it keeps its place behind queued jobs, and the runtime of an invocation stays registered until the invocation ends: a commit queued behind the commit that ends it is rejected with `invocation has ended`.

## Origins (ABI section 5.4)

AsyncLocalStorage propagation. `src/async-context.ts` takes `AsyncLocalStorage.snapshot()` (nothing where the runtime has no `node:async_hooks`). `HostSession.enqueue` snapshots the caller's context for each event a client makes (`CALLER_EVENTS`: open, submit, abort, registry, api, inspect, resume, seal, close, tx, timer) and `deliver` numbers it and passes the number as `step`'s `origin` argument; completions and `hopped` pass 0. `apply` runs each effect (`start`, which sets timers too) and each notice (`notify`: `onNotice`, listeners, waiters) inside the snapshot its `origin` names, and runs 0 in the ambient context. A hops chain carries no origin: its hops run ambient, and the core restores the origin of the work it parked when it gets `hopped`.

The map of snapshots is the host's, and `origin_free` (notice 10) is the only thing that shrinks it besides a discard or a reopen: the core frees an origin at the end of a step without reads when nothing holds it. A step that is not ok drops the event's origin on the host's side. `reopen` resumes the new core in the context of the first `open`; `replay` and `resend` keep the context of the request they feed again (`ownedContexts`, `ReplayableEvent.context`). The flight recorder records each event's `origin` (the trap report and `replayEvents` pass it back; the binary recording of the Go count tool has no field for it, so a replay of one runs without origins). `HostSession.originsHeld` is the map's size.

## Hop chains

`open.storageProfile` names the Storage adapter whose await structure the core models when it charges hops for commits and reads. Values (owner decision S7, 2026-10-07 18:30): `memory`, `node-sqlite`, `cloudflare-do`, `jsonl`, `gate` (the conformance reference's capsql facade behind its lazy MemoryStorage proxy) and `gate-capsql` (the same facade opened directly: the reference's `openNodeSqliteStorage` and `openNodeJsonlStorage`). Each adapter names its own profile (`MemoryStorage` memory, `openNodeSqliteStorage` node-sqlite (charged the Node adapter's table, the profile `node`), `openDurableObjectSqliteStorage` cloudflare-do, `openNodeJsonlStorage` jsonl); `HarnessOptions.storageProfile` overrides it, and only the contract hooks (`facade/contract-setup.ts`, `useStorageProfile` mapping memory to `gate` and the node adapters to `gate-capsql`) select the gate profiles, so the gate's examples run the reference's profile while Pi's tests, unedited, run real adapters. The host always sends the field. The core owns the hop tables (dcore-store).

Status: the host side is implemented (`host.ts` `hops` effect, `wire.ts` `order`); the core does not emit `hops` yet. ABI.md section 5.3 has the kinds and the rules. The core decides where time passes; the host runs the hops and sends completions at Pi's resume points.

Host rules.
1. Process a step's notices and effects in its `order` list when it has one.
2. On a `hops` effect: `let left = n; const hop = () => { if (--left > 0) { if (n - left === at) apply(commits); queueMicrotask(hop) } else if (open.delete(id)) send(hopped{id}) }; open.add(id); queueMicrotask(hop)`. The chain's state lives in one pooled object whose `run` is bound once, so a hop allocates nothing. `cancel`, `close`, a protocol failure or a discarded handle drop the chain, and with it the commits it has not applied.
   The `hop` export answers a `hopped` event with an integer when the step has nothing to decode (ABI.md section 4.1): the host opens the one chain it names without a step, and an empty step costs one call and no allocation. The host falls back to `step` for a core without `hop`, when a trace or a settings reader is set, and when events are queued.
3. Send `tool_done`, `hook_done`, `phase_done` and the abort completion in the microtask where Pi's await of the handler resumes. The host must not add awaits or `.then` hops between the handler settling and the send. The audit of the current host against Pi's resume points is part of this change (`effects.ts`, `facade/taskruntime.ts`).
   A `cancel` only aborts the effect's signal: the host keeps the handler running and still sends its terminal event (`tool_done`, `hook_done`, `model_event` error/done), and the core settles on that event, as Pi awaits the handler it signalled (tool.ts:260 `await tool.execute`, generation.ts:415-426 `for await`, generation.ts:229 `fetchDeferred`). Only a discarded handle or `close` drops late completions (ABI section 4.6).
4. Send each host event when it happens; the core needs no stamp.
5. A facade promise that Pi resolves from a commit (submit, compact, abort, wait) resolves in the microtask the `api_result` notice is processed, so the caller's continuation lands the same number of hops later as in Pi (submit path measured at 3, equal to Pi).

Worked example, E20 (Pi ticks on `SqliteStorage`, dcore-trace's and cfhost's instrumented runs):

| tick | Pi | with hop chains |
|---|---|---|
| 471 | commit 3 resolves; `submit(first)` settles. The `#reserve` job is already queued behind it | `api_result(first)` then a `hops` chain for the reserve job's storage time, in one ordered list |
| 474 | the test, 3 hops after the settle, calls `submit(followUp)`; reserve runs 474-505 | host event arrives mid-chain; the core enqueues the follow-up behind the reserve job |
| 506 | reserve resolved at 503; `#start/#run/#step` enqueue 3 hops later | `hopped`, then a 3-hop chain; `#step`'s enqueue lands behind the follow-up (commit 4 is the follow-up) |

E25 (`compact()` at 5022 against the reserve job 5022-5053) and interop row I (tool `api.commit` at 966; settle enqueue +5, behind the reserve's `#step` path) have the same shape. E23 round 2064933: the host's phase delivery (chain from the publication of commit 66) and `#runAbort`'s `#step` (chain from job196's resolution, then abort handler return and `#step` enqueue in one microtask) land in the same round, delivery first by FIFO position; real chains reproduce it without a tie rule.

Cost. A chain costs the host `n` microtasks (a few hundred ns each) and one core step (one wasm call and one step decode) when it ends; nothing else. The core parks one chain per Session-line job (its storage hops), plus the short continuation chains of Pi's scheduler path (reserve to `#step`, `#runAbort` to `#step`), so a turn costs about three chains per commit. The measured chain count per W1 turn and the W1/W2-3500 budget check belong to the change that makes the core emit `hops`; the host side is O(n) microtasks per chain and allocation-free (one closure per chain).

Superseded drafts: a virtual clock with `yield`/stamped `tick`, and a notice-based `hops`.

## Observability and the flight recorder

`observe.ts` gives each object per-step records and a replay buffer. `DoSessionConfig.recorder` takes a `FlightRecorder`; the session attaches it to the core handle and the object's store at every cold open, so it describes one session lifetime and is rebuilt like every other cache of SQLite (ADR D9).

- **Step records** (`recorder.stepRecords()`, the last 1,024 by default): the event kind, the crossings (the step, each `pig.read`, each `pig.uuidv7`), the statements, commits and rows read and written in the store from the step's start to the next step's (the commits the host applied for a step are its own), bytes in and out, the notices and effects the step returned, linear memory, the bytes allocated and allocations during the step (differences of the Wasm core's `alloc_stats`, which runs no collection), step time and the core version. `liveEvery: N` also asks the core for its live heap (`mem_stats`, which runs a full collection) after every Nth step; it is off by default. The count gate's allocation numbers come from a replay, not from these records (`durable/contract/README.md`, "Replay counts"): the records are a gauge of the live object.
- **The ring** (`recorder.recordedEvents()`, the last 256 events by default): each event's payload bytes, the `pig.read` requests and answers and the uuids the core took while it ran. The first event of the session (the open) is also kept apart. The clock is the event's `now` and ids come from the host, so these are all the core's inputs. The recorder copies bytes; it does not hash or decode a step and never blocks one.
- **Trap reports**: when a step fails, the `FatalError` the session raises carries `report` (`recorder.report(error)`): the error, the core's abi_id and build, the ring, the open event and the step records, as JSON (bytes in base64). `replayReport(module, report)` replays a ring that holds the whole session on a fresh core with the recorded reads and uuids served in order; an event that makes the core take a read or uuid it did not take, or ask a different read, stops the replay as a divergence. A report whose ring dropped the start of the session replays the way recovery does (ADR D16): a core opened over the object's store (an export of its SQLite) with the recorded open, then the failing event once.
- **Recordings**: `recorder.recording()` writes the ring in the format `durable/core/contracttest/counts` reads, so `countgate replay` runs it natively and under both Wasm builds. It refuses a ring that dropped events: the core's state before the first is not in it.

## Trap recovery and recycling (host)

ADR-0001 D16, Durable plan 2 item 3. Two owners replace a trapped handle; they share the events and the rule that a trap is recoverable once.

A Durable Object session (`DoSession.recover`, cfhost c998fb256b) reopens in place: the failed step names its root event (`FatalError.event`); the session drops the instance, opens a new one from SQLite, fails the in-flight client requests except the one the failed step began (`CoreClient.failAll(error, keep)`), binds the client to the new session (`rebind`) and feeds that request once (`HostSession.resend`). A second trap on the fed request, or on the reopen, is final: the caller gets the error and the object alarm retries with backoff (`retryLater`). Every `FatalError` carries the last 32 events (`recent`).

A Harness (the facade, which has no object to own the reopen) passes `HostOptions.renew` and the host loop does it (`HostSession`: `trapped`, `reopen`, `recycle`, `Renewal`). A trap is a `CoreTrap`: the core threw in `step` or `rows`, ran out of memory at the module's cap, or called `proc_exit`. Nothing of the trapped step was applied: commits are applied only after the step returns. The host then:

1. Cancels what the old handle started: effect signals abort, hops chains stop, `onCancel` names each running effect, and the timer driver forgets its timers (`TimerDriver.reset`). A late completion from an old effect is dropped, because effect IDs restart in the new handle (`EffectHost` belongs to one epoch).
2. Gives the handle up (`Renewal.drop(trap)`): the lease is released and its instance dropped; the next `acquire` is a new instance of the module.
3. Sends `open` with the owner's current payload on the new handle, then `resume` and `seal` again if the old handle had been sent them.
4. Tells the owner (`onRecycled`): the client sends its unanswered requests again under their IDs, except those the old core may have applied and that cannot apply twice (a submission without a request ID, a withdrawal of a submission), which fail with `RecycledUncertainError`; it sends the `begin` of a transaction that had not taken the line again, acknowledges a transaction whose `end` reached the store before the drop (`RecycledError` otherwise: nothing of it was committed), and sends a `close` the old core took and had not answered. The facade wakes the waits that end on a `published` notice, asks for commit publication again when it has listeners, and opens its watches again (`WatchHub.reattach`).
5. Runs the pending event once more when it is not owned by the client and does not name the old handle's work (`close`, `resume`, `seal`, a direct `submit`). Events that name the old handle's work (`model_event`, `tool_done`, `hook_done`, `phase_done`, `timer`, `hopped`, `tx`, `rows` and the like) are dropped: the reopened core re-derives that work from the store, as it does after a process restart. A trap in the `rows` that answer a step's reads is a trap on the event that began the chain: the host applies nothing of a step that asks for reads, so that event is the pending one (a client request among them counts as undelivered).

A second trap before the recovery window closes (the reopen, the refeed and the replays) fails the host: `FatalError` "trapped again while recovering", cause the `CoreTrap`. The window ends at a sentinel queued behind the refeed, so a later unrelated trap recycles again. Without `HostOptions.renew` a trap is fatal, as every other failure of the core is.

Known gap. The `published` notice of a commit follows the commit by a hops chain. A trap inside that window loses the notice: the commit is in the store, but its listeners (`subscribeCommits`, the frame of a view watch) are never told. Waits recover and watches resync by value, but a commit-publication listener misses that one commit.

Recycle at a quiet point. `HostSession.quiet` is true when no event is queued, no effect or chain is running and no reopen is pending; the facade adds that no request, transaction or wait is unanswered (`Harness.quiet`). When the instance's linear memory is over `PoolOptions.highWater` (it never shrinks), the pool asks the idle object to give up its session (`Tenant.unload`; a Harness: `HostSession.recycle`, a Durable Object: its cache drop): the instance goes and the next event cold-opens a fresh one. The facade checks at the first quiet point after an event once the instance is over the mark, one microtask later so a caller's next request keeps the host busy.

Counters: `HostCounters.traps` (core traps caught) and `recycles` (handles replaced). Tests: `test/do-recovery.test.ts` (the Durable Object path), `test/host-recycle.test.ts` (the host loop against scripted cores), `test/recycle.test.ts` (a trap, before and after, at every event of a tool turn on the real core; a poison event; quiet recycling; a transaction at every trap point; a watch at every event of a commit), and `durable/contract` `robust recycle` (the crash scenario with a trap after each of its commits, wasm builds only).
